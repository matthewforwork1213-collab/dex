> 이 문서가 기준 문서다(통합본 없음, 2026-10-01 정리).
> **범위**: (1) 사용자 API(API-001~007)의 서버 처리 (2) 공통 시스템 로직 F-012~F-020 (3) 공통 알림 F-031~F-033.
> **(2)·(3) 공통 섹션은 백오피스 백엔드 문서에 같은 내용으로 중복 수록**되어 있다. 고칠 때는 두 문서를 함께 고친다.
> F-ID는 분할 전 통합 번호를 그대로 쓴다. 같은 F-ID가 프론트 문서에도 있으며, 프론트는 화면, 백엔드는 서버 처리를 다룬다.
> 모든 날짜·시각 판정은 **UTC**, 금액은 **USDT**(소수점 둘째 자리 10진 문자열, 부동소수점 금지). API 응답의 일시는 UTC ISO-8601로 내려주며, 사용자 화면의 로컬 시간 변환은 프론트가 한다(NFR-011, 서버는 변환하지 않음).
> **미정 항목 개발 기본값(2026-10-07)**: 확정 전까지 아래 값으로 개발하고, 확정되면 이 문서를 고친다. 서비스명 = 맥스보드 / MAX BOARD(#NAME), 빙고판 배경색 = TetherMax 기본 파랑 고정·백오피스 입력 없음(색 변경 기능 검토 중, #COLOR), 혜택 상세 상단 큰 제목 = 어드민 입력 제목(`<br />` 줄바꿈 적용, #TITLE), 빙고 Batch 실행 시각 = 설정값(예시 12:30 UTC, #BATCH), SEO 중국어 간체 = 미지원(#SC), 배너 외 추가 이미지 = 없음(배너는 혜택 목록 카드 전용, #IMG). "오늘 마감"은 기기 로컬 날짜 기준(확정 2026-10-07).
> **구현 기준(확정 2026-10-12)**: 목업 기본 화면(V2) 배치 + 문서 규칙(문구·정책은 문서 우선). **용어**: 달성 = 줄·빙고판 완성(·랭킹 순위)으로 받을 예정인 상태(돈은 아직 안 나감), 지급(적립) = 지급 기간 시작 시 참여 UID로 실제 지급(요구사항정의서 "용어").

## 1. 사용자 API 서버 처리

### F-001. 혜택 목록 조회

| 항목 | 내용 |
|------|------|
| 설명 | 혜택 목록에 노출할 맥스보드 카드 목록을 준다. |
| API | API-001 `GET /api/maxboard/boards` (공개) |
| 입력 | `lang` |
| 처리 | 단계가 PREVIEW~PAYOUT인 빙고판만 조회(SCHEDULED·ENDED·TERMINATED 제외). 정렬은 등록 최신순(`createdAt` 내림차순). `lang=KO`면 KO 제목·부제목, 그 외는 EN |
| 출력 | 카드 목록(boardId, benefitNo, 거래소, 단계, 랭킹 ON/OFF, 제목, 부제목, 배너 URL, 상세 경로, 등록 시각). 제목·부제목은 `<br />`을 포함한 저장값 그대로 반환(REQ-107). 상세 경로는 `/{lang}/max-board?benefitNo={n}`(글로벌 리그와 같은 방식, 번호는 백엔드가 빙고판 생성 시 발급) |
| 예외 | 공개 캐시 대상. 캐시 무효화 이벤트는 API스펙 1.1 "캐싱"(단계 전환, 콘텐츠 수정, 강제 종료 등). **강제 종료 시 캐시 즉시 무효화**(REQ-071) |
| 관련 요구사항 | REQ-057, REQ-071, REQ-075, REQ-085 |

### F-002. 혜택 상세 조회

| 항목 | 내용 |
|------|------|
| 설명 | 단계와 랭킹 ON/OFF에 맞는 상세 구성 정보를 준다. 개인화 정보는 넣지 않는다. |
| API | API-002 `GET /api/maxboard/boards/{boardId}` 또는 `GET /api/maxboard/benefits/{benefitNo}` (공개, 응답 동일, `benefitNo` 포함, 확정 2026-10-05) |
| 입력 | `boardId`, `lang` |
| 처리 | 단계별 `actions`(participationOpen, checkOpen)와 `notice`(AGGREGATING / RESULT_ANNOUNCED / PAYOUT_IN_PROGRESS) 계산. 단계 구간마다 `startDate`, `endDate`(마지막 날, 포함), `startAt`(시작일 00:00:00Z), `endAt`(종료일 23:59:59Z), `days`(종료일 − 시작일 + 1) 제공. 랭킹 OFF면 `ranking` 키와 `ANNOUNCEMENT` 단계를 응답에서 생략. `batchDelayed`(공개, 확정 2026-10-12)는 F-006과 같은 기준(참여 단계에서만 true 가능)으로 계산해 비회원·리더보드 지연 안내에 쓴다. `rewards.maxPerPerson` = 가로 3줄 + 세로 3줄 + 완성 리워드 합계(히어로 "빙고 리워드 최대", 확정 2026-10-12) |
| 출력 | 빙고판 기본 정보, 단계 일정, 자격 기준일(`uidRegisteredOnOrAfter` = 참여 시작일 − 30일), 9칸 구성, 리워드 7종과 1인 최대 금액, 랭킹 구간(ON), SEO, `batchDelayed`, 응답 시점 서버 UTC 시각 `serverTime`(참여 마감 카운트다운 기준, 확정 2026-10-07). `serverTime`은 공개 캐시에서 빼고 응답할 때마다 채운다(캐시 구성상 어려우면 응답 헤더 `Date`로 대신, 확정 2026-10-12) |
| 예외 | 없는 빙고판·SCHEDULED(노출 전)·ENDED·TERMINATED → `404 BOARD_NOT_FOUND`. 유의사항은 프론트 고정 문구라 API로 내려주지 않는다(REQ-108). 공개 캐시 대상이며 무효화 이벤트는 API스펙 1.1 "캐싱"(빙고 Batch 지연 상태 변경 포함) |
| 관련 요구사항 | REQ-054~057, REQ-063, REQ-076, REQ-082, REQ-112, REQ-117, REQ-128 |

### F-003. 참여 가능 여부 판정

| 항목 | 내용 |
|------|------|
| 설명 | 로그인 TUID의 참여 상태를 판정하고 자격 UID 목록을 준다. |
| API | API-003 `GET /api/maxboard/boards/{boardId}/eligibility` (공개, 비회원은 GUEST. `Cache-Control: private, no-store`) |
| 입력 | 인증 정보의 TUID, TUID에 연동된 UID 목록(계정 시스템), 빙고판 거래소·참여 시작일, 빙고판별 참여 기록 |
| 처리 | 자격 UID = 아래를 **모두** 만족하는 UID. (1) 요청 TUID에 현재 연동 (2) 빙고판 대상 거래소 UID (3) **테더맥스 DB 최초 등록일(UTC 날짜) ≥ 참여 시작일 − 30일**(참여 기간 중 등록 포함, 다시 연동돼도 최초 등록일 기준) (4) **이 빙고판** 참여 기록 없음 (5) **이슈 UID로 지정되지 않음**(확정 2026-10-02). TUID 가입일은 보지 않는다. 사전공개 단계에도 같은 기준(참여 시작일 − 30일)으로 판정한다(확정 2026-10-05). 상태 판정: GUEST / PARTICIPATING(현재 TUID의 PARTICIPATING·EXCLUDED·WITHDRAWN 참여가 있고 그 참여 UID를 아직 보유) / RESELECT_REQUIRED(참여 UID를 잃음: 마지막 참여가 RESET 또는 FORFEITED이고 활성 참여 없음, 또는 지급(적립) 후 소유권 이전·이슈 UID 지정으로 참여 UID를 잃어 이력만 남은 경우, 확정 2026-10-12) / NOT_REGISTERED(자격 UID 1개 이상) / NO_ELIGIBLE_UID(0개). 사용자는 UID를 직접 연동 해제할 수 없으므로 참여 UID를 잃는 원인은 소유권 이전·이슈 UID 지정뿐이다 |
| 출력 | `state`, `exchange`(거래소 코드·이름, 화면 문구 `{거래소}` 치환용), `eligibleUids`(**UID만**, 게이지 미반환), `actions.canRegister`(NOT_REGISTERED + PARTICIPATION 단계), `actions.canReselect`(RESELECT_REQUIRED + PARTICIPATION 단계 + 자격 UID ≥ 1). RESELECT_REQUIRED면 `resetUid`(잃은 참여 UID), `resetAt`(계정 DB 이력 시각), `resetReason`(`OWNERSHIP_TRANSFER` / `ISSUE_UID`, 화면 분기에는 쓰지 않음) |
| 예외 | `404 BOARD_NOT_FOUND`, 계정 시스템 조회 실패 → `503 SERVICE_UNAVAILABLE` |
| 관련 요구사항 | REQ-022~027, REQ-030, REQ-031, REQ-077, REQ-110, REQ-114, REQ-115 |

### F-004·F-005. 참여 UID 등록·재선택

| 항목 | 내용 |
|------|------|
| 설명 | 자격 UID 1개를 참여 UID로 등록한다. 참여 UID를 잃어 초기화(`RESET`)된 뒤의 재선택도 같은 API로 처리한다. |
| API | API-004 `POST /api/maxboard/boards/{boardId}/participation` (로그인) body `{ uid, confirmed }` |
| 처리 순서 | 1) 단계 = PARTICIPATION(마지막 날 포함) 2) TUID의 이 빙고판 참여 상태 확인: 활성 참여 있으면 거부, RESET만 있으면 재선택 모드(`mode: RESELECT`). FORFEITED는 집계 시작 이후에만 생기므로 1)에서 거부됨 3) 요청 UID 자격 재확인(F-003 조건 1~5) 4) 참여 레코드 생성(TUID, UID, 등록 시각) — **이 시점에 참여 기록이 생긴다** 5) 참여 시작일부터 그 UID에 쌓인 게이지·연속 기록·연속 칸 활성화 이력을 그대로 연결(소급). 재선택이면 그 빙고판에서 처음 온 사람처럼 시작: 이전 참여의 칸·줄·완성·랭킹·달성 리워드는 승계하지 않음(확정 2026-10-12) 6) `UID_REGISTERED` 이력 기록(소급 게이지 값 포함) |
| 동시성 | `(boardId, uid)` 유일 제약, `(boardId, tuid, 활성)` 유일 제약으로 동시 요청 시 1건만 성공 |
| 출력 | participantId, mode(NEW / RESELECT), uid, 등록 시각, 소급 결과(사용 가능 게이지, 현재·최장 연속(최장 연속은 사용자 화면 미사용), 활성 연속 칸, 반영 기준일). 반영 기준일은 정합성 확인·CS용이며 화면에 표시하지 않는다. 다음 업데이트 시각은 주지 않는다(확정 2026-10-02) |
| 에러 코드 | `VALIDATION_ERROR`, `CONFIRMATION_REQUIRED`(confirmed≠true), `UNAUTHORIZED`, `BOARD_NOT_FOUND`, `PHASE_NOT_PARTICIPATION`, `ALREADY_PARTICIPATING`, `UID_NOT_LINKED`, `UID_EXCHANGE_MISMATCH`, `UID_REGISTERED_TOO_EARLY`, `UID_ALREADY_PARTICIPATED`(원 TUID로 다시 돌아온 UID·다른 TUID에서 이전된 UID 포함), `UID_ISSUE_DESIGNATED`(이슈 UID), `CONCURRENT_REQUEST` |
| 예외 | 참여 UID 변경 API는 없다. 집계 시작 이후 참여 UID를 잃은 사용자(소멸)는 재선택 불가 → 리워드 없음 |
| 관련 요구사항 | REQ-023~031, REQ-033, REQ-114 |

### F-006. 내 빙고판 현황 조회

### F-012. 빙고 Batch: 페이백 반영·게이지 적립

| 항목 | 내용 |
|------|------|
| 설명 | 빙고 Batch가 페이백 배치 결과를 불러와 진행 중인 빙고판의 자격 UID 게이지에 적립한다. |
| 입력 | 테더맥스 페이백 DB의 페이백 배치 결과(UID별 거래 페이백, 페이백 배치 반영일), 진행 중 빙고판 목록 |

| 처리 | **빙고 Batch 실행 시각**이 빙고판 **참여 기간(시작일 00:00:00 UTC부터 종료일 23:59:59 UTC까지) 안**인 빙고 Batch가 가져온 페이백만 반영(마지막 날 실행분 포함). 그날 빙고 Batch는 그날 완료된 페이백 배치 결과와, 전날 빙고 Batch 뒤에 늦게 끝난 페이백 배치 결과를 가져온다. 늦게 들어온 페이백은 **원래 페이백 배치 반영일로 기록**한다(연속 유지). 대상: 빙고판 거래소 UID 중 **테더맥스 DB 최초 등록일 ≥ 참여 시작일 − 30일**인 모든 UID(연동 여부·참여 등록 여부와 무관, 비회원 UID와 **이미 참여 중인 UID 포함**). ### F-016. UID 소유권 이전·탈퇴 처리

| 항목 | 내용 |
|------|------|
| 설명 | 참여 UID의 소유권 이전, 이슈 UID 지정, TUID 탈퇴를 반영한다. 사용자는 UID를 직접 연동 해제할 수 없으므로 참여 UID를 잃는 원인은 소유권 이전(다른 사람이 소유권 인증으로 가져감)과 이슈 UID 지정 두 가지다(확정 2026-10-12). |
| 입력 | 계정 DB의 소유권 이전 이력, 이슈 UID 지정 이력, TUID 탈퇴 이력(모두 맥스보드가 직접 확인). 판정 시각은 **테더맥스 계정 DB 이력의 시각**(확정 2026-10-12) |
| 처리 | 확인 시점: 사용자 요청 시(상세 진입·참여 등록·칸 체크), 매일 빙고 Batch(참여 기간 이후에도 **지급 완료까지** 계속 대조, 확정 2026-10-12), 리워드 확정(F-017)·적립(F-018) 직전. 소유권 이전·이슈 UID 지정은 같은 규칙으로 처리하며 이력 시각으로 상태를 정한다: (1) 참여 기간 안 → 초기화(`RESET`, 사유 `OWNERSHIP_TRANSFER` / `ISSUE_UID`). 그 빙고판에서 처음 온 사람처럼 된다(체크 칸·줄·완성·랭킹·달성 리워드 전부 이 TUID 진행에서 분리). 새 UID를 선택할 수 있고 새 UID는 자기 게이지·연속 이력으로 시작. 완성자였다면 다음 빙고 Batch 산정에서 순위 대상에서 빠짐(자리 비움 아님). 단, 이력 시각이 참여 기간 안이어도 **집계 시작 재산정 이후에 감지**되면 순위를 다시 당기지 않도록 (2) 소멸로 처리한다(확정 2026-10-12) (2) 집계 시작 이후~지급(적립) 전 → 소멸(`FORFEITED`, 같은 사유). 새 UID 선택 불가, 리워드 없음, 완성자면 랭킹 자리 비움 (3) 지급(적립) 이후 → 이미 지급된 금액은 회수하지 않고 참여 상태·지급 금액은 바꾸지 않으며 이력만 남김. 리워드는 지급 기간 시작 때 최종 상태 기준으로 한 번만 지급하므로 이중 지급은 없다(확정 2026-10-12). 소유권 이전된 참여는 새 TUID로 넘어가지 않는다. 이슈 UID는 자격 UID 목록에서 제외(F-003), 지정 기간 게이지·연속 미기록(F-012). 탈퇴: 해당 TUID의 모든 빙고판 참여 상태 `WITHDRAWN`, 리워드 미지급. 참여 기간 중 탈퇴한 완성자는 순위 대상에서 빠지고, 집계 시작 이후 탈퇴는 랭킹 자리 비움 |
| 출력 | 참여 상태(초기화 `RESET` / 소멸 `FORFEITED` / 탈퇴 `WITHDRAWN`)와 사유(`resetReason`: `OWNERSHIP_TRANSFER` / `ISSUE_UID`, RESET·FORFEITED 공통), 이력(초기화 `RESET`·소멸 `FORFEITED`·지급 후 UID 변경 `UID_LOST_AFTER_PAYOUT`, 계정 DB 이력 시각 포함) |
| 예외 처리 | 이전된 UID는 새 TUID에서도, 원 TUID로 다시 돌아와도 같은 빙고판 재참여 불가(진행 복원 없음). 이슈 UID 지정이 풀려도 재참여 불가 |
| 관련 화면 | 혜택 상세, 어드민 참여자 목록 |

### F-019. 빙고 Batch 지연·누락 판정, 누락 복구·재계산

Slack 알림은 F-031 |
| 처리 | 그날의 **빙고 Batch를 다시 실행**: 테더맥스 페이백 DB에서 그날 데이터를 다시 읽어 **누락일의 배치 기록으로** 반영 → 게이지(F-012)·연속 기록·연속 칸 활성화(F-013)·랭킹(F-014) 재계산. 칸 체크는 사용자가 하므로 체크 칸·줄·완성은 바뀌지 않는다. 누락으로 끊긴 연속은 이어짐. 복구가 끝나면 그 날짜 행은 결과 `MISSING`을 그대로 두고 `recovered=true`, `recoverable=false`(다시 복구 불가)로 표시(확정 2026-10-12). 재계산 반영 여부(`applied`)는 **복구 요청 시점의 단계**로 정한다: 참여 기간 중 요청이면 재계산 반영, 참여 기간 종료 후 요청이면 원천 기록만 보정하고 이력 유형 `SOURCE_CORRECTED`로 남긴다(확정 2026-10-12) |
| 출력 | 재계산 결과, 복구·재계산 이력(대상 UID, 복구한 배치 반영일, 변경 전·후 값, 실행 주체, 시각) |
| 예외 처리 | 이미 활성화된 연속 칸·체크한 칸은 유지. **참여 기간 종료 후에도 복구는 실행할 수 있으나 원천 기록만 보정하고 자동 반영 안 함**(`SOURCE_CORRECTED`, CS가 기존 수동 지급 기능으로 개별 처리). 원천 데이터가 없으면 페이백 시스템에서 먼저 채운 뒤 복구. 강제 종료되면 실행 중인 복구도 중단 |
| 관련 화면 | 어드민 ③ 배치 탭 |
| 관련 API | API-110(배치 결과 조회), API-111 `POST /api/admin/maxboard/boards/{boardId}/batches/{batchDate}/recover`(복구, 백오피스 API스펙) |
