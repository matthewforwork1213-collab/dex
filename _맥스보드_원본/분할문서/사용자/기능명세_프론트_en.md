> This document is the reference document (no consolidated version; organized 2026-10-01).
> **Scope**: what the user screen shows and takes as input. Server judgment, storage and batches are in `기능명세_백엔드_en.md`.
> F-IDs keep the consolidated numbering from before the split. The same F-ID also exists in the back-end document; the front end covers the screen, the back end covers server processing.
> Items marked **[Tentative]** are not yet confirmed in planning. This document will be updated once they are confirmed.
> **Implementation basis (confirmed 2026-10-12)**: the **screen layout of the default screen (V2, event-style design)** of the deployed mockup `src/mockup/index.html` + **the rules in this document**. V2 changes only the layout (design); **for copy and policy this document prevails**. The V2 layout elements (hero, participation area, section tabs, Bingo mission area and HOW TO PLAY, 02 / REWARDS) are described in F-002 "Screen composition" and Information Architecture 1.4. Parts of V2 that differ from the document rules (the secondary text "TETHERMAX × exchange / PAYBACK EVENT" at the top, English "payback" and "Maxboard" wording, the full schedule expanded by default without times, the deadline hidden below the countdown, the pre-open name "사전 공개 / Preview") are **not implemented**; follow this document. The default screen settings (Cell Mix "Mixed", Board Color "Default", Service Name "맥스보드") are the baseline; the mockup's scenario panel (stage, user and width switches, etc.), the V1 comparison screen (`?ui=v1`), improvement options, and the cell mix, board color, contrast correction and service name toggles are **for comparison and demos only and are not implemented**. The cell mix display (amount cells only / streak cells only) is applied automatically according to the actual board setup (F-006).
> **Development defaults for open items (2026-10-07)**: develop with the values below until they are decided, then update this document. Service name = 맥스보드 / MAX BOARD (#NAME); board background color = fixed TetherMax default blue with no back-office input (a color change feature is under review, #COLOR); large title at the top of the benefit detail = admin-entered title (`<br />` line breaks applied, #TITLE); Bingo Batch run time = a setting (example 12:30 UTC, #BATCH); SEO Simplified Chinese = not supported (#SC); additional images other than the banner = none (the banner is only for the Benefits list card, #IMG). "Ends Today" is based on the device local date (confirmed 2026-10-07).

## 2. Common Rules

| Item | Rule | Basis |
|------|------|------|
| Time | All API date-times are UTC. Neither the next update time nor the last updated time is shown anywhere on the user screen (confirmed 2026-10-02; last updated time confirmed 2026-10-12). Dates and times on screen (stage periods, participation start time, eligibility reference time, payout date, history times, etc.) are **converted to the user's device local time** and shown without "UTC". The front end does the conversion. Judgments (stage changes, whether the user can join, etc.) follow the server's UTC values as-is. Exception: the common Notes text keeps the UTC notice ("All dates and times are based on UTC." (KO "모든 기간과 시각은 UTC 기준입니다")) (notice of the judgment basis) | NFR-011 (confirmed 2026-10-02) |
| Period format | Stage periods convert the API's `startAt` ~ `endAt` (= start date 00:00:00 UTC ~ end date 23:59:59 UTC) to device local time and show **both date and time** (because the local date can differ from the UTC date). Where only `startDate`/`endDate` are used, attach the boundary times (00:00:00 / 23:59:59 UTC) and then convert. Example: participation 10-08 ~ 10-21 (UTC) → on a KST device "2026.10.08 09:00 ~ 2026.10.22 08:59" | API Specification 1.1, 1.5 |
| Amounts | API amounts are decimal strings with two decimal places (`"12.50"`). Do not convert them to numbers (floating point) for calculation; display them from the string. The unit is USDT. Display rules (confirmed 2026-10-12): **admin-set amounts** (cell target amount, line and Full Board Rewards, ranking tier amounts, hero "Maximum Bingo Rewards" total, Total Ranking Rewards) are shown with unnecessary trailing zeros in the decimal part removed (`"3.00"` → "3", `"2.50"` → "2.5", e.g., "+3 USDT", "2.5 USDT"). **Calculated values** (Bingo Gauge, My Rewards amounts and total, total cashback) are shown with two decimal places as-is (e.g., "12.50 USDT") | API Specification 1.1, REQ-129 |
| Error copy | API `error.message` is for developers. User copy is selected from i18n resources by `error.code` | NFR-009 |
| Language | Title, subtitle and OG are KO for KO and EN for all other languages. The `lang` query is sent only to API-001 and 002, which have per-language content (not sent to API-003~007) | REQ-085 |
| Terms | Reward, Bingo (Row/Column), Bingo Reward, Full Board, Full Board Reward, Check, Bingo Gauge, N-Day Cashback Streak, Ranking Reward. In English, 페이백 is written as **Cashback** and the service name as **MAX BOARD** (no "payback" or "Maxboard"). The aggregation stage label is KO "집계 중", EN "Calculating" (the language pack's "계산 중" is not used, confirmed 2026-10-02). Stage names (user screen): Pre-launch / Participation / Calculating / Results / Reward Distribution (KO 오픈 예정 / 참여 기간 / 결과 집계 / 결과 발표 / 리워드 지급; Participation needs language-pack review. "사전 공개 / Preview" is not used). Ends in / Ends Today (KO 참여 마감까지 / 오늘 마감). Countdown units Days / Hrs / Mins / Secs (KO 일 / 시간 / 분 / 초). Max Cells to Check (KO 체크 가능한 최대 칸). Paying Out Sequentially (KO 순차적으로 지급 중) [EN draft] (confirmed 2026-10-05~06). Internal terms (KO "보상", "줄 달성") are not used on screen. EN equivalents: 리워드 Reward, 빙고(가로/세로) Bingo (Row / Column Bingo), 빙고 리워드 Bingo Reward, 빙고판 완성 Full Board, 완성 리워드 Full Board Reward, 칸 체크 Check, 빙고 게이지 Bingo Gauge, N일 연속 페이백 N-Day Cashback Streak, 랭킹 리워드 Ranking Reward, 이벤트 리워드 Event Reward, 유의사항 Notes. Sentence tone follows the TetherMax language pack (summary: `05.리포트/맥스보드_문구_톤가이드.md`). **Achieved and paid (credited)** (confirmed 2026-10-12): achieved = the state in which a reward is **expected to be received** through a completed line or Full Board (or placing within the ranking) (no money paid yet; My Rewards badges "Pending" / "Calculating" / "Confirmed"); paid (credited) = **actually paying** the confirmed rewards to the participating UID at the start of the payout period (the screen says "paid" (지급) and the system process is called "credit" (적립); same meaning). When the participating UID is lost and the user is reset, all achieved rewards on that board disappear too (F-005) | REQ-083, Requirements Definition "Terms" |
| Line breaks | If the title or subtitle contains `<br />`, `<br/>` or `<br>` (case-insensitive), **show it as a line break** (both on the Benefits list card and the benefit detail). Not applied to the SEO title/description or OG. HTML tags other than `<br />` are not executed and are shown as literal text (security). There is no character limit, so wrap long text without breaking the layout | REQ-107 |
| Ranking OFF | If `rankingEnabled=false`, **do not render** the ranking info area, the leaderboard or the announcement stage (the API response has no `ranking` key and no `ANNOUNCEMENT` stage either) | REQ-082, NFR-008 |
| 404 | If any user API returns `404 BOARD_NOT_FOUND`, go to SCR-U05 (including payout period ended and terminated) | REQ-057, REQ-071 |
| Responsive | Mobile responsive. Non-members can also view | NFR-012 |
| Disabled buttons | Buttons that cannot be pressed ("Opens on ○○", "Calculating", "Participation Ended", "Unavailable") are drawn with a gray background and gray text, a not-allowed cursor and no click events (`disabled`). Active buttons keep their color (confirmed 2026-10-06). Which button appears for each stage × state is in the section 3 "Button table" | REQ-119 |
| Countdown time | The participation deadline countdown (F-002) computes time left from the difference between API-002 `serverTime` (server UTC) and `PARTICIPATION.endAt` instead of the device clock, then counts down every second by elapsed device time (accurate even if the device clock is wrong). At 0, reload the detail. API-002 is publicly cached, but `serverTime` is not cached and is filled in on every response. If the cache setup makes this difficult, the front end derives the server time from the `Date` response header (adding `Age` for a cached response) (confirmed 2026-10-12) | REQ-117, API Specification API-002 |
| Notes | Show the **common Notes for all boards** at the bottom of the benefit detail. The text is fixed (hardcoded) in front-end i18n resources in **15 languages** and shown in the user's language. The original text is managed in the language pack / copy sheet; the KO/EN text in the mockup is for convenience only (confirmed 2026-10-12). No API or back-office input. Only `<br />` inside the text is treated as a line break. As an exception, the text "All dates and times are based on UTC." (KO "모든 기간과 시각은 UTC 기준입니다") is kept (notice of the judgment basis) | REQ-108 |
| Cache | Benefits list and detail use a public cache (except the detail's `serverTime`). The leaderboard (API-007) uses a public cache **only for logged-out requests**; logged-in requests contain personal data in `me`, so they are received with `Cache-Control: private, no-store` (confirmed 2026-10-12). Personalized responses (`/eligibility`, `/me`) are not cached. Cache invalidation is done by the server (API Specification 1.1) | NFR-001 |

- **Pre-open eligibility display** (confirmed 2026-10-05): in the pre-open stage too, eligibility is checked with the logged-in user's currently linked UIDs and the result is shown (the 30-day rule is computed from the participation start date, so the result is the same after the start. Later changes such as an ownership transfer or issue UID designation are judged again in the participation period). API-003 judges `state` and `eligibleUids` in pre-open as well, and `actions.canRegister` is `false`. In pre-open there is no [Link UID] button, only the guidance text, and the button is the disabled "Opens on ○○" for all users (○○ = participation start date and time, local time, KO "○○ 오픈 예정") (confirmed 2026-10-12).
- **Post-participation screen for non-participants** (confirmed 2026-10-02): in the announcement and payout periods, users who did not register a participating UID (including non-members; GUEST, NO_ELIGIBLE_UID and NOT_REGISTERED all see the same screen) see "The Participation Period Has Ended" (KO "참여 기간이 끝났어요") and a disabled button "Participation Ended" (KO "참여 기간 종료"). No login prompt, join CTA or payout notice is shown. With ranking ON, "Check the final ranking." (KO "최종 순위를 확인해보세요.") and the final ranking are shown together. Non-members see this same screen, with no login prompt. The aggregation stage keeps the existing "Calculating" screen.
- **Leaderboard coverage** (ranking ON, confirmed 2026-10-02): in every stage (participation, aggregation, announcement, payout), show the ranks of **all winning places** (from 1st to the `winnerCount`th place, e.g., up to 30th if there are 30 winners) and My Rank.
- **Leaderboard rows and pagination** (ranking ON, confirmed 2026-10-02): if completers are fewer than the winning places, show only the existing ranks, with no empty-row UI (e.g., 30 winners and 18 completers = 18 rows). Split into pages of a fixed 10 rows (users cannot change the number of rows), navigated with page numbers + Prev/Next buttons, the same in every stage. If there is only 1 page, hide the page buttons. The My Rank row stays fixed below the list regardless of page. The former "fixed-height scroll, 2 columns on PC" approach is not used (1 column on both PC and mobile).
- **Aggregation-stage leaderboard** (ranking ON, confirmed 2026-10-02): show the ranking the server recalculates once right after the aggregation stage starts (00:00 UTC on the next day). It includes all completers during participation, including those who completed after the last day's Bingo Batch (including users who registered a participating UID on the last day and completed with the retroactive gauge), and there are no further updates afterwards. Places vacated during the aggregation stage (abuse exclusion, withdrawal, forfeiture) are also not applied in this stage; the recalculated result stays frozen and they are applied at announcement (confirmed 2026-10-12). The label is confirmed as "Calculating" (KO "집계 중"). If supporting copy is needed, use "Calculating. The final ranking will be confirmed when the results are announced." [EN draft] (KO "집계 중이에요. 결과 발표 때 최종 순위가 확정돼요") [review needed, subject to language-pack review]. The aggregation ranking differs from the final ranking only by places vacated this way; at announcement those places are left vacant and lower ranks are not moved up (confirmed). Completers who withdraw or are reset during the participation period drop out of the ranking at the next Bingo Batch recalculation (not a vacant place, confirmed 2026-10-12).
- **Streak display** (confirmed 2026-10-12, as in the mockup): during participation, show the label "Current Cashback Streak" (KO "현재 연속 페이백 기록") + large number "4 Days" (KO "4일", "1 Day" for 1, `streak.currentDays`) + small "Cashback Streak" (KO "연속 페이백") + a progress bar. The best (longest) streak is not shown (API-005 `streak.maxDays` is not used on screen). In the aggregation, announcement and payout periods, the label changes to "Final Cashback Streak" (KO "최종 연속 페이백 기록") with the same number display, and the progress bar is hidden. In EN, the first letter of Day/Days is capitalized. Final value = the current streak days at the end of the participation period (API-005 `streak.currentDays`, no updates from aggregation).
- **Final winners leaderboard** (ranking ON, screen label "Final Ranking" (KO "최종 순위")): from the announcement stage, the confirmed ranking is announced at once, and the same content stays visible through the payout period until the end (404). Columns are the same as in other stages: rank, trader (masked TUID), total cashback, Ranking Reward (EN Rank / Trader / Total Cashback (USDT) / Ranking Reward (USDT), confirmed 2026-10-12). Not updated after aggregation (final result fixed).
- Do not let the front end decide whether buttons are enabled; follow the API values (`actions.participationOpen`, `actions.checkOpen`, `actions.canRegister`, `actions.canReselect`).
- **Screen for abuse-excluded users** (confirmed 2026-10-02): the exclusion (EXCLUDED) is not disclosed to the user. There is no separate notice text or screen state such as "Not eligible for payout" (API-003 returns `PARTICIPATING`). The front end does not branch on `participantStatus` and draws according to the API values. During aggregation, the screen is the same as for other participants. In the announcement and payout periods (payout period for ranking OFF), if API-005 reward amounts come as `null`, show the amount as "-" and do not show the crediting notice. If API-005 `ranking` or API-007 `me` is `null`, hide my rank display and the leaderboard "My Rank" row. In the leaderboard list too, that place is not shown as a row, like any other vacant place (confirmed 2026-10-05). The My Rewards status badge (Pending / Calculating / Confirmed) stays the same as for other participants (changing the badge would reveal the exclusion, confirmed 2026-10-05).

[EN draft] (KO "이벤트 리워드는 지급되지 않아요") below the body; this sentence is not used in the payout period (if the UID was lost after payout, rewards may already have been paid). The screen below is **the same as for a first-time participant**: the board setup only (no gauge or My Rewards); during the participation period, depending on whether there is an eligible UID to select, [Select New UID] or "You have no eligible {exchange} UID.
