## 1. 사용자 유형

### 1-1. 기본 4분할

위키의 축은 `Guest / Member without linked UID / UID-linked member / Admin`입니다. **DEX PRD가 쓰는 S1~S4 같은 화면 상태 코드 체계는 기존에 없습니다.**

| DEX PRD | 기존 유형 | 대응 |
|---|---|---|
| **S2** (비회원 클레임) | Guest + Guest UID holder + Non-member cashback-withdrawal user | 거의 1:1 |
| **S3** (가입 후 미연동) | Member without linked UID | 1:1 |
| **S4** (연동 완료) | UID-linked member | 1:1 |
| (DEX에 없음) | Restricted member | 계정 제한 9종이 DEX 화면에 어떻게 보이는지 미정의 |
| (DEX에 없음) | Withdrawn member | 탈퇴 시 DEX 연동·비회원 클레임 처리 미정의 (~~녹화파일~~ — A-16으로 해당 없음) |

### 1-2. ⚠️ 권고 — S3를 둘로 쪼개야 합니다

기존 Project 3에 **`exchange_guest` / `exchange_member_unlinked` / `exchange_member_linked`** 3분할 선례가 있습니다. 거래소 상세 페이지용입니다.

DEX도 같은 구분이 필요합니다.

| 상태 | 의미 |
|---|---|
| S2 | 비회원 |
| S3 | 회원, 연동 0건 |
| **S3'** | **회원, 타 거래소 연동 있음, 이 DEX만 미연동** |
| S4 | 이 DEX 연동 완료 |

**S3'를 S3로 뭉치면 CEX 연동은 있고 DEX만 없는 사용자가 "아무것도 연동 안 한 사용자"로 잘못 분류됩니다.**

### 1-3. 권한 판정 순서 (기존 규칙, DEX에 승계 권장)

1. 사용자 유형 확정
2. 로그인 필요 여부
3. 연동 UID 필요 여부
4. UID 상태 확인 (linked / issue / transferred / failed / disconnected)
5. 일시적 계정 제한
6. 출처 인용 및 미정 항목 표시

### 1-4. 핵심 구분 규칙

| 구분 | 규칙 |
|---|---|
| Member vs UID-linked member | 페이백·쿠폰·랭킹 다수는 **로그인이 아니라 `연동 완료` UID**를 요구 |
| Issue UID vs 정상 UID | 이슈 UID는 페이백 내역, 랭킹 자격, 쿠폰 사용 선택, 초대 리워드 출금에서 **전부 제외** |
| 탈퇴 vs 미연동 | 탈퇴하면 연동 UID가 **guest UID로 전환**되고 잔액은 UID에 남음. 추후 다른 계정이 연동 가능 |
| 필수 push vs 마케팅 push | 필수 push는 출금 결과, UID 연동 결과, 소유권 결과에 발송 |

## 2. 백오피스 역할과 권한

### 2-1. 역할 4종 — 존재합니다

| 역할 | 정의 | 1차 기준 접근 불가 화면 |
|---|---|---|
| **Master** | CEO/CTO 예약 계정, 전체 권한 | 없음 |
| **Operator** | **현재 Master와 동일한 전역 접근.** 문서에 "transitional setup"으로 명시, 향후 분리 가능 | 없음 |
| **PM** | 핵심 서비스 기능 운영. **결제·내부 기밀 페이지 제한** | Event reward payment |
| **CS** | 최저 권한. 사용자 정보 조회·지원 메뉴 열람만. **콘텐츠 편집 불가** | 거래소 리스트·순서·관리, 이벤트 수정, 래퍼럴 계정 관리, event reward payment, 회원 차단·해제 |

**보안 규칙:** 최소 권한 원칙, 계정 공유 금지, 퇴사 즉시 삭제.

**런타임 확인 (2026-07-23):** 관리자 계정 생성 폼의 `등급` 선택지는 `CS`, `PM`, `Operator` 3개만 노출. **`Master` 미노출.** 비밀번호 필드가 `type="text"`로 렌더되는 P1 결함 존재.

### 2-2. ⚠️ 정식 "기능 × 역할" 매트릭스는 **기존에도 없습니다**

`02-feature-permission-matrix.md`는 이름과 달리 **역할 매트릭스가 아닙니다.** 실제 축은 이렇습니다.

```
Feature ID | Feature | Guest | Member without linked UID | UID-linked member | Admin | Key conditions | Source
```

`Admin` 열이 **단일 열**이고 값이 `C`, `Admin manages`, `History only`, `System/admin` 같은 **자유 서술**입니다.

**DEX PRD의 `ROL-1` 결번은 위키의 공백을 그대로 물려받은 것입니다.** 새로 만들어야 합니다.

### 2-3. 돈이 나가는 기능의 선례 — DEX 권한 설계의 유일한 근거

| 기능 | Master | Operator | PM | CS |
|---|---|---|---|---|
| **Event reward payment** | O | O | **X** | **X** |
| Manual push | O | O | X | X |
| Secret coupon 발급 | O | O | X | X |
| Event guide email | O | O | X | X |
| **관리자 계정 관리** | **O** | X | X | X |

**"돈이 나가는 기능은 PM과 CS 둘 다 제외"**가 유일한 확정 선례입니다. DEX 월 마감 승인, 수동 조정 권한을 여기에 맞추면 됩니다.

### 2-4. Master + Operator + PM 공통

Event page renewal, 회원 리스트 엑셀 내보내기, 거래소 배너, KOL 관리, 퀴즈 이벤트 등록·수정, UID 예외 처리, SEO, 거래소 API 지원 관리, 선정산 관리, Global League 백오피스, VIP 승인·수동 지정, Partner Exchange renewal

### 2-5. 조회는 CS 포함 (Master + Operator + PM + CS)

Google OTP 히스토리(**보존 2년**), 페이백 챌린지 히스토리, Bitcoin price guess 히스토리, 페이백 부스트 히스토리, 퀴즈 이벤트 히스토리, UID 예외 조회, 초대 리워드 출금 트리

### 2-6. ⚠️ 2인 승인은 **기존에 없습니다**

위키가 명시적으로 미확정으로 기록했습니다.

> 지급, 회수, 삭제, 발송, 계정 생성 같은 고위험 작업의 확인 dialog, **2인 승인**, audit log, rollback — 미확정

> 버튼이 보인다는 사실은 확인 절차, 이중 승인, 감사 로그, 실제 API 권한이 구현됐다는 증거가 아니다

**DEX에서 처음 도입한다면 후보:** 월 마감 승인, 수동 정정, Exchange Type 설정

### 2-7. 감사 로그 — 정식 체계 없음, 4가지 형태 혼재

| 유형 | 실제 구현 |
|---|---|
| **별도 "히스토리" 화면** | 수동 푸시, 엑셀, 수동 쿠폰 발송, 이벤트 안내 이메일, 구글 OTP(2년), VIP, 소유 확인 제한 내역, 제한내역, 탈퇴회원 리스트 |
| **사유 필드 의무** | 수동 event reward 지급·차감은 사유 필수. UID 예외 처리는 최대 500자 메모 |
| **"audit log 필요"만 선언** | 거래소 상세 댓글 관리자 행위. WOOX promotion 보존 정책은 미정 |
| **최종 수정자 기록** | `거래소 래퍼럴 관리`에 컬럼 존재 |

**권고:** DEX도 같은 패턴으로 **"DEX 정산 히스토리", "DEX 소유권 심사 히스토리", "DEX 콘텐츠 발행 히스토리"** 3개 화면 신설.

### 2-8. 권한 없을 때 UI — 표준 없음, 4가지 혼재

| 패턴 | 사례 |
|---|---|
| ① 페이지 차단 + 메시지 | PM이 결제 페이지 접근 → `You do not have permission.` |

**권고:** ②/③으로 통일. **④는 안티패턴이므로 DEX에 채택 금지.**

## 3. 상태 사전

**20개 도메인, 150개 상태값.** 포맷은 도메인별로 다릅니다. (3-8 표 17개 + UID 3-1 + 계정 제한 3-4 + 출금 3-6. `소유권 인증`은 3-5와 3-8에 중복 등장하므로 한 번만 셉니다.)

### 3-1. ⭐ UID 상태 — **우선순위가 명시된 유일한 도메인**

DEX 상태 칩 설계의 **유일한 선례**입니다.

| 상태 키 | 한국어 표시 | 의미 | **홈 우선순위** | 한도 소모 |
|---|---|---|---:|---|
| `ownership_check` | 소유 확인중이에요 | 소유권 확인 진행 중 | **1** | O |
| `manual_link_pending` | 연동 시도중이에요 | 수동 연동 대기 | **2** | O |
| `issue_uid` | 이슈 UID | 문제 UID | **3** | O |
| `linked` | 연동 완료 | **연동 성공 + 소유 확정** | **4** | O |
| `link_failed` | 연동에 실패했어요 | 연동 실패 | **5** | O |
| `ownership_failed` | 소유 확인에 실패했어요 | 소유 확인 실패 | **6** | O |
| `disconnected` | 연동 해제되었어요 | 해제 또는 소유권 이전 | **7** | O |

**⚠️ `linked` = `연동 완료`는 소유 확정까지 끝난 상태를 뜻합니다.** DEX의 `Active`가 소유 검증 전 상태를 포함하면 의미가 어긋나므로 **같은 라벨 재사용 금지.**

**표시 규칙:** UID 항목 11개 이상이면 `더보기` 클릭 전까지 10개만 노출.

### 3-2. ⭐ 전역 상태 우선순위 규칙 — **기존에도 없습니다**

DEX PRD의 공백은 기존 체계에도 똑같이 존재합니다. 국소 규칙 4개만 있습니다.

| # | 규칙 | 범위 |
|---|---|---|
| 1 | **UID 홈 우선순위 1~7** | 홈 UID 목록 |
| 2 | **IP 제한 우선** — IP 제한과 다른 서버 제한이 겹치면 IP 제한 토스트 | 이메일 인증 |
| 3 | **언어 결정 체인** — URL > local storage > country > browser > EN | 언어 |
| 4 | **포트폴리오 실패 카드** — 최우선/최신 실패 카드 1개만 표시 | My Portfolio |

**DEX의 "Aster 만료 임박 + 데이터 지연" 같은 중첩을 해결할 선례는 ①의 7단계 서열 하나뿐입니다.** 같은 형식(정수 priority)으로 확장할 것을 권합니다.

### 3-3. ⭐ 상태 칩 명칭·색상 체계 — **정의되어 있지 않습니다**

상태 사전에 **chip·badge·색상 토큰 언급이 0건**입니다.

발견된 칩 관련 기술은 이것뿐이고 **모두 색상 미정의**입니다.
- Benefits 페이지 `Ongoing` / `Completed` 탭 + count badge
- benefit 카드에서 **NEW badge 제거됨**
- 거래소 상세 댓글 **Verified badge**
- 이벤트 chip / chip filter
- WOOX **Travel Rule badge는 표시 전용**

**결론: DEX 상태 칩의 명칭·색상·우선순위는 상속할 수 없습니다. 신규 수립해야 하고, 그 결과가 CEX에도 역적용되는 최초의 마스터 목록이 됩니다.**

**단 승계해야 할 것 2가지**
1. 한국어 표시 문구 스타일 — **구어체 종결형** (`소유 확인중이에요`, `연동에 실패했어요`)
2. **다크모드 지원** (4.5차에서 웹 다크모드 확장)

## 5. 기존 CEX 연동 플로우 (DEX 대조 기준)

### 5-1. 연동 한도

```
노출여부(exposure)=Y && 연동가능(linkable)=Y 인 거래소 수 × 3
```

- **한도 수치를 사용자에게 공개하지 말 것** (온보딩 규칙)
- 모달 문구: `UID 연동은 최대 {거래소 개수 X 3}개까지 가능해요`
- **7종 상태 전부 한도 소모** — 연동완료, 연동시도, 연동실패, 연동해제, 소유확인, 소유확인실패, 이슈 UID
- **실패/해제 UID도 한도를 계속 점유.** 삭제로 해제하는 플로우는 "미확정"

**⚠️ DEX 한도(`3 × 활성 DEX 수`)와 UID 한도의 합산·독립 관계가 미정의입니다.**

### 5-1-1. 이 한도가 DEX에 주는 영향 (2026-10-23 추가)

| # | 내용 |
|---|---|
| 1 | **위 산식은 거래소 종류를 가리지 않습니다.** DEX 4곳을 거래소 레코드로 등록하면 **그것만으로 이 한도가 12 올라갑니다.** 별도 DEX 한도를 또 두면 같은 레코드를 두 번 셉니다 |
| 2 | **소모 규칙이 DEX와 정반대입니다.** 여기서는 실패·해제 UID가 칸을 계속 점유하고 셀프 해제도 불가(5-5)인데, DEX 명세는 **제거 시 칸을 반환**합니다 |
| 3 | **어드민 설정 위치는 이미 존재합니다.** `노출여부`·`연동가능` 이 거래소 리스트의 실제 플래그이므로, **거래소 레코드가 곧 한도 입력값**입니다. 거래소 1곳을 비노출로 바꾸면 전 회원 한도가 움직입니다 |
| 4 | **없는 것은 회원별 사용량 조회입니다.** CEX·DEX 양쪽 다 고객센터가 "한도에 걸렸나" 를 확인할 화면이 없습니다 |

> **확인 필요:** `연동가능(linkable)` 이 거래소 생성 폼의 `가입 가능여부` 와 같은 필드인지. 같다면 DEX용 이름 변경이 한도 산식에도 영향을 줍니다.

→ `05_연동_출금_플로우_국영문.md` 2-9-1 · 2-9-2, 결정요청서 `B-3-1`

### 5-2. 연동 단계

1. 진입 → 한도 게이트
2. UID 입력 (Project 3에서 eligibility 게이트 제거)
3. **CAPTCHA** (플로우에 1회)
4. 거래소 조회 — 레퍼럴 하위 여부, UID 존재. **백엔드 전용, 사용자 미노출**
5. 중복 판정 — 같은 계정이면 거부, 다른 계정이면 **소유권 주장으로 라우팅**

DEX 판단에 그대로 상속되는 공백입니다.
