## 1. 시스템 모델 (문서가 전제하는 것)

테더맥스는 트레이더가 이미 지불한 수수료의 일부를 돌려주는 페이백 플랫폼이다. 현재 3개 상품군을 운영한다.

| 상품 | 파트너 수 | 귀속 방식 | 연동 키 | 페이백 지급 주체 | 출금 경로 |
|---|---|---|---|---|---|
| CEX | 17 | 거래소 레퍼럴 가입 | 거래소 UID | **테더맥스** | 테더맥스, 최소 10 USDT |
| 브로커 | 2 | 브로커 레퍼럴 + 신원 검토 | 브로커 계정 | 테더맥스 | 테더맥스 |
| **DEX (신규)** | **4** | 테더맥스 레퍼럴 링크 | **지갑 주소 + DEX 계정 ID** | **DEX가 사용자 DEX 계정으로 직접** | **DEX 사이트, 테더맥스 최소액 없음** |

### 1.1 DEX가 기존 2개 상품과 근본적으로 다른 점

문서 1이 스스로 정리한 내용이며, 설계 전반의 출발점이다.

1. **개설할 계정이 없다.** 따라서 연동할 UID가 없다. 식별자는 사용자가 직접 만든 지갑 주소다.
2. **신원 확인이 없다.** 기존 퍼널의 자격 검증 단계가 사라진다.
3. **사용자가 담보를 직접 보유한다.** 아무도 동결할 수 없고 아무도 복구해 줄 수 없다. 잘못된 안내의 대가가 크다.
4. **보상이 항상 비율이 아니다.** Lighter Standard 계정은 수수료가 0%라서 돌려줄 것이 없다.

### 1.2 절대 규칙 (문서 전체가 반복 강조)

- 지갑 **연결이나 서명을 요구하지 않는다.** 사용자는 주소를 복사해서 붙여넣기만 한다.
- DEX 거래로 **이벤트 리워드와 초대 리워드가 발생하지 않는다.**
- 테더맥스는 DEX 트레이더의 **돈을 움직이지 않는다.** 지급·승인·출금 레코드를 만들 수 없다.
- 회원에게 보이는 **모든 금액은 USDT**다. USDC는 1:1 환산, Aster는 Aster가 지급 시점에 계산한 USDT 환산값(`usdtValue`)을 그대로 쓴다. 테더맥스가 자체 환산하지 않는다.
- 지갑 주소는 **공개 식별자**이므로 잘라서 표시하고, 분석 이벤트·URL·로그에는 절대 넣지 않는다.

### 1.3 DEX 4곳의 구조 차이 (설계 복잡도의 주원인)

| 항목 | Lighter | ApeX | EdgeX | Aster |
|---|---|---|---|---|
| 정산 통화 | USDC | USDT | USDC | 수수료 자산 (가변) |
| 레코드 키 | 지갑 주소 단독 | 지갑 + AccountID | ethAddress + accountId | venue + 주소 |
| 정산 주기 | **주 1회 (월요일)** | 시간당 | 일 1회 (00:00 UTC) | ⚠️ **미확정** (PM이 `1h` 언급, 공식 회신 대기) |
| 웹훅 | **없음** (폴링) | 있음 (사양 미정) | 일부 | 요청 단계 |
| 상태 체계 | Accruing / Paid / Withheld | Pending / Paid | Pending / Paid | Pending / Paid |
| 출금 가능 잔액 | 제공 안 함 | `available_balance` | **제공 안 함** | ⚠️ **요청 단계** (R6 미회신) |
| 고유 제약 | Standard 계정 페이백 0, 2026-07-28 이후 바인딩만 | AccountID 미반환 | 팀 전체 귀속(2~3단계) | **365일 후 바인딩 만료** |
| 서브계정 | 지갑이 전부 포함 | 미확인 | 계정 여러 개 | 주소마다 별개 |

이 표가 이번 설계의 난이도를 결정한다. 네 곳이 **정산 주기, 키, 통화, 상태, 제공 데이터가 모두 다르다.** 화면 하나를 만들 때마다 DEX별 분기가 생긴다.

### C-1. DEX 상세 페이지가 돈의 흐름을 반대로 설명한다

**근거:** VD-5 (계산기), VD-6 (설명 서랍), VD-7 (단계별 가이드 기본 문구)

VD-5 흐름도:
```
You → Trading fee → {venue} → Partner settlement → TetherMax → "Cashback returned to you"
```
설명 카드: "**TetherMax gives cashback** — TetherMax returns {cashback} to you, so your effective fee becomes {effective fee}."
VD-6: "거래소가 테더맥스에 정산금을 지급하고 테더맥스가 대부분을 돌려준다."

같은 페이지 FAQ(VD-8)는 정반대다: "Lighter pays your cashback in USDC **into your own Lighter account**, and you withdraw it on Lighter."
랜딩(DX-3, DX-12)도 "Paid by the DEX, into your account"다.

**영향:** 사용자가 테더맥스 잔액에 쌓인다고 믿고 출금하러 갔다가 찾지 못한다. CS 문의와 신뢰 손상으로 직결된다. 이것은 카피 오류가 아니라 **CEX 템플릿을 그대로 복사한 결과**이므로 계산기 구조 자체를 다시 설계해야 한다.

### C-2. "Deposit {currency} into your TetherMax wallet"

**근거:** VD-7 단계별 가이드 기본 라벨 (2단계)

테더맥스에는 지갑이 없다. 사용자가 이 지시를 그대로 따를 방법이 없다.

### C-3. 랜딩 첫 화면이 "Connect a wallet"이라고 한다

**근거:** DX-1 리드 문구 "No KYC checks. Connect a wallet, and start trading!"

문서 전체가 "지갑 연결을 절대 요구하지 않는다"를 수십 번 강조하는데, 사용자가 처음 보는 문장이 그것을 뒤집는다. 엣지케이스 문서 자체도 미해결 항목 #16으로 올려놨다.

### C-4. "Available"이라는 단어의 의미가 DEX마다 다르다

**근거:** LK-7, LK-10, CH-11, WD-2, 엣지케이스 미해결 #4·#5

DEX 카드는 "Available Cashback"이라고 표시하지만 실제 값은 **누적 지급액**이다. 사용자가 DEX에서 출금해도 이 숫자는 줄지 않는다 (의도된 동작 — "earned"는 감소하지 않음).

| DEX | "Available Cashback"의 실제 의미 |
|---|---|
| Lighter | 주간 CSV 기준 Paid 누적 |
| ApeX | Paid 누적 (별도로 "Available on ApeX"가 ApeX 실제 잔액) |
| EdgeX | `totalPaidAmount` (누적 지급액). 출금 가능 잔액 자체를 제공하지 않음 |
| Aster | 정의 없음 |

**결과:** 홈의 "DEX Cashback Balance"는 DEX마다 다른 의미의 숫자를 합산한 값이 된다. ApeX 카드에는 "Available"이 두 개 있어 어느 쪽이 실제로 뺄 수 있는 돈인지 알 수 없다.

### C-5. SPE 소수점 제한이 예시 값을 입력할 수 없게 만든다

**근거:** SPE-6 (소수 3자리 제한) vs SPE-7 (예시 0.05% = 0.0005)

Spending Estimate의 요율 입력이 소수 3자리까지만 허용되는데, 같은 문서의 예시가 소수 4자리다. Lighter 요율 테이블은 4자리를 허용한다. 구현하면 바로 막힌다.

## 5. 데이터 신뢰성 문제

### R-1. Lighter 연동이 주소 일부만 보고 추측한다

> **2026-10-20 — 일부 해소됐습니다 (A-07).** 10월 19일 senya 회신으로 **즉시 확인이 가능**해졌습니다. 마스킹 1건 일치 시 즉시 연동하고 `used_at`을 바인딩 시각으로 씁니다. **"다음 월요일 CSV까지 Processing 대기"는 폐기됐습니다.**
>
> **다만 마스킹 충돌 위험은 그대로입니다.** 식별 문자가 6개뿐이라 2건 이상 겹칠 수 있고, 그때만 `Processing`이 발생합니다. 이 부분은 아직 파트너와 논의되지 않았습니다 (B-3-2).
>
> ⚠️ **추가로 발견된 것:** 마스킹 대조를 **EIP-55 체크섬 주소 기준**으로 계산해야 합니다. 소문자로 계산하면 Lighter 연동이 전부 실패합니다 (B-3-2a).

**근거:** LW-13 (Proposed), LK-9, CSB-19~23

Lighter 실시간 API(`userReferrals`)는 주소를 **마스킹**해서 준다: `0x` + 앞 2자 + 뒤 4자 = 식별 가능한 문자 6개. 전체 주소는 **매주 월요일 CSV**로만 온다.

제안된 처리:
1. 이미 받은 CSV에 있으면 → 확정
2. 없지만 마스킹 패턴이 일치하면 → **Processing** 상태로 보류, 다음 CSV까지 대기
3. 둘 다 아니면 → 레퍼럴 아님으로 거부

**위험:**
- 6자 일치는 다른 지갑과 충돌할 수 있다. 충돌하면 엉뚱한 사용자 화면에 남의 적립 추정치가 붙는다.
- 후보가 여러 개면 Ambiguous로 두는데, 해소 기준이 없다.
- CSV에 끝까지 안 나타날 때의 처리가 Proposed다 (14일 후 삭제 안). **수수료를 낸 지갑만 CSV에 올라온다면, 정상 연동한 사용자가 2주간 거래하지 않았다는 이유로 연동이 삭제된다.**
- 적격 기준이 2026-07-28 이후 바인딩이라 그 전에는 실데이터 테스트가 불가능하다.

### R-2. 비회원 클레임에 소유권 확인이 없다

**근거:** LW-17~25, EC-GST-*

캡차만 통과하면 남의 지갑 주소로 적립액과 이력을 조회할 수 있다. 회원 간 지갑 중복은 화면 녹화 분쟁 절차가 있지만 비회원 경로에는 없다.

파트너 문서(Lighter R18)는 "남의 지갑을 붙여넣어도 얻을 게 없다 — 페이백은 바인딩된 지갑으로만 지급된다"고 한다. 이는 **지급**만 다루고 **정보 노출**은 다루지 않는다.

연쇄 문제: 비회원 기록이 남은 지갑을 다른 사람이 회원 계정에 연동하면 그 기록이 그 사람 계정으로 이관된다(LW-25). 소유권 검증 없이 이관된다.

### R-3. 데이터 지연 임계치가 전부 제안 단계다

| DEX | 제안된 임계치 | 상태 |

| ApeX | 2시간 (2회 정산 주기) | Proposed |

추가로 백오피스는 "24시간 무데이터면 Degraded"라는 별도 기준을 쓴다(CSB-14). DEX별 기준과 충돌한다.

### R-4. 정정 레코드가 "earned는 감소하지 않는다"와 충돌한다

**근거:** EC-DAT-5 (Proposed), WD-8, CSB-8

파트너가 정정하면 음수 Adjustment 레코드가 들어와 earned 총액이 줄어들 수 있다. 그런데 WD-8 화면 문구는 "Exchange Cashback is what you have earned, so it doesn't go down when you withdraw"다. 출금으로는 줄지 않지만 정정으로는 줄 수 있다는 점이 설명되지 않는다.

## 6. 백오피스 구조

### 6.1 설계 원칙

**"복제하지 말고 분류한다."** Exchange 레코드에 필수 필드 **Exchange Type**(CEX / DEX / Broker)을 추가하고, 하위 모듈은 DEX 전용 사본 없이 이 필드만 읽는다.

- Exchange Type은 다른 필드보다 먼저 입력해야 하고, 값을 고르면 나머지 필드가 나타난다.
- 저장 후 None으로 되돌릴 수 없다.
- 기존 거래소는 활성·비활성 모두 CEX로 일괄 채운다.
- 파트너 이름으로 유형을 추론하지 않는다.
- **레코드와 콘텐츠를 분리한다.** Exchange 메뉴는 파트너 레코드(파트너당 1행), 신규 Cashback Products 메뉴는 페이지별 콘텐츠. 레코드를 등록해도 DEX 랜딩에 자동 노출되지 않는다.

### 6.4 브로커 에디터가 DEX PRD에 들어온 이유

백오피스 엣지케이스 문서 자체가 미해결 항목 #14로 "Part 4가 PRD 트리 밖에 있다"고 인정한다. DEX 온보딩과 무관한 브로커 필드 30여 개가 일정과 QA 범위를 키운다. **별도 PRD로 분리를 권한다.**

## 9. 상태 표시 체계 부재

문서 곳곳에 상태 칩이 흩어져 있고 **마스터 목록과 우선순위가 없다.**

발견된 상태:
- Active
- Processing (연동 확인 중)
- Unavailable (페이백 0)
- Standard account, no cashback (Lighter)
- Expires in {n} days (Aster)
- Referral expired (Aster)
- Inactive (DEX 비활성화)
- Ownership verification in progress
- This wallet has been unlinked (소유권 이전됨)
- Ownership verification was unsuccessful
- Data delayed / Last updated {time}

**문제:**
- 두 개 이상이 동시에 해당할 때 무엇을 먼저 보여줄지 없다. 예: Aster 만료 임박 + 데이터 지연, Lighter Standard + Processing
- 행(Linked Accounts)과 카드(선택된 계정)의 매핑이 다르다
- EdgeX·ApeX 고유 상태(AccountID 미반환, 제한 IP 거래)는 칩이 정의되지 않았다
- "Unavailable" 칩은 정상 연동한 신규 사용자에게 오해를 준다

## 13. 정리

### 잘 되어 있는 부분

- DEX 4곳의 구조 차이를 정확히 파악하고 각각의 예외를 명시했다
- 지갑 주소 검증 규칙(EVM, EIP-55, trim, 소문자 저장, 체크섬)이 매우 상세하다
- 엣지케이스를 약 150건 정리하고 "이미 정의됨"과 "제안 단계"로 구분했다
- 백오피스 설계 원칙("복제하지 말고 분류한다")이 명확하고 확장성을 고려했다
- 파트너 API 요구사항을 R1~R13으로 체계화하고 각 DEX 회신 상태를 추적한다
- 운영자 알림 체계가 구체적이다
- 어트리뷰션을 단일 서비스로 모은 설계가 좋다

### 보충이 필요한 부분

1. **모델 정합성 교정** — CEX 템플릿 복사로 생긴 오류 (3장, 4장)
2. **"Available / Total Claimed / DEX Cashback Balance" 의미 재정의** — DEX마다 다른 데이터를 하나의 단어로 부르는 문제
3. **상태 표시 체계 수립** — 마스터 목록과 우선순위
4. **지갑 한도 운영 설계** — 백오피스 전체가 공백
5. **DEX 비활성화 영향 정의** — 연쇄 효과 전부
6. **권한 모델 수립** — 결번 상태
7. **알림 체계 설계** — 회원 알림 채널·문구
8. **Aster 연동 섹션 신설** + 5번째 DEX 일반화
9. **비회원 클레임 소유권 설계**
10. **Proposed 항목 확정** — 약 150건 중 절반 이상

### 파트너 확인에 걸려 있는 항목

우리가 결정할 수 없고 파트너 회신을 기다려야 하는 것들이다. 자세한 내용은 `02_데이터_확보_매트릭스.md` 참조.

- **Aster:** 초안만 발송, 회신 없음. 레퍼럴 조회 API 대부분 요청 단계. 365일 바인딩 갱신 방식 미정
- **ApeX:** AccountID 미반환, 원장 필드 일부 누락, 웹훅 사양·인증 방식·base URL 미정
- **EdgeX:** 팀 전체 귀속 범위, partnerRate 값, 하위 추천 오버라이드 비활성화, 신규 귀속·Paid 전환 웹훅
- **Lighter:** 페이백 요율(추정치 계산에 필요), CSV 전달 방식·시각, $1 미달 주차 처리
