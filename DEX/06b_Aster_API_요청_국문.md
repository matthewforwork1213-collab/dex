## 요약

요구사항 v1.3을 보냈으나 아직 공식 회신을 받지 못했습니다. **수신 확인과 일정 합의**를 요청합니다.

현재 Aster가 제공하는 것으로 파악한 내용입니다.
- 레퍼럴 사용자의 **수수료** 조회는 승인된 사용자에 한해 Builder API로 가능
- **리베이트** 조회는 **계정 소유자만** 가능
- 테더맥스가 우리 코드로 추천된 사용자의 리베이트를 읽을 수 있는 방법이 문서상 없음

마지막 항목이 출시를 막습니다.

### 일찍 논의가 필요한 2가지

**① 365일 바인딩.** 갱신 경로가 없으면 **1년 후 테더맥스가 추천한 모든 트레이더의 페이백이 중단됩니다.** 별도로, 만료 전 트레이더에게 경고하려면 **잔여 일수를 아무 때나 읽을 수 있어야** 합니다 — 바인딩 시점뿐 아니라 매 조회마다 `bindExpireTime`이 필요합니다. 9번 항목입니다.

**② 월 20,000 USDT 상한.** 확인했습니다. 월중에 상한에 도달하면 리베이트가 어떻게 되는지, 소진율을 조회할 수 있는지 알고 싶습니다. 아래 **F5**입니다.

## 출시 차단 항목 (P0)

### 1. 추천 사용자에 대한 파트너 접근

테더맥스 추천으로 가입한 계정에 대한 **읽기 전용 접근**과 QA용 **테스트넷**이 필요합니다.

문서상 두 가지 방법이 가능해 보입니다.

**(a)** Builder 승인 사용자 목록(`GET /fapi/v3/builder/approvedUser`)처럼 레퍼럴 바인딩 사용자를 반환

**(b)** 테더맥스가 **builder fee 0으로 builder 등록**하고 사용자가 가입 시 승인

**어느 쪽을 선호하시는지 알려주십시오.** 어느 경우든 우리 접근은 읽기 전용이어야 하며 거래·이체·출금 권한이 없어야 합니다.

### 2. 지갑 주소 조회로 귀속 상태 반환

지갑 주소를 받아 아래를 반환하는 엔드포인트입니다.

| 필드 | 용도 |
|---|---|
| `isTethermaxReferral` | 우리 추천으로 가입했는지 |
| `bindTime` | 바인딩 생성 시각 |
| `bindExpireTime` | 만료 시각 |
| `rebateRate` | 이 주소에 적용되는 요율 |
| 내부 사용자 ID (있다면) | 대조용으로만 보관 |

`GET /fapi/v3/referral/userStatus?address=`를 제안했습니다. **경로는 제안이고 필드가 필요한 내용입니다.**

### 3. 주소·정산일별 리베이트 레코드

주소·자산·정산일별 1건으로, 영구 ID(예: income `tranId`), 주소, 소득 유형, 자산, 수수료 기준, 소득, USDT 환산값, 정산일, 상태(`PENDING`/`PAID`), 시각을 포함합니다.

### 4. 모든 레코드·명세서·웹훅에 `usdtValue`

**파트너 접근 다음으로 가장 중요한 항목입니다.**

Aster는 수수료 자산으로 리베이트를 지급합니다 (USDT, USD1, USDC, USDC.e, ETH, BTC, BNB, USDF, asBNB 등). **테더맥스는 자산 간 환산을 하지 않습니다.** 표시·합계·명세서·대조·웹훅 전부에 **Aster가 지급 시점에 계산한 USDT 환산값만** 사용하고, 원 자산과 금액은 감사용으로만 보관합니다.

따라서 **`usdtValue`와 `payoutPrice`, `priceTime`**이 아래 전부에 필요합니다.
- 모든 리베이트 레코드
- 모든 월 명세서 행
- 모든 웹훅 payload

**`usdtValue`가 없는 레코드는 우리 수집 로직이 거부합니다.** 적용할 자체 가격이 없기 때문에 표시할 수 없습니다.

### 5. 주소별 리베이트 잔액 (USDT 환산)

Aster에 아직 남아 있는 금액을 트레이더에게 보여주기 위해 필요합니다.

### 6. 레퍼럴 코드 검증

테더맥스 레퍼럴 코드나 링크가 Aster에서 승인된 것인지 검증하고 `isValid`와 리베이트 등급을 반환하는 엔드포인트입니다. 링크 게시 전에 호출합니다.

## 출시 후 30일 내 필요 (P1)

### 7. 월간 리베이트·커미션 명세서

USDT 환산 기준이며, 합계가 해당 월 레코드의 `usdtValue` 합과 일치해야 합니다.

### 8. 파트너 웹훅

3가지 이벤트이며, 각각 주소·이벤트 유형·이전과 신규 상태·원 자산과 금액·`usdtValue`·`payoutPrice`·`priceTime`·`tranId`·시각·고유 `eventId`를 포함합니다.

| 이벤트 | 시점 |
|---|---|
| **신규 바인딩** | 트레이더가 우리 추천에 바인딩. 갱신·재바인딩 포함 |
| **바인딩 만료 임박** | `bindExpireTime` 30일 전 |
| **리베이트 지급** | 리베이트가 Paid로 전환 |

푸시에 서명을 넣고, HTTP 200 반환까지 24시간 백오프 재시도를 요청합니다.

### 9. 365일 바인딩 — 갱신과 잔여 일수 조회

**이 항목이 상업적으로 가장 큰 영향을 가지며, 두 부분으로 나뉩니다.**

#### 9a. 갱신 (P1)

추천 주소를 기본 365일간 테더맥스에 바인딩합니다(`bindExpireTime`). 갱신 경로가 없으면 **1년 후 우리가 추천한 모든 트레이더의 페이백이 중단되고 복구할 방법이 없습니다.**

두 가지 중 하나면 해결됩니다.

**(a)** 트레이더가 거래를 계속하는 동안 테더맥스 바인딩을 유지

**(b)** 만료 후 트레이더가 테더맥스 레퍼럴 코드를 재바인딩

어느 경우든 새 바인딩 시각과 만료 시각을 반환하고 바인딩 웹훅을 보내 주시면, 계정을 다시 활성 상태로 되돌리겠습니다.

#### 9b. 매 조회마다 `bindTime`·`bindExpireTime` 반환 — **P0**

트레이더에게 만료까지 남은 일수를 보여줘야 합니다. 그러려면 만료 시각을 **바인딩 생성 시점뿐 아니라 아무 때나 읽을 수 있어야** 합니다.

**지갑 주소 귀속 조회를 호출할 때마다 `bindTime`과 `bindExpireTime`이 반환되는지 확인 부탁드립니다.**

PM 회신에서 referred-user 상세 엔드포인트가 "지갑 주소, 계정 ID, **가입일**, 적격 플래그, 현재 할인·커미션 자격 상태"를 반환한다고 하셨습니다. **가입일은 바인딩 만료일과 다릅니다.** 그래서 이 부분만 따로 확인하고자 합니다.

**왜 중요한지 구체적으로 말씀드리면**

테더맥스에서는 지갑 주소가 테더맥스 계정에 연결되고, 그 연결이 시간에 따라 바뀔 수 있습니다. 트레이더가 지갑을 제거했다 다시 추가하거나, 소유권 분쟁 후 다른 테더맥스 계정이 그 지갑을 가져갈 수 있습니다. **바인딩 자체는 Aster 쪽에서 지갑과 Aster 사이에 존재하므로 이런 변화와 무관합니다.**

그래서 Aster 답변에 따라 두 가지 설계가 갈립니다.

| 매 조회마다 반환하는 경우 | 바인딩 시점에만 전달하는 경우 |
|---|---|
| 필요할 때 `bindExpireTime`을 읽어 항상 정확한 잔여 일수 표시 | 수신한 시점의 값만 보유 |
| 지갑이 계정 간 이동해도 문제없음. 다시 조회하면 됨 | 지갑이 다른 계정으로 옮겨가면 만료 정보를 잃고, **우리가 처음 기록한 날짜**부터 세야 하는데 그것은 실제 바인딩일이 아님 |
| 테더맥스 연동 전에 바인딩한 지갑도 정확 | 그런 지갑은 **처음부터 틀림** |

두 번째 경우 트레이더에게 눈에 띄게 잘못된 카운트다운이 표시됩니다. 피하고 싶습니다.

**선호 순서**

1. 지갑 주소 귀속 조회 **매번** `bindTime`과 `bindExpireTime` 반환 — 완전 해결
2. 안 되면, 추천 지갑 전체의 만료일을 주기적으로 갱신할 수 있는 벌크 엔드포인트
3. 안 되면, 바인딩이 **항상 반환되는 `bindTime`으로부터 정확히 365일**임을 확인 → 우리가 계산

## 질문

1. **지갑 주소 귀속 조회가 호출할 때마다 `bindTime`과 `bindExpireTime`을 반환합니까?** (9b — 가장 중요)
2. 레퍼럴 바인딩 사용자를 Builder 승인 목록처럼 반환할 수 있습니까, 아니면 테더맥스가 builder fee 0으로 등록하고 사용자가 가입 시 승인해야 합니까?
3. `tranId`는 한 사용자의 모든 소득 유형에서 고유합니까, 아니면 한 유형 안에서만 고유합니까?
4. **리베이트가 취소될 수 있습니까? 취소되면 어떻게 표시됩니까?** 원본을 참조하는 새 레코드를 기대하며, 원본 수정은 아닐 것으로 봅니다
5. **USDT 환산에 어떤 가격(mark / index / spot)을 쓰고, 지급의 어느 시점 가격입니까?** 지급 후 환산값이 고정되고 재계산되지 않음을 확인해 주실 수 있습니까?
6. 갱신(9a)에 대해 — 거래를 계속하는 동안 바인딩을 유지하는 쪽입니까, 만료 후 재바인딩하는 쪽입니까?
7. Aster가 반환할 수 있는 내부 사용자 ID나 계정 ID가 있습니까?

### 이전 논의에 대한 후속 질문

PM 회신에서 나온 여섯 가지입니다. 위 1~11번 항목과 혼동되지 않도록 **F1~F6**으로 번호를 분리했습니다. 네 건은 답변이 필요하고, **F4·F6은 우리 쪽 이해를 확인만 받는 것**입니다.

**F1. 정산 주기 — 1시간입니까, 1일입니까?**

회신에 커미션·페이백 원장이 *"time period is 1h"*라고 되어 있습니다. 우리 요구사항 문서는 일 단위 정산일을 전제로, 레코드가 다음 날 09:00 UTC에 공개된다고 가정했습니다.

표시 방식이 달라지므로 어느 쪽이 맞는지 확인 부탁드립니다.

| 1시간인 경우 | 1일인 경우 |
|---|---|
| 시간당 기간을 UTC 영업일로 묶어 표시 | 일별 레코드를 그대로 표시 |
| 폴링 주기 단축 | 공개 후 1일 1회 폴링 |
| 데이터 지연 임계치가 수 시간 | 임계치가 정산 다음 날 |

**F2. Pending 금액**

회신에 *"pending amount is not easy to provide"*라고 되어 있습니다. 이해합니다.

정말 제공이 어렵다면 **Paid 금액만 트레이더에게 표시**하고 나머지는 아직 보고되지 않은 것으로 처리하겠습니다. 다만 빈 필드로 두지 않고 그에 맞춰 설계하려면 확인이 필요합니다. 읽는 시점의 레코드 `state`만으로 충분하며, 누적 pending 잔액은 필요 없습니다.

**F3. 지급처**

회신에 *"all paid on Aster chain perp/spot account"*라고 되어 있습니다. 반영했습니다 — 우리 화면은 페이백이 이미 Aster 계정에 있다고 안내하고 출금을 위해 Aster로 연결합니다. 다른 곳으로 받을 수 있다면 정정해 주십시오.

**F4. "지갑-계정 조회" 항목**

회신에 불명확하다고 하셨는데 우리 표현이 부족했습니다. 의도는 간단합니다 — **트레이더가 테더맥스에 Aster 지갑 주소를 붙여넣었을 때, 그것이 우리 추천에 속하는지 확인하고 해당 계정의 식별자를 받는 것**입니다. Aster에는 별도 계정 ID가 없고 주소가 곧 계정이므로 위 2번이 이를 포함합니다. 이 항목은 삭제해도 됩니다.

**F5. 월 지급 상한**

프로그램 전체 기준 **월 20,000 USDT** 상한, 거래량에 따라 월말 전 재조정, 7일 리뷰 기간으로 확인했습니다.

올바르게 처리하기 위해 두 가지를 여쭙니다.
- **월중에 상한에 도달하면 이후 리베이트는 어떻게 됩니까?** 중단됩니까, 다음 달로 이월됩니까, 비례 삭감됩니까?
- **상한 소진율을 조회할 수 있습니까?** 필드나 엔드포인트가 있으면 읽어서 모니터링하고, 상한에 닿기 전에 협의 드리고자 합니다

**F6. 레퍼럴 링크 생성**

계정 잔액이 0보다 커야 레퍼럴 링크가 생성된다는 점을 확인했습니다. 우리 쪽에서는 해결됐습니다. 향후 파트너를 위해 문서화되면 좋겠다는 의미로만 언급합니다.

## 관할 지역 — P2

테더맥스에서 귀사 프로그램을 **어느 지역에** 노출할지에 영향을 주는 질문 2건입니다. 연동을 막는 항목은 아닙니다.

| # | 질문 | 질문 이유 |
|---|---|---|
| 1 | 귀사가 **사용자 소개를 받지 않아야 하는 관할**이 있습니까? | 사용자 국가에 따라 파트너 노출을 제어하고 있습니다. 추측하지 않고 귀사 기준을 그대로 적용하고자 합니다. |
| 2 | 서비스를 제공하지 않는 국가 목록을 공유해 주실 수 있습니까? | 동일한 목적입니다. 위 필터의 초기값으로 사용합니다. |

각 항목에 짧게만 답해 주셔도 충분합니다.

## 현재 우리가 처리하는 바인딩 만료 동작

우리 동작을 투명하게 공유합니다.

| 단계 | 테더맥스 처리 |
|---|---|
| **만료 30일 전** | 만료 임박 웹훅 수신 시 트레이더의 Aster 계정에 "만료일 {date}"를 표시하고 1회 알림. 갱신이 가능한 경우에만 갱신 절차 안내 |
| **만료 시점** | 계정을 "Referral expired"로 표시하고 신규 리베이트 레코드를 기대하지 않음 |
| **만료 후** | 주소는 연동 상태를 유지해 이력이 남습니다. 만료 전 적립분은 계속 표시되고 Aster에서 출금 가능합니다. **`bindExpireTime` 이후 날짜의 레코드는 트레이더에게 표시하지 않고 검토 보류 후 Aster에 보고합니다** |
| **갱신 시** | 새 바인딩 시각부터 활성으로 되돌립니다. 만료와 갱신 사이 기간의 리베이트는 테더맥스에 귀속하지 않습니다 |

## 프로그램 동작 이해

| # | 주체 | 단계 |
|---|---|---|
| 1 | 트레이더 → Aster | 테더맥스 레퍼럴 링크로 가입. Aster가 주소를 기본 365일간 테더맥스 추천 하에 바인딩 |
| 2 | 트레이더 → 테더맥스 | Aster 지갑 주소 붙여넣기 |
| 3 | 테더맥스 → Aster | 주소 조회 |
| 4 | Aster → 테더맥스 | 귀속 확인, 바인딩 시각과 만료 시각 반환 |
| 5 | 트레이더 → Aster | 선택한 마진 자산으로 거래. Aster가 수수료와 리베이트 산정 |
| 6 | Aster → 테더맥스 | 주소·일별 리베이트 레코드 제공, 각각 지급 시점 USDT 환산값 포함 |
| 7 | Aster → 트레이더 | 다음 날 수수료 자산으로 트레이더 Aster 계정에 지급 |
| 8 | Aster → 테더맥스 | 지급된 리베이트를 `tranId`와 USDT 환산값으로 푸시 |
| 9 | 트레이더 → 테더맥스 | 페이백 확인 후 "Withdraw on Aster" 선택 |
| 10 | 테더맥스 → 트레이더 | Aster를 새 탭으로 염 |

**테더맥스는 트레이더의 자금을 보유하거나 이동하지 않습니다.**

Aster 소득 내역에서 리베이트는 `REFERRAL_KICKBACK` 또는 `COMMISSION_REBATE`로 나타나는 것으로 이해했습니다.

## 식별자

Aster에는 **별도 계정 ID가 없습니다.** 지갑 주소가 계정이며 각 서브계정이 자체 주소를 가집니다. 따라서 **venue + 주소**로 키잉하고 각 서브계정 주소를 별개 연동 계정으로 취급합니다. Aster 내부 `userId`는 반환되는 경우에만 저장합니다.

메인 지갑 주소는 현재 EVM입니다. 같은 프로그램에서 Solana 주소를 지원한다면 알려주십시오 — 별도 검증 규칙을 먼저 정의해야 받을 수 있습니다.

## 수기 CSV 대체 경로 (API 미개통 시)

09:00 UTC 이후 접근 통제 공유 폴더로 일 1회 전달.

```
tranId, address, settlementDay, incomeType, asset, feeBasis,
income, payoutPrice, priceTime, usdtValue, state, time
```

`time`은 미지급 시 비어도 됩니다. **USDT 환산값이 없는 행은 거부합니다.**

## 우리 측 데이터 처리 규칙

| 규칙 | 내용 |
|---|---|
| 레코드 키 | venue + 주소. 각 서브계정 주소는 별개 계정 |
| USDT 환산 | `usdtValue`만 사용. 원 자산·금액은 감사용. **`usdtValue` 없는 레코드는 거부** |
| 불변성 | 수정하지 않음. 정정은 원본 참조 새 레코드 |
| 확정 | Aster가 09:00 UTC에 공개한 후 48시간 |
| 귀속 기간 | 거래 시각이 `bindTime`과 `bindExpireTime` 사이일 때만 귀속. **기간 밖 레코드는 검토 보류** 후 보고 |
| 지갑 주소 | 소문자 16진수, 대소문자 구분 없이 비교. 파트너가 보낸 주소도 동일 규칙 검증 |
| 개인정보 | 요청하지 않음 |
| 조회 기간 | 최대 180일 |

**대조:** 연동된 지갑 주소로 매칭합니다. **미매칭 레코드는 보류 후 주간 보고**합니다. 월말에 `usdtValue` 합계가 월 명세서와 일치해야 하며, 원 자산 금액은 감사용으로 보관하되 별도 대조하지 않습니다. 양측 모두 명세서 후 30일 내 `tranId`를 인용해 이견 제기 가능합니다.

## 보안

- **읽기 전용 에이전트.** 거래·이체·출금 불가
- 보안 키 저장소 보관, IP 허용 목록
