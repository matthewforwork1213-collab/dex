## 3. 핵심 데이터 공백 8가지

우리 설계에 직접 영향을 주는 순서대로 정리했다.

### 공백 1. 누적 출금액(Total Claimed)을 제공하는 DEX가 없다

**영향 화면:** DEX 선택 카드(LK-7), 비회원 My Cashback(GW-2), Partner Hub 모달(PH-4)

네 곳 모두 "사용자가 DEX에서 얼마를 출금했는지"를 제공하지 않는다. 구조적으로 제공할 이유도 없다 — 출금은 DEX 내부에서 사용자가 직접 하는 일이고, 테더맥스는 당사자가 아니다.

그런데 화면 설계는 Total Claimed를 표시한다. EdgeX만 "Paid to your EdgeX account / On the way"로 대체했다.

**선택지:** (a) 모든 DEX에서 제거 (b) ApeX만 `available_balance`로 역산 (c) 파트너에게 추가 요청
**권고:** (a). 엣지케이스 문서 미해결 #6도 "파트너가 보고하지 않으면 숨김"을 권고한다.

### 공백 2. EdgeX는 출금 가능 잔액을 제공하지 않는다 (명시적 거부)

**근거:** EdgeX D5 — "지급 후에는 마진에 섞여 구분할 수 없고, 출금 가능 금액과 자산 원장은 계정 소유자의 것이므로 파트너에게 노출하지 않는다"

대체 제공: `accruingAmount`(오늘 적립, 미정산) / `pendingAmount`(정산, 미지급) / `totalPaidAmount`(누적 지급)

**결과:** EdgeX 카드는 "Paid to your EdgeX account"(누적) + "On the way"(진행 중) 구조가 된다. 다른 DEX와 의미가 다른 숫자가 같은 합계(DEX Cashback Balance)에 들어간다. → 공백 3과 직결

### 공백 3. "DEX Cashback Balance"가 서로 다른 의미의 합산이 된다

| DEX | 합산되는 값의 실제 의미 |
|---|---|
| Lighter | 주간 CSV 기준 누적 Paid |
| ApeX | 누적 Paid (ApeX 실제 잔액은 별도 항목) |
| EdgeX | `totalPaidAmount` — 누적 지급액 |
| Aster | 정의 없음 (usdtValue 합계로 추정) |

사용자는 이 숫자를 "지금 뺄 수 있는 돈"으로 읽는다. 실제로는 "지금까지 받은 돈"이다. 이미 다 출금했어도 숫자는 그대로다.

**권고:** 명칭을 "Paid to your DEX accounts" 계열로 바꾸고 캡션에 "누적 적립액이며 출금해도 줄지 않습니다"를 명시한다.

### 공백 4. Lighter 마스킹 주소 — ✅ **즉시 확정은 해소, 충돌 위험은 남음 (A-07)**

**근거:** Lighter v2 회신, LW-13 (Proposed), **senya 10/19 회신**

실시간 API는 주소를 마스킹한다: `0x` + 앞 2자 + 뒤 4자 = 식별 문자 6개. 전체 주소는 주간 CSV에만 있다.

> **해소된 부분.** 처음에 "Lighter는 즉시 연동 확정이 불가능하다"로 적고, 파트너에게 "주간 CSV 전에 전체 주소 1개를 확인해 줄 수 있는가"를 물을 항목으로 뒀다. **senya가 10월 19일에 이미 답했다.** 마스킹 1건 일치 시 **즉시 연동**하고 `used_at`을 바인딩 시각으로 쓴다. **일주일 Processing 대기 설계는 폐기됐다** (A-07).

**남은 것 — 마스킹 충돌 (B-3-2):**
- 식별 문자가 6개뿐이라 **2건 이상 겹칠 수 있다.** 그때만 `Processing`이 발생한다
- 이 경우의 처리 방식은 **아직 파트너와 논의되지 않았다**
- Processing 최대 기간과 만료 후 처리 (14일 삭제 안의 위험: 거래를 안 한 정상 사용자가 삭제됨) — **B-3-3**
- Processing 상태에서 적립 추정치를 보여줄지

> ⚠️ **추가 발견:** 마스킹 대조를 **EIP-55 체크섬 주소 기준**으로 계산해야 한다. 소문자로 계산하면 Lighter 연동이 전부 실패한다 (B-3-2a).

### 공백 5. ApeX AccountID가 없어 키 설계가 확정되지 않는다

**근거:** ApeX 미해결 #1

설계상 모든 DEX 레코드는 `지갑 주소 + DEX 계정 ID`로 식별한다. ApeX 스펙은 API 2, 원장 레코드, 웹훅 어디에도 `account_id`를 반환하지 않는다.

**파트너에게 물어볼 것:** `account_id`를 추가하거나, "지갑 1개 = ApeX 계정 1개"임을 확인해 달라.
**후자라면** Lighter처럼 지갑 주소 단독 키로 운영 가능하다. 백오피스에 이미 "Wallet only mode"와 나중에 키를 교체하는 "Re-key" 기능이 설계되어 있다(LNK-24).

### 공백 6. ApeX 원장 레코드에 금액·토큰·주소·지급시각이 없다

**근거:** ApeX 미해결 #7

스펙에 있는 것: `commission_state`, `reward_period`, `fee_basis`, `record_id`, `available_balance`
**스펙에 없는 것: 페이백 금액 자체, `wallet_address`, `token`, `payout_time`**

금액이 없으면 화면에 표시할 수 없다. 출시 차단 사항이다.

### 공백 7. Aster는 회신이 없다

Aster의 P0 항목 대부분이 "Requested" 상태다. 현재 가능한 것은 Builder API 경유 일부(승인된 사용자 목록, 수수료 조회)뿐이고, **리베이트 조회는 계정 소유자만 가능**하다.

추가로 **365일 바인딩 만료**가 Aster에만 있다. 갱신 방식(R13)이 정해지지 않으면 **모든 Aster 사용자가 1년 후 페이백을 받지 못한다.**

---

### 공백 8. 내부 요구 5개 항목 중 3개가 그대로는 성립하지 않는다 (2026-10-20)

개발팀이 정리한 `결론(거래소 질문)` 5개 항목을 DEX 4곳 역량과 대조한 결과다.

| # | 요구 | Lighter | ApeX | EdgeX | Aster | 판정 |
|---|---|:---:|:---:|:---:|:---:|---|
| 1 | 단건 조회 (마스킹 없는 지갑 주소) | **✕** | ● | ● | ◐ | Lighter만 불가 |
| 2 | 커미션 조회, 1일 기준 | **✕** | ◐ | ● | ● | Lighter 구조적 불가 |
| 3 | 거래소가 고객에게 지급한 커미션 조회 | ◐ | ● | ● | ◐ | 조회는 되나 **모델이 성립 안 함** |
| 4 | 출금 시 전액 인출 (부분 출금 금지) | **✕** | **✕** | **✕** | **✕** | **전제 오류** |
| 5 | 테더맥스 레퍼럴 발생분만 구분 | ● | ◐ | ◐ | ● | 가능. 2곳 단서 |

**1·2번 — Lighter는 협상 대상이 아니다.** 단건 조회 API가 없고 UID 개념 자체가 없어 대체 식별자를 줄 수도 없다(마스킹 매칭이 유일, A-07로 즉시 확정만 해소). 정산이 주 1회라 일 단위 조회는 제공할 데이터가 없다. **구조적 한계이므로 파트너 질문 목록에 넣지 않는다.**

**3번 — "발생 − 지급 = 잔액" 모델은 ApeX에만 성립한다.**

```
Lighter / EdgeX / Aster : 발생 100 − 지급 100 = 0   (발생 즉시 고객 계정으로 나감)
ApeX                    : 발생 100 − 수령 60  = 40  (Rewards Center 미수령분)
```

차감 모델은 테더맥스가 돈을 들고 있는 CEX 전제에서 나온 것이다. 나머지 3곳은 **`지급 완료 누적액`을 그대로 표시**하는 현행 확정안이 맞다. 더구나 고객이 DEX에서 실제 출금한 금액은 **4곳 모두 제공하지 않는다**(공백 1).

**4번 — 테더맥스에 출금 버튼이 없으므로 강제할 수단이 없다.** 출금은 DEX 사이트에서 일어나고 금액은 고객이 정한다. 다만 요구문의 뒷문장(*"자동으로 DEX가 지급해주는 방식이 가장 좋다"*)은 **Lighter·EdgeX·Aster에서 이미 기본값**이다. ApeX만 claim이 필요하다. 화면 영향은 [03](03_정책_결정_기록.md) B-7-18.

**5번 단서 2건** — EdgeX는 팀 전체 귀속이라 `downlineRewardAmount`가 섞여 오므로 `selfRebateAmount`만 표시한다(오버라이드 비활성화 요청 C-9). ApeX는 **특별 이벤트 요율(`current_eligibility`)이 페이백 요율을 바꾸는지 미확정**이라 "거래소 자체 이벤트로 발생한 커미션 제외"가 아직 보장되지 않는다(5장 ApeX 5번).

## 4. 수기 업로드(CSV) 대체 경로

API 미개통 구간은 전부 백오피스 엑셀 업로드로 대체한다(CSB-2).

| DEX | CSV 전달 | 시각 | 템플릿 필수 컬럼 | 거부 규칙 |
|---|---|---|---|---|
| **공통** | 접근 통제 공유 폴더 | 일 1회 | 기존 컬럼 + Wallet Address, Account ID, record ID, trade date, status, amount, Rebate Coin | Account ID 누락, 토큰 불일치, 주소 오류 4종 |
| Lighter | **CSV가 정산 기준 (대체가 아님)** | 매주 월요일 | week, wallet, account_index, bind time, tier, fees paid, cashback, TetherMax share, status, tx hash | 지갑·주차·상태·금액 누락 |
| ApeX | 일 1회 | 02:00 UTC | record_id, wallet_address, account_id, reward_period, fee_basis, amount, token, commission_state, payout_time | record_id 누락, USDT 외 토큰 |
| EdgeX | 일 1회 | 02:00 UTC | 18개 컬럼 (id, ethAddress, userId, accountId, 금액 5종, state, 지급 참조 3종 등) | record ID·account ID 누락, USDC 외 코인 |
| Aster | 일 1회 | 09:00 UTC 이후 | tranId, address, settlementDay, incomeType, asset, feeBasis, income, payoutPrice, priceTime, usdtValue, state, time | **usdtValue 없는 행 거부**, 바인딩 기간 밖은 보류 |

**주의:** 공통 템플릿의 "Account ID 누락 시 행 거부" 규칙이 Lighter·Aster·ApeX(wallet-only)와 충돌한다. 세 곳은 Account ID가 없는 것이 정상이다. (백오피스 엣지케이스 미해결 #8)

## 5. 파트너에게 물어볼 것 (정리)

### Lighter (5건)
1. 합의된 페이백 요율 (수혜자 몫 / 테더맥스 몫) — **주중 추정치 계산에 필수**
2. 주간 CSV 전달 방식과 월요일 몇 시인지. 수수료가 없는 수혜자도 매주 포함되는지
3. 주간 $1 미달 금액이 다음 주로 이월되는지 소멸되는지
4. **주간 CSV 전에 전체 주소 1개를 레퍼럴로 확인해 줄 수 있는지** (마스킹 매칭 제거 가능)
5. 담당 연동 엔지니어

### ApeX (8건)
1. **`account_id` 추가, 또는 "지갑 1개 = 계정 1개" 확인** (키 설계 차단)
2. 웹훅 이벤트 목록과 페이로드, 서명 방식, 재시도 정책
3. **인증 방식과 base URL** (스펙에 없음)
4. 정정·취소를 원장에 어떻게 표현하는지
5. 특별 이벤트 요율이 사용자 표시 요율에 영향을 주는지
6. 지갑 주소로 조회하면 귀속된 모든 계정이 반환되는지
7. **원장 레코드에 페이백 금액·지갑 주소·토큰·지급 시각이 포함되는지** (출시 차단)
8. **Rewards Center의 claim이 전액 단위인지, 부분 claim이 가능한지** (화면 문구와 미수령 잔액 표시에 영향)

### EdgeX (7건)
1. partnerRate 모델 수용 + **실제 값** (상업 협의 대기)
2. 팀 전체 귀속 (level 2·3 포함) 확인
3. **회원 간 추천 오버라이드 비활성화** (테더맥스 커미션 보호 + "DEX 초대 보상 없음" 원칙)
4. 재무팀이 일별 커미션 레코드와 월 명세서 외에 인보이스를 요구하는지
5. 신규 귀속·Pending→Paid 전환 웹훅 (현재 `user.rate_changed`만 확인됨)
6. 파트너 API 키와 테스트 환경, 제한 지역 API
7. 일별 레코드의 정정·취소 표현 방식

### Aster (6건 + 회신 자체)
1. 레퍼럴 바인딩 사용자를 Builder 승인 목록처럼 받을 수 있는지, 아니면 테더맥스가 builder로 등록해야 하는지
2. `tranId`가 소득 유형 전체에서 고유한지
3. 리베이트 취소가 가능한지, 어떻게 표시되는지
4. USDT 환산에 어떤 가격(mark/index/spot)을 쓰고, 지급 후 고정되는지
5. **365일 바인딩 갱신 방식 (R13)** — 거래를 계속하면 유지되는지, 만료 후 재바인딩인지
6. 내부 사용자/계정 ID를 반환할 수 있는지

## 6. 요청 서비스 수준 (전 파트너 공통)

| 항목 | 목표 |
|---|---|
| API 가용성 | 월 99.5% |
| 호환성 깨지는 API 변경 사전 고지 | 30일 |
| 정산 통화 / 요율 / 제한 변경 고지 | 14일 |
| P0 장애 응답 | 1시간 내 확인, 24/7 |
| 지원 채널 | 공동 텔레그램 + 양측 담당 엔지니어 지정 |
| 데이터 조회 기간 | 최대 180일 (이보다 오래된 활동은 소급 불가) |
| 미매칭 레코드 | 1% 미만, 2영업일 내 해소 |
| 분쟁 제기 기한 | 명세서 후 30일 |

**180일 제약의 의미:** 사용자가 Cashback Summary에서 180일보다 오래된 달을 열면 이미 수집된 데이터만 보인다. 소급 수집이 불가능하므로 **출시 초기부터 수집이 끊기지 않아야 한다.**

## 7. 결론

### 데이터 확보 관점의 출시 가능성

| DEX | 출시 가능 여부 | 차단 사유 |
|---|---|---|
| **Lighter** | 가능 | 단, 주간 CSV 의존 구조를 수용하고 연동 확정 방식을 정해야 함 |
| **EdgeX** | 가능 | 단, 출금 가능 잔액 없는 UI를 확정하고 partnerRate를 합의해야 함 |
| **ApeX** | **차단** | 원장에 금액이 없고 계정 키가 없음. 인증 방식 미정 |
| **Aster** | **차단** | 회신 없음. P0 대부분 요청 단계 |

### 권고

1. **Lighter + EdgeX 2곳으로 1차 출시**, ApeX·Aster는 회신 후 순차 투입하는 방안을 검토한다. 백오피스가 DEX별 활성/비활성을 지원하므로 구조적으로 가능하다. 단 **지갑 한도가 "3 × 활성 DEX 수"이므로 활성 DEX가 2곳이면 한도가 6개로 줄어든다** — 이 규칙을 먼저 재검토해야 한다 (정책 결정 **B-3-1**).
2. **ApeX 원장 금액 필드와 AccountID**를 최우선으로 요청한다. 이 둘 없이는 화면을 만들 수 없다.
3. **Aster 바인딩 갱신(R13)**을 상업 협의 안건으로 올린다. 기술 항목이 아니라 "1년 후 모든 Aster 사용자의 페이백이 끊긴다"는 사업 문제다.
4. **Lighter 요율**을 받아야 주중 적립 추정치를 계산할 수 있다. 못 받으면 주중에는 아무 숫자도 보여줄 수 없다.
5. 수기 CSV 업로드 경로를 **1차 출시 시점부터 동작하게** 준비한다. 네 곳 중 API가 완비된 곳이 없다.
