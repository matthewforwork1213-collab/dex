## A-02. DEX 지갑을 기존 Account 메뉴에 통합 (별도 메뉴 신설 없음)

- **영향 문서 ID:** `NAV-5`, `LST-1`, `LST-35`~`LST-40a`
- **영향 범위:** 백오피스

## A-03. Aster 365일 바인딩은 갱신 전제로 설계하고 UI에 잔여 일수를 표시한다

> 🔄 **2026-10-26 뒤집힘 — 바인딩이 연속으로 유지됩니다.** 갱신 전제도, 잔여 일수 표시도 **불필요**합니다. 아래 결정은 기록으로만 남깁니다. ⚠️ Aster 서면 확인은 아직 없습니다.

- **결정:**
  1. **1년마다 갱신해야 하는 것을 전제**로 설계한다
  2. **UI에 잔여 일수를 계산해 표시**한다
  3. 잔여 일수 계산의 기준값은 **Aster가 조회로 반환하는 `bindExpireTime`을 우선** 사용한다
  4. Aster가 조회로 반환하지 않으면, **바인딩 시각을 수신한 시점에 이력 테이블로 영구 기록**하고 **지갑 주소 기준**으로 조회한다
  5. **최초 바인딩 시각을 모르는 지갑은 잔여 일수를 표시하지 않는다.** 틀린 숫자보다 안 보여주는 편이 낫다
- **결정일:** 2026-10-20
- **근거:** 테더맥스에서는 지갑과 테더맥스 계정의 연결이 바뀔 수 있다 — 연동 해제 후 재연동, 소유권 분쟁으로 다른 계정에 이전. 바인딩 자체는 Aster 쪽에 있어 영향받지 않지만, 테더맥스가 만료일을 조회로 받지 못하면 **재연동 시 정보를 잃는다.** 그러면 우리 DB 최초 등록일 기준으로 셀 수밖에 없는데 그것은 실제 바인딩일이 아니다. 특히 **테더맥스 연동 전부터 Aster에 바인딩돼 있던 지갑은 처음부터 틀린다.**
- **파트너 확인 대기:** Aster가 매 조회마다 `bindTime`과 `bindExpireTime`을 반환하는가 (요청서 9b, P0)
- **영향 문서 ID:** `LK-8`, `LW-11`, `CSB-16`
- **영향 범위:** 프론트, 백오피스, 데이터, 파트너 협의
- **관련 미결:** B-7-2

## A-05. 거래소 API 요청 문서는 DEX별 4개로 분리하고 국문·영문 각 4개로 작성한다

- **결정:** 파트너 발송용 문서를 **DEX별 4개 마크다운으로 분리**한다. **영문이 발송본, 국문이 내부 검토용**이며 1:1로 대응한다.
- **결정일:** 2026-10-20
- **근거:** 헤일리가 각 파트너에게 그대로 전달할 수 있어야 한다. 국문 내부 판단이 섞이면 파트너에게 노출된다.
- **산출물:** `06a`~`06d` 영문 4개 + `06a`~`06d` 국문 4개 + `06_내부가이드`

### 2026-10-20 수정 2건

**1. 영문 전용 → 국문·영문 각 4개.** 1차 마감 요구사항이 "국문/영문으로 작성"이었다. 처음에 영문 전용으로 적은 것은 요구사항을 잘못 읽은 것이다.

**2. 발송 문서 안의 내부 메모 블록을 폐기한다.** 처음에는 "각 발송 문서 상단에 내부 메모 블록을 두고 발송 전 삭제한다"로 정했다. **이 방식을 버린다.**

> **발송본 안에 "이 블록은 삭제하고 보내세요"가 들어 있는 구조는 그 자체가 사고 위험이다.**

실제로 전수 점검에서 06c·06d 영문에 국문 메모가 남아 있는 것이 발견됐다. EdgeX 쪽은 본문이 "This note confirms points 1 to 8"이라고 선언하는데 그 위 메모가 **"실제로 승인된 것이 아니다"**라고 적고 있었다. 그대로 나가면 신뢰를 잃는다.

**새 규칙: 발송본에는 내부 메모를 넣지 않는다.** 발송 전 확인 사항은 **`06_내부가이드`의 "발송 전 문서별 확인 사항"** 한 곳에만 둔다.

## A-07. Lighter 연동은 즉시 확인한다 (Processing 일주일 대기 설계 폐기)

  2. 사용자가 붙여넣은 지갑을 **EIP-55 체크섬 형식으로 변환 후** 마스킹해 대조

## A-08. ★ 적용·배제를 가르는 단일 원칙

- **결정:** DEX의 부가 서비스 적용 여부는 아래 한 줄로 판정한다.

> **자격을 만드는 행위에는 DEX를 포함한다. 돈을 받는 목적지에서는 DEX를 배제한다.**

| 구분 | DEX | 예시 |
|---|---|---|
| **자격을 만드는 행위** | **포함** | 미션 달성, 거래로 인한 페이백 적립, 누적액 집계, 연동 완료, 내역 표시, 알림 발송 |
| **돈을 받는 목적지** | **배제** | 이벤트 리워드 수령 UID, 쿠폰 사용 대상 UID, 초대 리워드 출금 계좌, 챌린지 보상 수령 UID |

- **결정일:** 2026-10-20
- **근거:** 테더맥스는 DEX 사용자에게 송금할 수단이 없다. 그러나 **행위 자체를 인정하지 않을 이유는 없다.** DEX로 미션을 달성했으면 달성한 것이고, DEX에서 페이백이 쌓였으면 쌓인 것이다. 받는 곳만 CEX UID로 제한한다.
- **영향 범위:** 프론트, 백오피스 전반

### 적용 방법 — 2026-10-20 수정

처음에는 **"UID 선택 목록이 뜨는 모든 화면에서 DEX를 제외한다"**로 적었다. **이 기준은 쓸 수 없다.**

기존 서비스를 전수 확인한 결과 **사용자 화면에 UID 드롭다운이 거의 없다.** 실제 패턴은 세 가지다.

| 패턴 | 화면 | 사례 |
|---|---|---|
| **(a) 연동 UID 전체 나열** | 목록에서 한 건을 누름 | 누적 페이백 좌측 레일, 페이백 랭킹 드로어 |
| **(b) 단일 UID 상세 고정** | 진입 시점에 UID가 정해짐 | 페이백 상세(`B Bitget UID 8504291751 활성`), 페이백 타임라인 |
| **(c) 명시적 UID 선택기** | **소수.** 돈을 받을 UID를 고름 | 맥스보드 `SCR-U03 참여 UID 선택`(바텀시트/팝업), WOO X Pro `리워드 수령 UID 지정`(최초 1회 고정) |

> **(c)만이 "돈을 받는 목적지"다.** (a)와 (b)는 조회 화면이다.

그 외에 UID 선택 UI가 있는 곳은 **백오피스 검색 필터**(글로벌 리그 `팀명 / TUID / 참여 UID`)와 **거래소 선택**(부스트 요율 비교)이다.

> ⚠️ **처음에는 "드롭다운이 단 하나도 없다. 패턴은 두 가지뿐이다"로 적었다. 틀렸다.** 1차 조사(부스트, 누적 페이백, 타임라인, 글로벌 리그, 페이백 랭킹, UID 연동 상세, 매칭 출금) 7종에는 없었지만, 2차 조사에서 **맥스보드와 WOO X Pro 이벤트에 명시적 선택기가 있는 것을 확인했다.** 그래서 (c)를 추가했다. 판정 기준은 그대로 유효하다 — 오히려 (c)가 "돈의 방향" 기준의 전형적 사례다.

**그래서 판정 기준을 화면 형태가 아니라 돈의 방향으로 바꾼다.**

> **그 화면에서 테더맥스가 사용자에게 돈을 보내는가?**
> **보낸다 → DEX 배제. 보내지 않는다 → DEX 포함.**

| 판정 | 근거 | 해당 화면 |
|---|---|---|
| **배제** | 테더맥스 잔액에서 출금이 일어남 | 매칭 출금, 페이백 상세 출금 CTA |
| **배제** | 이벤트 리워드가 지급됨 | 글로벌 리그 데일리 리워드, 페이백 랭킹 상금, **페이백 부스트** |
| **배제** | 쿠폰이 적용됨 | 쿠폰 사용 대상 |
| **포함** | 조회·표시만 함 | 페이백 타임라인, 누적 페이백, 내역 |
| **포함** | 자격·달성을 판정함 | 미션 게이지, 리뷰 작성, 퀴즈 응시 |

**이 기준은 화면을 열어보지 않아도 판정할 수 있다.** 이전 기준은 화면 구조를 먼저 알아야 했다.

## A-09. 이벤트 리워드는 DEX에서 전면 배제 — 지급·회수·선택 목록 포함

- **결정:** 이벤트 리워드(Event Reward)는 DEX에서 **사용할 수 없다.** 따라서 아래 전부가 배제된다.
  1. **적립** — DEX 활동으로 이벤트 리워드가 발생하지 않는다
  2. **지급** — DEX 지갑을 지급 대상으로 선택할 수 없다
  3. **회수** — 대상이 없으므로 해당 없다
  4. **주는 기능의 선택 목록** — 운영자가 이벤트 리워드를 지급하는 **모든 화면의 UID 선택 목록에서 DEX를 제외**한다
- **결정일:** 2026-10-20

## A-13. 페이백 챌린지 — 게이지는 DEX 포함, 수령 UID는 DEX 배제

- **결정:**
  1. **챌린지는 수령 UID를 선택해야 작동한다.** 받을 대상이 있어야 챌린지가 돌아간다
  2. **수령 UID로 DEX를 선택할 수 없다** → 사실상 **CEX UID가 있어야 챌린지가 작동한다**
  3. **게이지(누적액)는 DEX로도 찬다.** 출금 여부와 무관하게 **거래로 인해 발생한 페이백 금액만큼** 쌓인다
- **결정일:** 2026-10-20
- **근거:** 사용자 지시. A-08 원칙 그대로다.

### 이 구조가 해결하는 것

**"레벨 도달했는데 수령할 수 없는 상태"가 발생하지 않습니다.** 수령 UID 선택이 작동의 전제 조건이므로, 챌린지가 돌아가고 있다는 것은 이미 CEX UID가 선택되어 있다는 뜻입니다.

| 회원 유형 | 챌린지 작동 | 게이지 |
|---|---|---|
| CEX UID 있음 + DEX 지갑 있음 | **작동** | **CEX 페이백 + DEX 페이백 둘 다 누적** |
| CEX UID 있음, DEX 없음 | 작동 | CEX 페이백만 |
| **DEX 지갑만 있음** | **작동 안 함** | — (수령 UID가 없으므로 챌린지 자체가 시작되지 않음) |

### 기존 규칙에서 바꿔야 할 것

기존 챌린지는 **"적격 UID에 지급된 커미션"**만 누적액을 올립니다. DEX는 테더맥스가 지급하지 않으므로 **"DEX가 지급한 페이백 금액"을 산입하도록 기준을 넓혀야 합니다.**

| 항목 | 기존 | 변경 |
|---|---|---|
| 누적 기준 | 적격 UID에 **지급된 커미션** | + **DEX가 지급한 페이백 금액** |
| 출금 조건 | — | **출금과 무관.** 거래로 발생한 금액이면 누적 |
| 수령 UID 선택 목록 | 연동 UID 전체 | **CEX UID만** |
| 시작 조건 | 최초 UID 연동 완료 | **CEX UID 수령 대상 선택** (DEX 지갑 연동만으로는 시작 안 됨) |

- **영향 범위:** 프론트, 백오피스, 데이터
- **대체된 검토 항목:** B-2 페이백 미션 관련

| **처리 소요 안내** | 자동 절차의 "약 5분"과 달리 CS 처리는 더 걸립니다. 기대치를 맞춰야 합니다 |
| **남는 위험 인지** | 지갑 주소는 공개 정보라 타인의 주소를 넣기 쉽습니다. **먼저 넣은 사람이 선점**하는 구조이고, 되돌리는 속도가 CS 처리 속도에 달립니다 |

| **맥스보드 (거래소 빙고)** | 참여 UID로 이벤트 리워드 적립 | 빙고판 **1개 = 거래소 1곳**이다. DEX 빙고판을 만들지 않으면 **자연 배제**된다. 만들 경우 `SCR-U03 참여 UID 선택`에서 DEX 제외 |
| **VIP** | **VIP 요율도 이벤트 리워드로 지급** | DEX UID는 VIP 대상에서 제외. 아래 참조 |
| **페이백 부스트** | **부스트 차액을 이벤트 리워드로 지급** | DEX는 부스트 대상에서 제외 |

- **결정일:** 2026-10-20
- **근거:** 사용자 지시. A-09(이벤트 리워드 전면 배제)의 직접 귀결이다.

### ★ 여기서 나온 일반 규칙 — 요율을 올려주는 기능은 전부 배제

VIP와 부스트는 겉보기에 **"추가 페이백 요율"**이다. 그래서 "송금이 아니니 DEX에도 되지 않나" 싶지만 **아니다.**

> **테더맥스는 거래소 요율 자체를 바꿀 수 없다. 요율을 올려준다는 것은 차액을 테더맥스가 이벤트 리워드로 얹어준다는 뜻이다.**

| 기능 | 표면상 | 실제 구현 |
|---|---|---|
| **VIP** | "VIP가 되면 추가 페이백 요율" | 차액을 **이벤트 리워드**로 지급 |
| **페이백 부스트** | "기간 한정 페이백률 인상" | 커미션 페이백분(기본요율) + **이벤트 리워드분(부스트율 − 기본요율)** 으로 회계 분리 |

**따라서 "요율 상향"을 혜택으로 내거는 모든 기능은 DEX에 적용할 수 없다.** 앞으로 나올 유사 기능도 같은 판정을 받는다. 판정할 때 **"요율을 올려준다"는 말을 "차액을 테더맥스가 이벤트 리워드로 준다"로 바꿔 읽으면** 바로 결론이 나온다.

### VIP의 구조 — 내가 잘못 이해했던 부분

처음에 **"VIP 게이지가 개별 UID 단위라서 DEX UID를 대상에서 빼면 그만"**이라고 적었다. **UID 단위라는 사실은 맞지만 그게 배제 이유는 아니다.**

> **VIP는 UID별로 체크하므로 한 TUID 안에 여러 개의 VIP UID가 포함될 수 있는 구조다.** (사용자 확인, 2026-10-20)

**배제 이유는 산정 단위가 아니라 보상 형태다.** VIP 요율이 이벤트 리워드로 지급되기 때문이다. 산정 단위가 TUID였더라도 결론은 같았다.

그래서 **A-13(챌린지)과 갈리는 이유도 다시 쓴다.**

| | 게이지가 차면 생기는 것 | DEX 게이지 |
|---|---|---|
| **페이백 챌린지** (A-13) | **보상 수령 자격.** 수령 UID를 따로 고름 | **찬다.** 자격을 만드는 행위이므로 A-08에 따라 포함. 수령에서만 배제 |
| **VIP** (A-18) | **요율 상향 = 이벤트 리워드 지급 상태 그 자체.** 자격과 보상이 분리되지 않음 | **차지 않는다.** 게이지를 채워봐야 줄 수 있는 것이 없다 |

**자격과 보상이 분리되는가가 기준이다.** 챌린지는 분리된다(게이지 ≠ 수령). VIP는 분리되지 않는다(등급 = 요율 = 이벤트 리워드).

- **⚠️ 되돌려야 할 설계:** DEX PRD는 **마일스톤·VIP 진행바에 DEX 금액을 포함**하도록 설계돼 있다. 되돌려야 한다.
- **영향 문서 ID:** `WD-1`(마일스톤 진행바), `GW-2`, VIP 관련 전체
- **영향 범위:** 프론트, 백오피스, **데이터 집계 파이프라인** (VIP·부스트 집계에 DEX 데이터를 넣을 필요가 없어짐)
- **부수 효과:** **"DEX가 지갑별 요율 상향을 지원하는가"라는 질문이 완전히 불필요해졌다.** VIP와 부스트 둘 다 X이므로 쓸 곳이 없다. ①의 API 요청 문서에 넣었던 P2 1·2번 문항을 **삭제했다.** 국가 관련 3·4번만 남긴다.

**2. DEX만 쓰는 초대자는 받아도 출금할 수 없다.** → **B-2-9**

# B. 결정 대기

## B-1 그룹: 돈의 흐름 모델 교정 (최우선)

기존 문서가 CEX 템플릿을 복사해서 생긴 오류다. 사용자에게 잘못된 정보를 주고 있어 가장 먼저 정해야 한다.

### B-1-1. DEX 상세 페이지 계산기의 돈 흐름 설명 `미결정`

**쟁점:** VD-5 흐름도와 설명 카드, VD-6 설명 서랍이 "거래소 → 테더맥스 → 사용자" 구조로 설명한다. 실제 DEX는 "DEX → 사용자 DEX 계정"이다. 같은 페이지 FAQ(VD-8)와 랜딩(DX-3, DX-12)은 올바르게 설명한다.

**선택지**
- (a) DEX용 흐름도를 새로 설계한다. `You → Trading fee → {DEX} → {DEX}가 당신의 {DEX} 계정으로 지급` 구조로 바꾸고, 테더맥스는 "추적하고 보여주는 주체"로만 표현한다
- (b) 계산기에서 흐름도와 설명 카드를 제거하고 숫자만 남긴다
- (c) CEX·DEX 공통 추상 표현을 쓴다

**권고:** (a). 교육이 이 퍼널의 핵심 과제이므로 흐름도 자체는 가치가 있다. 다만 DEX 전용으로 다시 그려야 한다. "Partner settlement"라는 CEX 용어도 버린다.

**영향:** VD-5, VD-6 전면 재작성. Figma 재작업 필요.

---

### B-1-2. VD-7 단계별 가이드 기본 문구 `미결정`

**쟁점:** 기본 라벨이 "Deposit {currency} into **your TetherMax wallet**"이다. 테더맥스에는 지갑이 없다.

**권고:** 기본 5단계를 DEX 현실에 맞게 다시 쓴다. 입금 단계는 "거래소나 지갑에서 {DEX}로 {currency} 전송"이 되어야 한다. 백오피스에서 단계별로 운영자가 작성하는 구조이므로, 기본값만 고치면 된다.

**영향:** VD-7, EDC-16/17 기본값.

---

### B-1-3. DX-1 랜딩 히어로 리드 문구 `미결정`

**쟁점:** "No KYC checks. **Connect a wallet**, and start trading!" — 문서 전체가 "지갑 연결을 요구하지 않는다"를 강조하는데 첫 화면이 뒤집는다.

**권고:** 문장을 둘로 나눈다. DEX에서 하는 일(지갑 연결, 거래)과 테더맥스에서 하는 일(주소 붙여넣기)을 구분한다. 엣지케이스 미해결 #16도 같은 지적이다.

---

### B-1-4. "Available Cashback" 명칭 재정의 `미결정`

**쟁점:** DEX 카드가 "Available Cashback"으로 표시하지만 실제 값은 누적 적립액이다. DEX에서 출금해도 줄지 않는다. DEX마다 의미도 다르다 (EdgeX는 `totalPaidAmount`).

**선택지**
- (a) 전 DEX에서 "Paid"(지급 완료) 계열 명칭으로 바꾼다. 엣지케이스 미해결 #5 권고안
- (b) "Available"을 유지하고 캡션으로 설명한다
- (c) DEX별로 다르게 쓴다 (현재 상태)

**권고:** (a). "Available"은 "지금 뺄 수 있는 금액"으로 읽히므로 오해의 소지가 크다. 다만 ApeX의 `available_balance`는 실제로 뺄 수 있는 금액이므로 이것만 "Available on ApeX"로 남긴다.

**영향:** LK-7, LK-10, CH-11, WD-2, GW-2, CS-1, 모든 관련 카피.

**내부 데이터 모델에도 같은 원칙을 적용한다 (2026-10-20).** DEX는 "적립 기록"과 동시에 "지급 완료 기록"을 남겨 사용자 잔액을 0으로 상쇄하는 구조인데, 그 상쇄 레코드를 `withdrawal`로 명명하면 안 된다. **그것은 사용자의 출금이 아니라 DEX의 지급 완료 사건이다.** 테더맥스는 사용자가 DEX에서 실제로 출금했는지 영원히 알 수 없다(4곳 모두 `Total Claimed` 미제공, B-1-5). 컬럼명을 `dex_paid` 계열로 두어야 화면 문구 "적립액은 출금해도 줄지 않습니다"(WD-7)와 CS 응대가 어긋나지 않는다.

### B-2-8. DEX 초대 리워드의 지급 트리거 `미결정` ★A-19가 만든 공백

**쟁점:** 기존 규칙은 **"초대받은 사람이 출금할 때 상위 계정에게 초대 리워드 지급"**이다. **DEX 사용자는 테더맥스에서 출금하지 않는다.** 트리거가 성립하지 않는다.

> **2026-10-20 — 현행 규칙 원문을 확인했다** (파트너 허브 `Terms & Conditions`, A-20).
>
> `Invite Rewards are only earned on the **"trading-generated cashback" portion of a sub-account's withdrawal**.`
> `For some exchanges, Invite Rewards may not be earned even if a sub-account withdraws their cashback amount.`
>
> **산정 기준(거래로 인한 페이백)은 DEX에도 부합한다.** 이벤트 리워드를 제외한다는 점도 A-09와 맞는다. **문제는 트리거 하나뿐이다.**
>
> 또한 **`For some exchanges ... may not be earned`라는 예외 문구가 이미 존재한다.** 아래 D안의 근거가 된다.

| 안 | 트리거 | 특징 |
|---|---|---|
| **A. DEX 지급 시점** | DEX가 피초대자에게 페이백을 지급하고, 그 레코드를 우리가 수신한 시점 | CEX의 "출금 시"와 의미가 가장 가깝다. 다만 DEX별 주기가 다르다 (Lighter 주 1회 ~ ApeX 시간 단위) |
| **B. 정기 배치** | 일/주 단위로 일괄 산정 | 주기 편차를 흡수한다. 대신 CEX와 지급 시점이 달라진다 |
| **C. 피초대자의 CEX 출금 시 합산** | DEX 몫도 CEX 출금 때 함께 정산 | **피초대자가 CEX를 안 쓰면 영원히 지급되지 않는다.** 사실상 불가 |

| **D. DEX는 초대 리워드 대상에서 제외** | 지급하지 않음 | **기존 약관에 이미 예외 문구가 있다** (`For some exchanges, Invite Rewards may not be earned`). 다만 **A-19에서 "금액 표시"로 확정했으므로 이 안을 택하면 A-19를 뒤집어야 한다** |

**C안은 피해야 한다.** DEX만 쓰는 피초대자가 있으면 지급이 멈춘다.

**선결 — 해소됨.** 산정 기준은 **"하위 계정 출금액 중 거래로 인한 페이백 부분"**으로 확인됐다 (A-20). DEX 페이백도 "거래로 인한 페이백"이므로 **기준은 부합한다.** 남은 것은 **"출금"이라는 트리거를 DEX에서 무엇으로 대체할 것인가** 하나다.

### B-2-9. DEX만 연동한 초대자의 출금 경로 `미결정` ★A-19가 만든 공백

**쟁점:** A-19로 **초대 리워드는 쌓이지만, 출금 UID 선택 목록에 DEX가 나오지 않는다.** DEX 지갑만 연동한 사용자는 **리워드가 쌓이는 것을 보면서 영원히 출금할 수 없다.**

| 안 | 처리 |
|---|---|
| **A. 안내 문구** | 잔액 옆에 **"출금하려면 거래소 UID 연동이 필요합니다"** + CEX 연동 링크 |
| **B. 출금 버튼 비활성 + 사유** | 버튼을 누르면 이유를 알려준다 |
| **C. 방치** | 빈 모달이 뜬다. **채택 불가** |

**C안은 불가하다.** 모달을 열었는데 선택지가 0개면 사용자는 버그로 읽는다.

**A안을 권고한다.** 쿠폰함 안내 문구(A-14 과제)와 **같은 성격의 문제**이므로 문구 체계를 맞추는 것이 좋다.

**⚠️ 이 상태는 실제로 발생한다.** DEX는 KYC가 없어 진입이 쉬우므로, **DEX만 쓰면서 친구를 초대하는 사용자**가 나온다.

## B-3 그룹: 연동 정책

### B-3-1. 지갑 연동 한도 `미결정` ★최중요

**쟁점:** 현재 설계는 "3 × 활성 DEX 수, 전 DEX 합산(풀링)"이다. 활성 DEX 4곳이면 12개, 10곳이면 30개. 한 DEX에 전부 몰 수도 있다.

**문제점**
1. **백오피스에 설정·조회·예외 처리가 전혀 없다.** 설정 위치, 회원별 사용량 조회 화면, 운영자 override가 모두 없다
2. **DEX를 비활성화하면 한도가 줄어든다.** 2곳만 출시하면 6개가 된다. 기존 연동은 유지하되 신규만 막는다고 했지만 운영 화면이 없다
3. **소유권 클레임 승인이나 비회원 기록 이관으로 한도를 넘기면** 어떻게 되는지 없다
4. 한 DEX에 30개를 몰 수 있는 구조가 의도된 것인지 불명확하다

**선택지**
- (a) 현행 공식 유지 + 백오피스 설정·조회 화면 신설
- (b) **고정 총량으로 바꾼다** (예: 회원당 지갑 12개). DEX 수와 분리되어 활성화/비활성화 영향이 사라진다
- (c) DEX별 개별 한도 (예: DEX당 3개)

**권고:** (b). 활성 DEX 수에 연동하면 비활성화가 전 회원에게 영향을 주고, 1차 출시를 2곳으로 줄이면 한도가 6개로 떨어진다. 고정 총량이 운영상 안전하다.

**어느 쪽이든 추가로 정해야 할 것**
- 백오피스 설정 위치와 변경 권한
- 회원별 사용량 조회 화면
- 운영자 예외 부여 가능 여부
- Processing 상태도 한도에 포함하는지 (EC-LNK-24는 포함을 제안)
- 소유권 이전·비회원 이관으로 초과했을 때 처리
- 같은 주소를 여러 DEX에 연동하면 각각 1칸 차지 (EC-LNK-26, 확정됨)

### B-3-2. Lighter 마스킹 매칭 — **상황 변경 (2026-10-20 텔레그램 확인)** `미결정`

**기존 판단:** 전체 주소를 주간 CSV로만 받으므로 연동 즉시 확정이 불가능하고, 다음 월요일까지 Processing으로 묶어야 한다.

**변경:** **Lighter가 10월 19일에 즉시 확인 방법을 알려줬다. Processing으로 일주일 묶는 설계는 불필요하다.**

senya 원문
> You can still verify a single user straight after they link, without waiting for the CSV:
> • Check the referral: call `userReferrals` with your read-only token. **Results are newest first**, so someone who just signed up is on the first page. Mask the wallet the user pasted the same way and look for a matching row. `used_at` gives you the binding time.
> • Get the AccountID: call `accountsByL1Address`. It's public and needs no auth.

**새로운 연동 흐름**
1. 사용자가 지갑 붙여넣기
2. 캐시된 `userReferrals`(시간당 폴링, 300개씩, 최신순)에서 마스킹 대조
3. 일치하면 **즉시 연동.** `used_at`이 바인딩 시각
4. `accountsByL1Address`로 서브계정 조회 (공개, 인증 불필요)
5. 주간 CSV가 나중에 전체 주소로 확정

**남은 진짜 쟁점 — 마스킹 충돌**

식별 문자가 6개뿐이라 referee가 늘면 두 지갑의 마스크가 겹친다. **senya는 이 부분을 언급하지 않았다.**

오매칭되면 남의 바인딩 시각과 **적립 추정치**가 엉뚱한 사용자에게 붙는다. 표시 오류가 아니라 정합성 문제다.

**권고 처리**

| 경우 | 처리 |
|---|---|
| 마스킹 일치 1건 | **즉시 연동** |
| **마스킹 일치 2건 이상** | **연동하지 않고** 다음 주간 CSV로 확정 |
| 일치 없음 | 레퍼럴 아님으로 거부 |

**파트너에게 요청한 것** (요청서 2번 항목)
1. 전체 주소 1개로 referee 여부를 확인하는 엔드포인트 (가장 선호)
2. 마스크 길이를 6자에서 8자로 확대
3. 둘 다 불가하면 위 표대로 구현

### B-3-2a. Lighter 마스킹은 **체크섬 형식** 기준 ⚠️ 구현 주의 `확인 필요`

senya 원문: *"Mask the wallet the user pasted the same way (**EIP-55 checksum**, keep the first 4 and last 4 characters)"*

**우리 설계는 주소를 소문자로 저장한다.** 마스킹 대조를 하려면 **EIP-55 체크섬 형식으로 되돌린 뒤** 잘라야 한다. 소문자 상태로 마스킹하면 글자가 안 맞아 **전부 불일치**가 난다.

놓치면 Lighter 연동이 전부 실패하는 지점이다. 요청서에서 재확인을 요청했다.

**마스크 범위:** `0x12…abcd` = 문자열 앞 4자(`0x` + hex 2자) + 뒤 4자. v2 문서의 "0x + first 2 + last 4 hex"와 같은 뜻이다.

### B-3-3. Processing 상태 타임아웃 `미결정` — 범위 축소

**B-3-2 변경으로 적용 범위가 줄었다.** Lighter 즉시 확인이 가능해졌으므로 Processing이 발생하는 경우는 아래로 한정된다.

- 마스킹 충돌 (2건 이상 일치)
- DEX 조회 실패·타임아웃
- 수동 확인이 필요한 경우

**권고:** 14일 후 **삭제하지 않는다.** 사용자가 보기에는 "연동했는데 사라졌다"가 된다. "확인 실패" 상태로 전환하고 재시도 또는 고객센터 경로를 제공한다.

**Processing 중 금액 표시:** 마스킹 충돌로 인한 Processing이면 **어느 행이 이 사용자 것인지 모르는 상태**이므로 적립 추정치를 보여주면 안 된다.

### B-3-4. 연동 검사 순서 `미결정`

**쟁점:** LW-8이 "already added → already in use → wallet limit → attribution" 순서를 제안하고 "to confirm"으로 표시했다.

**권고:** 제안 순서를 확정한다. 근거: 비용이 낮고 확정적인 검사를 먼저 하고, 외부 호출(attribution)을 마지막에 한다. 단 **지갑 한도 검사는 attribution 다음으로 미루는 안도 검토** — 레퍼럴이 아닌 지갑 때문에 "한도 초과" 메시지를 받으면 사용자가 혼란스럽다.

### B-3-5. 비회원 클레임의 소유권 공백 `미결정` ★중요

**쟁점:** 캡차만 통과하면 남의 지갑 주소로 적립액과 이력을 조회할 수 있다. 회원 간 중복은 화면 녹화 분쟁 절차가 있는데 비회원 경로에는 없다.

파트너 문서(Lighter R18)의 "남의 지갑을 붙여넣어도 얻을 게 없다"는 **지급**만 다루고 **정보 노출**은 다루지 않는다.

**연쇄 문제:** 비회원 기록이 남은 지갑을 다른 사람이 회원 계정에 연동하면 그 기록이 그 사람에게 이관된다(LW-25). 소유권 검증 없이 이관된다.

**선택지**
- (a) 현행 유지. 지갑 주소는 공개 정보이고 온체인에서 거래 내역을 볼 수 있으므로 추가 노출이 아니라고 본다
- (b) 비회원에게는 금액을 가리고 "페이백이 적립되어 있습니다. 가입하면 확인할 수 있습니다"만 보여준다
- (c) 비회원 클레임 자체를 DEX에서 제외한다

**권고:** (a)를 기본으로 하되 근거를 문서에 명시한다. 온체인 거래 내역은 공개이지만 **페이백 금액은 테더맥스와 DEX 사이의 정보**라는 반론이 가능하므로 법무 검토가 필요하다. 이관 규칙(LW-25)은 별도로 제한을 둘 것을 권고한다 — 같은 지갑에 여러 비회원 기록이 있으면 이관하지 않는다.

**부수 미결:** 여러 비회원이 같은 지갑을 클레임하는 경우 규칙이 없다.

**쟁점**
- 시도 제한: IP·기기 기준 15분에 5회, 15분 대기 (LNK-29, EC-GST-3 제안)
- 기록 보관: 마지막 방문 후 90일 (EC-GST-9 제안)

**권고:** 제안값을 확정한다. 백오피스에 설정 화면이 이미 설계되어 있다(LNK-29).

### B-3-7. EdgeX 팀 전체 귀속 수용 여부 `파트너대기`

**쟁점:** EdgeX는 테더맥스 루트 계정으로 이어지는 추천 체인 전체(2~3단계 포함)를 테더맥스 귀속으로 반환하려 한다(D3).

**추가 쟁점 (D4):** 회원 간 추천 오버라이드를 비활성화해 달라고 요청했다. 비활성화하지 않으면 회원이 다른 회원을 초대해 수익을 얻게 되는데, 이는 "DEX 활동은 초대 보상을 만들지 않는다" 원칙과 충돌하고 테더맥스 커미션을 침식한다.

**권고:** 오버라이드 비활성화를 관철한다. 비활성화되면 `rebateAmount = selfRebateAmount`가 되어 화면 표시와 대조가 단순해진다.

### B-3-8. ApeX 지갑 단독 키 운영 `파트너대기`

**쟁점:** ApeX가 `account_id`를 반환하지 않는다. 백오피스에 "Wallet only mode"와 나중에 키를 교체하는 "Re-key" 기능이 이미 설계되어 있다(LNK-24).

**권고:** ApeX가 "지갑 1개 = 계정 1개"를 확인해 주면 Lighter처럼 지갑 단독 키로 확정한다. Re-key 기능은 불필요해진다.

---

### B-3-9. Aster Solana 주소 지원 `파트너대기`

**쟁점:** VD-12 상세 콘텐츠는 Aster가 Solana를 지원한다고 쓰는데, 연동 검증은 EVM 전용이다(EXT-13). EC-LNK-31은 Solana 주소를 거부하고 EVM을 쓰라고 안내하는 안을 제안한다.

**권고:** 1차 출시는 EVM 전용으로 확정한다. Solana를 지원하려면 DEX 레코드에 별도 검증 규칙을 먼저 정의해야 한다(EXT-13의 제안 사항).

### B-3-10. 지갑 하나에 DEX 계정이 여러 개인 경우 `미결정`

**쟁점:** EdgeX는 `userId` 하나가 여러 `accountId`를 가질 수 있고, ApeX도 가능성이 있다. EC-LNK-27은 "리베이트를 받는 계정만 연동하고, 2개 이상이면 수동 확인 Processing"을 제안한다.

**권고:** 제안값 확정. 단 수동 확인 큐가 백오피스에 설계되어 있는지 확인이 필요하다.

**권고:** DEX별 임계치를 단일 출처로 삼고 백오피스 24시간 기준은 폐기한다. Aster는 정산 주기 확인 후 결정한다.

---

### B-4-2. 정정 레코드와 "earned는 감소하지 않는다" `미결정`

**쟁점:** 파트너 정정이 들어오면 음수 Adjustment 레코드로 earned 총액이 줄어들 수 있다(EC-DAT-5, 제안). 그런데 WD-8 화면 문구는 "Exchange Cashback is what you have earned, so it doesn't go down when you withdraw"다.

**권고:** 문구를 "출금으로는 줄지 않습니다"로 한정한다(엣지케이스 미해결 #8 권고안). 정정으로 감소할 수 있음을 별도 안내 경로로 처리한다. 정정 발생 시 사용자 알림 여부도 함께 결정한다.

**파트너 확인 필요:** ApeX·EdgeX·Aster의 정정 표현 방식이 모두 미정이다.

---

### B-4-3. 운영자 정정 권한 `미결정`

**쟁점:** CSB-8은 운영자가 correction 레코드를 만들 수 있다고 하고, ApeX·EdgeX 섹션은 파트너 레코드만 정정으로 인정한다. 해당 권한도 정의되지 않았다.

**제안되어 있는 것:** 전용 권한, 사유·출처 필수, 100 USDT 초과 시 2차 승인.

**권고:** 제안값 확정. 돈과 직결되므로 권한과 승인 절차가 반드시 필요하다.

---

### B-4-4. 월 마감 승인 주체와 조건 `미결정`

**쟁점:** CSB-10은 "차이가 0일 때만, ops lead가 승인"을 제안한다. 30일 넘게 제기되지 않은 차이가 있으면 승인할 수 없다.

**권고:** 제안값 확정. 승인 권한을 명시적 역할로 정의한다.

---

### B-4-5. 미매칭 레코드 목표와 만료 `미결정`

**쟁점:** CSB-9은 "1% 미만, 2영업일 내 해소"를 목표로 하고 "180일 초과 시 Expired"를 제안한다. 백오피스 엣지케이스 미해결 #16은 알림 기준을 "롤링 7일 1%"로 바꾸자고 한다.

**권고:** 제안값 확정 + 알림 기준은 롤링 7일로 한다.

### B-4-6. Aster 만료 후 레코드 처리 `미결정`

**권고:** 확정. 단 **사용자에게 "만료 후 거래는 페이백이 없다"를 사전에 충분히 알렸는지**가 핵심이다. 만료 30일 전 알림 1회만으로 충분한지 검토한다.

## B-5 그룹: 어드민과 권한

### B-5-1. 권한 모델 수립 `미결정` ★중요

**쟁점:** ROL-1이 결번이다. 기본 권한 모델 자체가 없다.

**정의되지 않은 권한**
- Aster 보류 레코드 처리, 바인딩 수동 기록
- ~~소유권 클레임 검토~~ (A-16으로 해당 없음)
- 미매칭 레코드 처리
- Pending 연동 승인
- 공통 CSV 업로드
- Exchange Type 설정
- 월 마감 승인
- 정정 생성
- 지갑 한도 변경

**정의된 역할:** Backoffice administrator (파트너 레코드, API 키), Content operator (콘텐츠·순서), Cashback operations (모니터링·CSV·대조·클레임), Ops lead (승인), Marketing (푸시·이메일)

**DEX별 권한은 설계됨:** Lighter 5종(ROL-3), ApeX·EdgeX 6종(ROL-4), 비회원·쿠폰(ROL-5) — 다만 역할 배정이 대부분 제안 단계다.

**권고:** 권한 매트릭스를 별도로 작성한다. 역할 × 기능 표를 만들고 각 칸을 채운다. 2인 승인이 필요한 것은 현재 Fraud unlink 하나뿐인데, 정정과 월 마감 승인도 후보다.

---

### B-5-2. Exchange Type 저장 후 변경 허용 여부 `미결정`

**쟁점:** EXT-4가 "Open decision"으로 남겨 두었다. 기본은 잠금이고, 허용하면 상위 권한과 감사 기록이 필요하다.

**권고:** 잠금 유지. 단 **잘못 입력했을 때 정정 절차가 없다**는 문제가 있다. 레코드 삭제·재생성 경로 또는 관리자 전용 수정 경로를 마련해야 한다.

---

### B-5-3. API 키 설정 권한 주체 `미결정`

**쟁점:** EXT-12는 Backoffice administrator만 가능하다고 하고, EXT-18은 Lighter configuration 권한(ROL-3)이라고 한다.

**권고:** 하나로 통일한다. 파트너 키는 돈과 직결되므로 administrator로 제한하는 편을 권고한다.

---

### B-5-4. 저장 모델 통일과 Draft/Preview 도입 `미결정`

**쟁점**
- 저장 방식이 두 가지다. DEX 리스트와 브로커 리스트는 마우스를 놓는 즉시 저장, Edit Display Priority는 Edit/Save/Cancel이다
- **Publish / Preview / Draft 개념이 없다.** 다국어 대량 작성인데 저장이 곧 라이브다. 배너 미리보기만 있다
- 즉시 저장은 키보드 대안(NFR-8)과 충돌할 수 있다

**권고:** 저장 방식을 Edit/Save/Cancel로 통일하고, **Preview 기능을 추가한다.** DEX 1곳당 운영자 입력 필드가 약 100개 + 미디어 26개인데 미리보기 없이 라이브에 반영하는 것은 위험하다.

**추가 검토:** Draft 상태를 도입할지. 도입하면 "번역 미완성인 언어는 저장 차단" 규칙을 완화할 수 있다.

---

### B-5-5. DEX 노출 순서 단일 소스 `미결정`

**쟁점:** DX-1 리스트, Edit Display Priority의 DEX Listings, Cashback 랜딩, LNK-11이 모두 정렬한다. 백오피스 엣지케이스 미해결 #3은 DX-1을 단일 소스로 하자고 한다.

**권고:** 페이지별로 다른 순서가 필요한지 먼저 판단한다. 필요 없으면 단일 소스로 통합한다. 필요하면 어느 페이지가 어느 설정을 쓰는지 명시한다.

---

### B-5-6. Aster 연동 섹션 신설 `미결정`

**쟁점:** Lighter·ApeX·EdgeX는 백오피스에 전용 연동 섹션이 있는데(EXT-18~20) Aster만 없다. 365일 바인딩, usdtValue, 웹훅 설정을 관리할 화면이 없다.

**권고:** Aster 전용 섹션을 신설한다. 필요 필드: 레퍼럴 코드·링크, 바인딩 기간, 웹훅 엔드포인트·서명 키, USDT 가격 출처, 보류 레코드 임계치, Builder/에이전트 키.

---

### B-5-7. 5번째 DEX 온보딩 일반화 `미결정` ★중요

**쟁점:** 연동 섹션이 DEX별로 하드코딩되어 있다. 5번째 DEX를 추가하려면 개발이 필요하다. "DEX 온보딩 시스템"이라는 이번 작업의 취지와 정면으로 어긋난다.

**선택지**
- (a) 현행 유지. 신규 DEX는 매번 개발로 대응한다
- (b) 공통 설정 스키마를 설계한다. 정산 주기, 키 구성, 통화, 상태 매핑, 웹훅 유무, 지연 임계치를 데이터로 정의한다
- (c) 중간: 공통 필드는 일반화하고 DEX 고유 예외만 코드로 둔다

**권고:** (c). 완전 일반화는 과설계다. 네 곳의 차이를 분석하면 공통 축이 보인다 — 정산 주기, 키 구성, 제공 금액 종류, 상태 집합, 수집 방식(API/웹훅/CSV). 이것을 레코드 필드로 만들면 5번째 DEX의 개발량이 크게 줄어든다.

**이 결정이 이번 작업의 핵심 가치다.** 기존 문서는 "DEX 4곳을 붙이는 작업"으로 쓰여 있고, 우리가 요청받은 것은 "DEX를 온보딩하는 시스템"이다.

---

### B-5-8. 브로커 콘텐츠 에디터 분리 `미결정`

**쟁점:** 백오피스 Part 4가 브로커 에디터인데 DEX 온보딩과 무관하다. 백오피스 엣지케이스 미해결 #14가 "Part 4가 PRD 트리 밖에 있다"고 스스로 인정한다. 필드 30여 개가 일정과 QA 범위를 키운다.

품질 문제도 있다. BDC-14 결번, BDC-6a CTA 버튼 필드 미정의, BDC-15~17 수락 기준 부실, BDC-8 Founded 길이 제한과 연도 검증 불일치, "Execution Modal" 오타(BCC-4에서 수정 지시).

**권고:** 별도 PRD로 분리한다. 단 Exchange Type에 Brokers 값을 넣는 작업(EXT-6)은 이번 릴리스에 남긴다. 분류 체계의 일부이기 때문이다.

---

### B-5-9. DEX 비활성화의 연쇄 효과 `미결정` ★중요

**쟁점:** NFR-10은 데이터 보존만 정의한다. 실제 영향 범위는 훨씬 넓다.

**확정된 것 (DX-3, EXT-16)**
- 랜딩, 연동 플로우, 모든 셀렉터, Add DEX 목록, SPE 파트너 목록에서 사라진다
- 상세 페이지 URL은 랜딩으로 리다이렉트
- 데이터·콘텐츠·미디어 보존
- 회원 화면에 Inactive 표시
- 딥링크가 있으면 Withdraw 버튼 유지

**제안 단계이거나 미정의**
- **지갑 한도 재계산** (B-3-1과 직결)
- 데이터 수집을 언제까지 계속하는지 (sunset date 제안)
- 진행 중인 소유권 클레임과 Pending 연동 처리
- 예약된 푸시 처리
- 리뷰를 읽기 전용으로 할지
- Featured/Hero 슬롯에 들어 있으면 어떻게 하는지
- 재활성화 시 자동 재등록 여부 (제안: 하지 않음)
- 비활성화 확인 창에 영향 건수(지갑·Processing·클레임·미매칭·Pending)를 표시할지

**권고:** 비활성화를 "콘텐츠 숨김"과 "연동 중단"과 "데이터 수집 중단" 3단계로 분리한다. 한 번의 토글로 모든 일이 일어나면 운영자가 영향을 예측할 수 없다.

---

### B-5-10. 언어 세트 통일 `미결정`

**쟁점:** 에디터 4개(EN·KO·RU·ID), 사이트 15개, 푸시 6개(KO·EN·ZH·RU·VI·ID), SEO 4개, Prelogin Hero 2개. 백오피스 엣지케이스 미해결 #1이 "언어 목록을 한 곳에 정의"하라고 한다.

**문제:** 에디터가 4개 언어만 지원하면 나머지 11개 언어는 영어로 폴백된다. "every supported language"가 몇 개인지 불명확하다.

**권고:** 지원 언어 집합을 한 곳에서 정의하고 모든 화면이 그것을 읽게 한다. 어느 언어를 필수로 할지, 어느 언어는 폴백을 허용할지 정책으로 정한다.

---

### B-5-11. 정합성 교차 검사 확대 `미결정`

**쟁점:** 같은 DEX 수치가 ELC(랜딩), EDC(상세), SPE(계산기), Lighter 요율 테이블, maker/taker에 따로 입력되는데 교차 검사는 EdgeX 헤드라인 1개뿐이다(EXT-20).

NFR 11은 "파트너 요율·파트너 수·단위·입금 수단·혜택 문구가 모든 곳에서 일치해야 하고, 불일치하면 게시 차단"을 요구한다. 그런데 구현 요구사항이 없다.

**권고:** 교차 검사 대상을 명시한다. 최소한 (a) 헤드라인 요율 = 랜딩 카드 요율 = 상세 오퍼 요율, (b) 입금 수단 칩이 랜딩과 상세에서 동일, (c) 파트너 수 표기 = 게시된 레코드 수.

---

### B-5-12. as-at 날짜 UI `미결정`

**쟁점:** 90일 초과 시 경고하는 규칙은 있는데(EXT-15) UI가 정의되지 않았다. 위치, 재확인 주체, 레코드 단위인지 필드 단위인지 모두 미정이다. 경고 대상 필드로 언급된 leverage, market count, fee position은 **입력 필드 자체가 없다.**

**권고:** 레코드 단위로 하고 재확인 버튼을 둔다. 경고 대상 필드를 실제 존재하는 필드로 재정의한다.

## B-6 그룹: 표시 체계

### B-6-1. 상태 칩 마스터 목록과 우선순위 `미결정` ★중요

**쟁점:** 상태 칩이 문서 곳곳에 흩어져 있고 마스터 목록과 우선순위가 없다.

**발견된 상태:** Active / Processing / Unavailable / Standard account, no cashback / Expires in {n} days / Referral expired / Inactive / Ownership verification in progress / This wallet has been unlinked / Ownership verification was unsuccessful / Data delayed

**정해야 할 것**
- 동시에 두 개 이상 해당할 때 우선순위 (예: Aster 만료 임박 + 데이터 지연, Lighter Standard + Processing)
- 행(Linked Accounts)과 카드(선택된 계정)의 표시 매핑
- EdgeX·ApeX 고유 상태(AccountID 미반환, 제한 IP 거래)의 칩
- "Unavailable" 칩 명칭 — 정상 연동한 신규 사용자에게 오해를 준다. "아직 적립 없음" 계열로 바꾸는 안을 권고한다

**권고:** 상태 정의표를 별도로 작성한다. 열: 상태명 / 조건 / 우선순위 / 행 표시 / 카드 표시 / 금액 표시 여부 / 액션 버튼 상태 / DEX 적용 범위.

---

### B-6-2. 요율 하드코딩 제거 `미결정`

**쟁점:** CH-16은 요율 하드코딩을 금지하는데 RT-3/4/5가 "UP TO 90% / 30% / 84%", CH-4가 "0.0280%"를 고정 문구로 적는다.

**권고:** 전부 백오피스 값으로 치환한다. "UP TO {n}%"는 해당 라우트 파트너 중 최고 요율을 계산해서 넣는다.

---

### B-6-3. 금액 표시 규칙 `미결정`

**쟁점:** EC-G8이 제안한다 — 저장은 원래 정밀도의 decimal, 표시는 2자리 반올림(half-up), 합계는 반올림 전 값으로 더한 뒤 반올림. 그래서 행 합계와 0.01 차이가 날 수 있다. 랭킹은 반올림 전 값 기준.

추가 문제: 계산기 일별 금액이 "$0.0333"처럼 소수 4자리인데 다른 금액은 2자리다.

**권고:** 제안값 확정 + 계산기 표시 자릿수 규칙을 별도로 정한다. 0.01 미만 금액의 표시 방법도 정한다.

---

### B-6-4. 시간대 표기 `미결정`

**쟁점:** EC-G9가 "기간·컷오프·만료·캘린더·랭킹 월은 모두 UTC이고 '(UTC)'로 표기"를 제안한다. 백오피스는 기존에 KST를 쓰는 화면이 있다(BEC-G10은 UTC 주 표기 + KST 보조를 제안).

**권고:** 회원 화면은 UTC 통일 + 명시. 백오피스는 UTC 주 표기 + KST 보조. 한국 운영자가 KST로 일한다는 현실을 반영한다.

### B-6-5. Lighter Standard 카피 통일 `미결정`

**쟁점:** 3가지 문구, 상태명 2가지, 버튼 2가지가 혼재한다.

| 위치 | 문구 |

| LK-4, LK-9 | "Upgrade to Plus or Premium on Lighter to earn cashback." |
| EC-LNK-21 | "Switch to Plus or Premium on your Lighter Portfolio page to earn cashback." |
| EC-DEX-5 | "Switch to Plus or Premium on Lighter to earn cashback." |
| 상태명 | "Standard account, no cashback" / "Standard account -- no cashback" |
| 버튼 | "Upgrade on Lighter" / "Continue" |

**권고:** 하나로 통일한다. Lighter 실제 UI 용어(Upgrade인지 Switch인지)를 확인한 뒤 맞춘다.

### B-6-6. 계산기 거래량 범위 `미결정`

**쟁점:** Hub는 DEX 1K~250K, 상세 페이지는 100K~10M. 엣지케이스 미해결 #10도 지적한다.

**권고:** DEX별로 하나의 범위를 정하고 두 화면이 같은 값을 읽게 한다. 백오피스 SPE에서 관리한다.

### B-6-7. Withdraw on {DEX} 노출 조건 `미결정`

**쟁점:** 3곳에서 다르다.
- LK-7: 페이백이 0이면 비활성으로 렌더
- LK-9: Lighter 계정에 페이백이 있으면 렌더, Standard는 비활성
- EC-WD-8: 페이백이 있을 때만 렌더(숨김)

**추가 문제:** LK-9의 "Lighter 계정에 페이백이 있으면"은 **테더맥스가 판정할 수 없다.** Lighter 계정 잔액을 알 방법이 없다.

**권고:** 딥링크가 설정되어 있으면 항상 렌더한다. 버튼은 DEX 사이트를 열기만 하므로 금액과 무관하게 동작한다. 0일 때도 사용자가 DEX에서 확인하고 싶을 수 있다.

**추가 권고 (2026-10-20) — 버튼 라벨 자체를 바꾼다.** 위 권고는 "이 버튼은 출금 버튼이 아니라 이동 버튼"이라는 전제 위에 서 있다. 그렇다면 이름도 맞춰야 한다. 현재 1차 버튼은 `Withdraw on {DEX}`인데 다이얼로그 확정 버튼은 이미 `Go to {DEX}`다 — **같은 동작에 이름이 둘이다.**

| DEX | 현재 | 권고 | 이유 |
|---|---|---|---|
| ApeX | `Withdraw on ApeX` | **`Claim on ApeX`** | 미수령 잔액(`available_balance`)이 실재하고 claim이 필요한 유일한 DEX |
| Lighter / EdgeX / Aster | `Withdraw on {DEX}` | **`Go to {DEX}`** | 이미 사용자 계정에 입금 완료. 버튼은 이동만 한다 |

**특히 EdgeX에서 `Withdraw`는 위험하다.** 눌러서 가봐도 페이백 항목이 보이지 않는다(증거금에 혼입, D5). 기대와 실제의 간극을 단어가 최대로 벌린다.

### B-7-2. Aster 바인딩 잔여 일수를 언제든 읽을 수 있는가 `파트너대기` ★중요

**쟁점:** 사용자에게 "만료까지 n일"을 보여주려면 `bindExpireTime`을 **아무 때나 조회**할 수 있어야 합니다.

테더맥스에서는 지갑과 테더맥스 계정의 연결이 바뀔 수 있습니다 — 연동 해제 후 재연동, 소유권 분쟁으로 다른 계정에 이전. 바인딩 자체는 Aster 쪽에 있어 영향받지 않지만, **테더맥스가 만료일을 조회로 받지 못하면 재연동 시 정보를 잃습니다.**

| Aster가 매 조회마다 반환 | 바인딩 시점에만 전달 |
|---|---|
| 항상 정확한 잔여 일수 표시 | 우리가 받은 시점의 값만 보유 |
| 계정 이동이 문제되지 않음 | 계정이 바뀌면 만료 정보 소실 → **우리 DB 최초 등록일 기준으로 세야 하는데 실제 바인딩일이 아님** |
| 테더맥스 연동 전에 바인딩한 지갑도 정확 | 그런 지갑은 **처음부터 틀림** |

**Aster PM 회신에 `registration date`는 있지만 바인딩 만료는 없습니다.** 확인이 필요합니다.

**대비책 (Aster가 매 조회 반환을 못 할 경우)**
- 바인딩 시각을 받은 시점에 **이력 테이블로 영구 기록**하고, 지갑이 계정 간 이동해도 지갑 기준으로 조회
- 최초 바인딩 시각을 모르는 지갑은 **잔여 일수를 표시하지 않음** (틀린 숫자보다 안 보여주는 편이 낫습니다)

이 컬럼들은 **테더맥스가 보유하고 지급할 금액**입니다. DEX 금액을 섞으면 CS와 재무가 "지급해야 할 돈"으로 잘못 읽습니다.

**권고:** 기존 4개는 CEX 전용으로 두고 `DEX 누적 페이백(USDT)` 컬럼을 별도 추가. 상세는 [08_어드민_화면별_DEX_반영사항.md](08_어드민_화면별_DEX_반영사항.md) 2-1.

### B-7-6. UID 리스트의 `받아간 페이백` 컬럼 의미 충돌 `미결정`

**쟁점:** CEX에서는 "사용자가 테더맥스에서 출금해 간 금액"인데, DEX에서는 "DEX가 사용자에게 지급한 금액"입니다. 같은 컬럼에 의미가 다른 값이 들어갑니다.

`남은 페이백`은 DEX에 존재하지 않으므로 `-` 처리가 확정적입니다. 상단 합계도 분리가 필요합니다.

### ~~B-7-7. 소유 확인 심사 — 동영상 전환과 자동 실패 시간~~ `A-16으로 대체됨`

> **결론: 이번 범위에서 제외.** 동영상 플레이어 신설도, 10분 자동 실패 재검토도, 거절 사유 6종 확정도 **불필요합니다.** 아래는 보류 전 기록입니다.

**쟁점 1:** 현재 소유 확인 첨부파일은 **이미지**입니다. DEX는 **MP4/MOV 최대 100MB 동영상**이라 심사 화면에 플레이어가 필요합니다. 배속·구간 이동이 없으면 5분 목표를 지킬 수 없습니다.

**쟁점 2:** 기존 정책에 **10분 무응답 시 자동 실패**가 있습니다. DEX PRD에는 이 규칙이 없고 "약 5분 목표"만 있습니다. **동영상 심사는 이미지보다 오래 걸립니다.** 10분을 그대로 적용하면 실패율이 올라갑니다.

**추가:** 거절 사유 6종을 확정해야 합니다. 사용자에게 그대로 노출됩니다.

### B-7-8. 비회원 DEX 조회 기록을 어디에 둘지 `미결정`

**쟁점:** PRD는 기존 `비회원 수동 페이백` 화면(CEX 출금 처리 모듈)에 DEX 조회 기록을 섞도록 설계했습니다. 그런데 그 화면의 컬럼(`신청 페이백 금액`, `합산 신청 금액`, `페이백 출금시각`, `처리 여부`)이 DEX 행에서 의미가 없습니다.

**권고:** 별도 화면으로 분리하거나, 같은 화면에 두되 DEX 행은 **조회 기록 전용**임을 명확히 하고 출금 컬럼을 `-`로 둡니다. 운영자가 "처리"할 대상이 아닙니다.

### B-7-9. 거래소 래퍼럴 관리에 DEX 행 추가 여부 `미결정`

**쟁점:** 이 화면의 `마진율`은 두 곳에 쓰입니다 — 페이백 계산, 그리고 초대 리워드 계산.

**권고:** DEX 행을 추가하고 **마진율 0**으로 둡니다. 기존 규칙("거래소 margin이 0이면 초대 리워드 미발생")에 따라 **별도 차단 로직 없이 자동으로 0**이 됩니다.

**단 명시해야 할 것:** DEX 행의 마진율은 **초대 리워드 계산에만** 쓰고 **페이백 계산에는 쓰지 않습니다.** DEX 페이백은 DEX가 산정한 값을 그대로 받기 때문입니다.

### B-7-10. 거래소 가이드의 KYC 섹션 `미결정`

**쟁점:** 현재 거래소 가이드 상세는 KYC 중심 구조입니다 — "거래소 어떻게 가입해요?", "KYC 인증 버튼 찾기", "신분증 인증 / 카메라 촬영 / 완료 확인".

**DEX는 KYC가 없습니다.** 이 섹션 전체가 무의미합니다.

**권고:** DEX에서는 KYC 섹션을 숨기고 `DEX 계정 생성 가이드`를 신설합니다. DEX 가입은 "지갑 설치 → 레퍼럴 링크 접속 → 지갑 연결 또는 이메일 가입"이라 단계가 완전히 다릅니다.

`UID 연동 가이드`는 `지갑 주소 찾기 가이드`로 대체합니다. ~~`소유 확인 가이드`는 3단계 고정(16:9 이미지 3장)으로 바꿉니다~~ → **A-16으로 DEX에는 만들지 않습니다.** `EDC-26`도 불필요합니다. **DEX의 필수 가이드는 `지갑 주소 찾기` 1종입니다.**

특히 **D1(수익 배분 모델)과 D4(표시 금액)는 사업 영향**이 있어 승인 주체를 명확히 해야 합니다.

### B-7-23. 테더맥스 커미션 수익의 회수 프로세스가 정의되어 있지 않다 `미결정` ★중요

**쟁점:** DEX는 트레이더 몫과 테더맥스 몫을 **각각 직접** 지급합니다. 테더맥스 몫은 **각 DEX에 개설한 테더맥스 명의 계정으로** 들어옵니다.

```
테더맥스 수익 ─┬─▶ 테더맥스 EdgeX 선물계정    (USDC, 매일 자동)
               ├─▶ 테더맥스 Lighter 메인계정  (USDC, 매주 월요일 L2 이체)
               ├─▶ 테더맥스 ApeX 계정         (USDT, 시간당)
               └─▶ 테더맥스 Aster 계정        (수수료 자산, 일 1회)
```

**수익이 4곳에 분산되어 쌓이는데, 회수 절차가 어느 문서에도 없습니다.** 정의가 필요한 항목:

| 항목 | 내용 |
|---|---|
| 회수 주기·담당 | 누가 언제 각 DEX에서 트레저리로 출금하는가 |
| 계정 권한 | 파트너 API 키는 읽기 전용이므로 **출금은 수동**입니다. 계정 접근 권한자와 승인 절차 |
| 환전 정책 | **Aster는 수수료 자산(ETH·BTC·BNB 등)으로 들어옵니다.** 언제 무엇으로 환전할지 |
| 잔액 모니터링 | 입금 누락·금액 불일치를 발견하는 경로 |
| 회계 반영 | 월 명세서와 실제 수령액 대조 (EdgeX·ApeX·Aster는 월 명세서 제공) |

**선행 조건:** EdgeX 메인 계정 등록이 **아직 미이행**입니다([09](09_파트너_커뮤니케이션_기록.md) 2번). 등록 전까지는 커미션이 쌓일 계좌 자체가 없습니다. ApeX도 커미션 수령용 지갑 주소를 요청받은 상태입니다(09, Doris 09-21).

**영향 범위:** 재무·운영. 프론트/백오피스 작업은 아니지만 **출시 전에 정해져 있어야 수익이 잠기지 않습니다.**

### B-7-24. EdgeX·ApeX·Aster는 지급 사실을 독립 검증할 수 없다 `확인 필요`

**쟁점:** 지급 참조 수단이 DEX마다 다릅니다.

| DEX | 지급 참조 | 독립 검증 |
|---|---|---|
| **Lighter** | **L2 tx hash** | ✅ 온체인에서 직접 확인 가능 |
| EdgeX | `payoutId` + `transferId` + `collateralTransactionId` | ❌ 전부 EdgeX 내부 ID |
| ApeX | 없음 (L2 internal transfer, Doris 09-24) | ❌ |
| Aster | `tranId` 요청 중 | ❌ |

**Lighter 외 3곳은 "DEX가 보냈다고 한 것을 DEX가 준 ID로 되묻는" 구조입니다.** 고객 계정 쪽에서 교차 검증할 방법이 없습니다(고객 자산 원장은 받지 않으며, 받아서도 안 됩니다 — 개인정보 미수집 원칙).

**문제가 되는 경우는 하나입니다 — 고객이 "안 받았다"고 클레임할 때.** 테더맥스가 제시할 수 있는 것은 DEX가 준 참조 ID뿐이고, 결국 DEX에 확인 요청을 넣어야 합니다.

**대응 방향:** 고객 본인은 자기 DEX 거래내역에서 확인할 수 있습니다(EdgeX는 `TRANSFER_IN` 항목). **CS 스크립트를 "{DEX} 거래내역에서 {시각}의 입금 항목을 확인해 주세요"로 설계**하면 대부분 해소됩니다. 딥링크 목적지 선정(B-7-22)과 함께 처리합니다.
