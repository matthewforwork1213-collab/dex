### A-1의 귀결 — 매칭 제약은 그대로 적용됩니다

```
실제 출금액 = A + MIN(B, A)       A = 페이백, B = 이벤트 리워드
```
**DEX 페이백(A)이 0이면 이벤트 리워드도 출금할 수 없습니다.** (MAX-18 표 #4)
DEX에 이벤트 리워드를 주더라도 이 제약은 동일하게 걸립니다.

### A-2의 귀결 — 수정 대상 문구 4곳

| 위치 | 현재 문구 | 조치 |
|---|---|---|
| 파트너 허브 Linked Accounts | *"DEX wallets earn you no Invite Rewards."* | **삭제** |
| 파트너 허브 T&C | *"Invite Rewards are only earned on centralised exchange cashback. Sub-accounts trading on DEXs do not generate Invite Rewards."* | **삭제** |
| 초대친구 T&C | *"Trading on DEXs such as Lighter, ApeX, EdgeX and Aster does not earn Invitation Rewards"* | **삭제** |
| 초대 리워드 출금 모달 | *"can only be withdrawn to a linked centralised exchange UID"* + CEX UID만 노출 | **문구 삭제 + DEX 지갑을 목록에 추가** (동작 변경) |

※ **하위의 하위 제외 로직**은 거래 커미션 쪽 이야기이며 초대 리워드와 무관합니다.
초대 리워드의 하위 제외는 **테더맥스 내부 로직**이고, **DEX도 기존과 동일**하게 따라갑니다. (Q4)

### E-8 — 비율 체계

```
커미션율, 페이백률   분모 = 유저가 낸 수수료
마진율               분모 = 커미션

예) 커미션율 60%, 페이백률 54%
    마진 = 6%p (수수료 기준)
    마진율 = 6 / 60 = 10%          ← 서버에 저장되는 값
    커미션율 = 페이백률 ÷ (1 − 마진율) = 54 ÷ 0.9 = 60%   ← 역산
```

| Q1 | **DEX 4곳의 커미션율은 미정.** 허브 비교표의 Lighter 20% / ApeX 30% / EdgeX 30% / Aster 20% 는 **페이백률**(사용자 노출값)이며, 커미션율과 마진율은 추후 확정 |

### 귀결 — Wallet B 소요액

```
Wallet B 필요액 = Σ(고객 출금액) + Σ(가스비)
```
가스비가 건당 2~5 USDT라면, **10 USDT 출금 1건당 테더맥스 비용은 12~15 USDT**입니다.
페이백 100%를 유저에게 지급하는 구조에서 **가스비는 전액 손실**입니다.

→ **A-3(네트워크 리서치)의 핵심 평가 기준이 됩니다.**
리서치 담당자에게 **"건당 가스비 × 예상 출금 건수 = 월 손실액"** 산정을 요청해야 합니다.

**결정 (Q2):** **일단 가능한 것으로 전제하고 진행한다.**

### ★ M-3. 빙고 Batch 시각 ↔ Aster 09:00

> **REQ-036**: 빙고 Batch는 하루 1회 **전 거래소 공통 고정 시각**, Bitget 페이백 배치 이후 (시각 미정 `#BATCH`)

Aster는 **00:00 UTC 산정 → 09:00 이후 공개**입니다.
빙고 Batch가 09:00 UTC보다 빠르면 **Aster 페이백이 매일 하루씩 밀리고, 연속 판정도 같이 밀립니다.**

→ 빙고 Batch 시각 조건에 **"Aster 09:00 UTC 이후"** 를 추가해야 합니다.

## 2026-10-22 신규 발견 — DEX 마진율이 상충합니다 🔴

백오피스 프로토타입에 `거래소 래퍼럴 관리`를 추가하면서 드러났습니다. **08 문서 10-2의 권장안이 V2에서 더 이상 성립하지 않습니다.**

### 무엇이 깨졌나

08 문서 10-2는 **(a) DEX 행을 추가하고 마진율 0** 을 권장했고 근거는 이랬습니다.

> 거래소 margin rate가 0이면 사용자·파트너 모두 초대 리워드가 생성되지 않습니다. → 별도 차단 로직 불필요

이 권장은 **"DEX는 초대 리워드가 발생하지 않는다"** 를 전제로 합니다. **V1 전제입니다.**

| 결정 | 내용 | 시점 |
|---|---|---|
| A-19 | **DEX 초대에도 초대 리워드가 발생한다. DEX 행에도 실제 누적 금액을 표시한다** | 2026-10-20 |
| A-2 (사용자 답변) | DEX 초대 리워드 **O** | 2026-10-22 |

→ **마진율 0은 이제 정책을 자동으로 지키는 장치가 아니라, 정책과 정면으로 어긋나는 값입니다.**

### 필드 하나, 공식 둘, 반대 동작

마진율은 두 공식에 들어가는데 DEX는 둘에서 서로 반대로 동작해야 합니다.

| 공식 | DEX 처리 | 이유 |
|---|---|---|
| `페이백 = 총 커미션 × (1 − 마진율)` | **완전히 무시해야 함** | 테더맥스가 DEX 페이백을 계산하지 않음. DEX가 산정한 금액을 **그대로** 받음 |
| `초대 리워드 = 하위 출금액 × 거래소 마진 × 리워드 비율` | **사용해야 하고 0이 아니어야 함** | 0이면 A-19의 "실제 누적 금액"이 항상 0 |

> **구현 요구사항** — 이 필드를 **경로별로 분리**해야 합니다. 페이백 경로에서는 DEX 마진율을 무시하고, 초대 리워드 경로에서만 사용합니다. 스펙에 명시하지 않으면 DEX 페이백이 조용히 공식 결과값으로 바뀝니다.

### V2에서 입력값 하나가 이미 바뀌었습니다

| 입력값 | V1 | **V2** |
|---|---|---|
| 하위 계정 출금액 | DEX는 테더맥스 출금이 없어 **0** | **실재하는 숫자** — DEX도 테더맥스를 경유해 출금 |
| 거래소 마진 | 0으로 둘 예정 | **미정 — 아래 참조** |

08 문서의 "DEX는 출금액이 0이라 자동으로 0" 서술도 함께 무효입니다.

### 🔴 막혀 있는 상업 판단

| | |
|---|---|
| **V2 전제** | 커미션 **100%를 트레이더에게** 지급 → 테더맥스에 DEX 마진이 **남지 않음** |

## 2026-10-22 — 페이백 챌린지 DEX 미반영 확정 (R-10)

V2 재판정에서 **부분 → O** 로 올렸던 것을 **X** 로 되돌립니다. 부스트에 이어 두 번째 되돌림입니다.

### V1의 어중간한 상태가 함께 사라집니다

| | 게이지 | 수령 |
|---|---|---|
| **V1 (부분)** | DEX 페이백도 참 | **DEX 수령 불가** |
| V2 재판정 (O) | 참 | 가능 |
| **확정 (X)** | **안 참** | **안 뜸** |

> *"게이지는 차는데 받을 수는 없다"* 는 **사용자가 이유를 알 수 없는 상태**였습니다. 이제 챌린지는 CEX 전용 하나의 규칙입니다.

### 🔴 하나 남은 결정 — 게이지 합계에 DEX를 셀 것인가

화면은 **「페이백」** 이라고 말하고, **홈의 총 페이백에는 DEX가 들어갑니다.**

```
홈      총 페이백 잔액   1,240.00 USDT   ← CEX + DEX
챌린지   Level 1        980 / 1,000 USDT  ← CEX만?
```

양쪽에서 거래하는 회원은 **두 숫자가 어긋나는 것을 보고도 이유를 알 수 없습니다.**

| 안 | 내용 |
|---|---|
| **A (권고)** | 게이지에서 DEX를 빼고 **화면에 「CEX 거래 기준」 명시** |
| B | 게이지는 DEX까지 세되 수령만 CEX — **방금 없앤 상태로 되돌아갑니다** |

> **제외하는 것만으로는 해결되지 않습니다.** 문구를 쓰지 않으면 A도 B만큼 혼란스럽습니다.

### 레퍼런스

| 출처 | 내용 |
|---|---|
| **CoinGecko · CoinMarketCap** | 거래소 목록을 **spot / derivatives / DEX** 세 범주로 나눠 제공합니다. **CEX와 DEX를 다른 종류로 가르는 것은 암호화폐 제품의 관행**이고 우리가 발명한 구분이 아닙니다 |
| **DXC Halstack 디자인 시스템** | 그룹 옵션과 전체 선택을 **묶어서** 다룹니다 — 범주형 데이터에서 반복 클릭을 줄이는 용도로 명시 |
| **UXPin 드롭다운 패턴 가이드** | 전체 선택 옵션을 드롭다운 안에 두는 것이 일반적이라고 기술 |
| **Shopify Polaris · Helsinki Design System** | select 컴포넌트가 **그룹 라벨**을 정식 지원 (다만 그룹 단위 선택 컨트롤은 별도 아님) |

→ **그룹 헤더 + 상단 범위 선택**은 디자인 시스템이 각각 지원하는 두 요소를 합친 것입니다. 새 발명이 아닙니다.

### 적용

드롭다운 상단에 범위 선택 3개를 붙였습니다. **CEX·DEX 두 그룹이 다 있는 묶음에만** 붙습니다.

```
┌──────────────────────────────┐
│ [ 전체 ] [ CEX 전체 ] [ DEX 전체 ] │  ← 범위 선택 (신규)
├──────────────────────────────┤
│ CEX                           │  ← 그룹 헤더
│   Bitget · Bybit · OKX · …    │
│ DEX                           │
│   Lighter · ApeX · EdgeX · …  │
└──────────────────────────────┘
```

| 묶음 | 범위 선택 | 이유 |
|---|---|---|
| `EXALL` · `EXPUSH` · `ACCT` | **있음** | CEX·DEX 두 그룹이 다 있습니다 |
| `EXCEX` · `EXDEX` · `EXTYPE` · 나머지 12종 | 없음 | 그룹이 하나뿐이라 범위를 고를 것이 없습니다 |

**선택하면 트리거에 `DEX 전체` 로 적힙니다** — `DEX` 로만 적으면 트리거만 보고는 무슨 뜻인지 알 수 없습니다.

**점검 자동화** — `_점검_범위선택.js`. 범위 선택이 붙은 드롭다운을 **열고 → `DEX 전체`를 누르고 → 트리거 값이 바뀌는지**까지 한·영 양쪽으로 확인합니다. 현재 **30건 통과**(한 15 · 영 15), 범위 선택이 없어야 할 42건도 없는 것으로 확인.

> **배운 것 — 사용자가 올린 시안을 제 권고로 덮을 때는 더 조심해야 합니다.** 이번엔 *"칩이 헤더와 중복"* 이라는 표면만 보고, **단일 선택이라 DEX 전체를 고를 수단이 사라진다**는 것을 못 봤습니다.

## 2026-10-22 — 🔧 집계 일자 7일 확장, 위치가 틀렸습니다 (R-22)

**질문** — *"이거 거래소 생성/수정에서 오늘/1일전/2일전 이런 거 있었는데, 라이터 때문에 7일 전 만든다지 않았어요? 전체 내역에서 잘못 넣은 거예요?"*

**거래소 생성·수정이 맞습니다. 제가 전체 내역에 잘못 붙였습니다.**

### 왜 틀렸나

문서 `7-3`이 **"어드민 정산 관리의 집계 일자 드롭다운"** 이라고만 적었고, 저는 그것을 `페이백 > 전체 내역` 의 조회 필터로 해석했습니다.

**실물 거래소 추가 폼을 보니 아니었습니다.**

```
집계 시작(UTC)*   [ 선택 ▾ ] [ -- --:-- ]   ← 이 드롭다운이 상대 일자
집계 종료(UTC)*   [ 선택 ▾ ] [ -- --:-- ]
업데이트(UTC)*              [ -- --:-- ]
```

**결정적 근거는 7-3의 표입니다.**

| 거래소 | 필요 범위 |
|---|---|
| **Lighter** | **7일** |
| ApeX · EdgeX · Aster | 1일 |

→ **거래소마다 필요 범위가 다릅니다.** 조회 필터는 거래소별로 다를 수 없습니다. **거래소별 설정**이어야만 이 표가 성립합니다.

### 조치

| 화면 | 처리 |
|---|---|
| `거래소 > 생성·수정` | **집계 시작·종료에 상대 일자 드롭다운** 명시 + **7일까지 확장** + **`주기`(일/주) · `요일` 필드 신설** |
| `페이백 > 전체 내역` | **조회 필터로 정정.** 7일 확장 대상이 **아님**을 주석에 명시 |
| `4_백오피스 7-3` | **위치 특정** — 거래소 생성·수정 폼이라고 못 박고, 왜 전체 내역이 아닌지 근거를 적었습니다 |

> **둘 다 필요한 것이 아니라 설정 쪽 하나입니다.** 전체 내역의 `집계 일자`는 그냥 조회 범위이고 Lighter와 무관합니다.
>
> **`주기`·`요일` 필드가 핵심입니다.** 상대 일자를 7일로 늘리는 것만으로는 *"일주일에 한 번 집계한다"* 가 표현되지 않습니다. 둘이 같이 들어가야 **Lighter를 등록할 수 있습니다.**

```
회원별 사용량   조회 화면 없음     ← 값이 아니라 내 메모
예외 처리      미정의            ← 값이 아니라 내 메모
```

**입력칸 안에 "없음"이라고 적어 둔 것**이라 운영자가 보는 화면으로 읽히지 않습니다. `V1 문구` 때와 같은 실수입니다.

→ **진짜 화면으로 다시 만들었습니다.**

| 영역 | 내용 |
|---|---|
| 한도 규칙 | 산식 · 현재 한도 `12 = 4 DEX × 3` |
| **회원별 사용량 표** | 회원 번호 · 이메일 · **Lighter / ApeX / EdgeX / Aster 각각 몇 개** · `사용 / 한도` |

**맨 오른쪽 `12 / 12` 가 핵심입니다.** 고객센터가 *"왜 지갑이 연동 안 되냐"* 는 문의를 받았을 때 **답을 볼 수 있는 유일한 자리**입니다. 지금은 그 조회가 불가능합니다.

### 한도가 왜 문제인가

```
한도 = 활성 DEX 수 × 3    →  DEX 4곳이면 12개
```

**지금은 코드 안 상수입니다.** → **5번째 DEX를 게시하면 모든 회원의 한도가 12에서 15로 말없이 올라가고 아무도 통보받지 못합니다.**

**산식이 답하지 못하는 것 셋 — 전부 고객센터로 떨어집니다**

| # | |
|---|---|
| 1 | DEX를 **비활성화하면 한도가 내려갑니다.** 이미 넘긴 회원은? 초과분 적립이 멈추나요? |
| 2 | **지갑을 해제하면 자리가 돌아오나요?** 누적으로 세나요? |

> **같은 개수가 이미 두 곳에 나옵니다** — 회원 리스트의 `3 / 2`, 회원 연동 계정 모달의 그룹 헤더. 그 둘은 UID와 지갑을 함께 읽고, **DEX별로 쪼개는 건 이 화면뿐**입니다. 한도를 계산하는 기준이 그것이기 때문입니다.
