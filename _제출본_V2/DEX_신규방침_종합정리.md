# 1. 왜 바꾸는가

기존 구조는 **DEX가 트레이더에게 페이백을 직접 지급**하고, 테더맥스는 그것을 조회해서 보여주기만 했습니다. 이 구조에서 세 가지 문제가 있었습니다.

| # | 문제 |
|---|---|
| 1 | **이중 지급 위험** — DEX가 이미 유저에게 줬는데 테더맥스가 또 줄 수 없음 |
| 2 | **자금 통제점이 없음** — 테더맥스를 거치지 않으니 흐름을 끝까지 추적할 수 없음 |
| 3 | **CEX와 구조가 다름** — 파트너마다 다른 데이터 모양을 따로 처리해야 함 |

신규 구조는 이 셋을 한 번에 해결합니다. **커미션을 전액 테더맥스가 받고, 테더맥스가 지급합니다.**

---

# 2. 한 장 요약

> ## DEX가 고객에게 직접 주던 구조를 폐기합니다.
> ## 커미션 100%를 테더맥스가 받아, 테더맥스가 고객에게 지급합니다.
> ## 결과적으로 **CEX와 같은 구조**가 됩니다.

### 전제조건 2개 — 이것이 연동의 전부

| # | 조건 | 어디서 |
|---|---|---|
| **1** | 트레이더 캐시백 비율을 **0%**로 설정 (자동 지급 차단) | DEX 백오피스 |
| **2** | 커미션 **100%를 테더맥스 Wallet A**로 전액 라우팅 | DEX 정산 설정 |

**둘 다 합의되기 전까지 나머지 모든 내용은 잠정입니다.** 4개 요청서 모두 이 장에만 빨간색을 쓰고, Aster 요청서는 *"이 슬라이드만 빨간색을 쓴다. 표지처럼 읽어라"*라고 명시합니다.

### 바뀌는 것 한눈에

| | 기존 | 신규 |
|---|---|---|
| 페이백 지급 주체 | DEX | **테더맥스** |
| 테더맥스 역할 | 조회·표시만 | **수취 · 계산 · 지급 전체** |
| 출금 장소 | DEX 사이트 | **테더맥스 앱·웹** |
| 최소 출금액 | 없음 | **10 USDT** |
| 적립액 성격 | 영수증 (출금해도 안 줄어듦) | **통장 잔고 (출금하면 줄어듦)** |
| **이벤트 리워드** | **전면 배제** | **사용 가능** |
| 가스비 | 해당 없음 | **테더맥스 부담** |

# 3. 구조 — 지갑 2개와 7단계

## 3-1. 지갑 2개

```
          4개 DEX
             │  커미션 100%
             ▼
    ┌──────────────────┐
    │   Wallet A       │   커미션 정산 지갑
    │   (Commission)   │   4개 DEX의 커미션 전액 수취
    └────────┬─────────┘
             │  ★ 수동 리밸런싱 1일 1회
             │     전일 예상 지급액 + 가스비만 이동
             ▼
    ┌──────────────────┐
    │   Wallet B       │   페이백 전용 지갑
    │   (Cashback-Only)│   고객 대면 · 가스비 선충전
    └────────┬─────────┘
             │  자동 지급 (가스비 동반)
             ▼
       고객 EVM 지갑
```

**A와 B는 절대 같은 풀이 아닙니다.** 요청서 원문: *"Wallet A holds settlement inbound, Wallet B holds trader-facing cashback — never the same pool."*

## 3-2. 7단계 플로우

| # | 주체 | 내용 | 자동/수동 |
|---|---|---|---|
| 1 | 고객 | 테더맥스 레퍼럴로 DEX 가입 — **지갑 주소로 식별** | — |
| 2 | DEX | 0% 설정 + 커미션 100%를 Wallet A로 | 자동 |
| 3 | API | 전일 커미션 원장 수신 → 시스템 전체 갱신 (**D+1**) | 자동 |
| 4 | 테더맥스 | **A → B 리밸런싱** (전일 예상 지급액 + 가스비) | **수동 · 1일 1회** |
| 5 | 고객 | 잔액 확인 → **10 USDT 이상**이면 출금 신청 | 수동 (1회 클릭) |
| 6 | 테더맥스 | Wallet B → 고객 EVM 지갑 송금 (**가스비 포함**) | 자동 |
| 7 | API | 출금 전후 변동값을 **6개 화면에 반영** | 자동 |

**수동은 4번 하나뿐입니다.** 나머지는 전부 자동입니다.

# 4. 원장 API

## 4-1. 공통 스키마 — 필수 5 + 선택 3

4개 파트너 **전부 같은 스키마**로 요청합니다. 전일 24시간 집계, **D+1 지정 시각** 노출.

### 필수 5 — 없으면 연동 불가

| # | 필드 | 설명 |
|---|---|---|
| 1 | `wallet address` | **DEX는 UID가 없으므로 지갑 주소가 유일한 식별자** |
| 2 | `trade_type` | `spot` / `perp` 구분 — 두 거래량을 분리 집계 |
| 3 | `fee_paid` | 트레이더가 그 거래에서 실제 지불한 수수료 |
| 4 | `commission` | 그 거래에서 테더맥스에 지급된 커미션 |
| 5 | `referral_code` | 테더맥스 귀속 거래임을 검증 |

### 선택 3 — 있으면 좋은 것

| # | 필드 | 용도 | 중요도 |
|---|---|---|---|
| 1 | `UID / AID` | CS 교차확인 · 중복·누락 추적 | 보통 |
| 2 | **`symbol` · `volume`** | **글로벌리그 · 맥스보드 작동에 필수** | **높음 — 협상 항목** |
| 3 | `network (EVM)` | Wallet B가 어느 체인으로 지급할지 결정 | 높음 |

> **선택 2번이 이벤트 기능의 생사를 가릅니다.** Aster 요청서는 *"글로벌리그·맥스보드가 범위에 들어오면 이 항목을 필수로 승격할 수 있다"*고 명시했습니다.

### 응답 예시

```json
{
  "date": "2026-10-19",
  "wallet": "0x##...##",
  "trade_type": "perp",
  "fee_paid": ##.##,
  "commission": ##.##,
  "referral_code": "TM####"
}
```

`##`은 플레이스홀더이며 최종 합의 후 실측값으로 교체합니다.

## 4-2. 엔드포인트 — EdgeX 요청서에만 구체안이 있음

```
GET  /v1/referral/code/{user_id}
GET  /v1/trade/fees/{user_id}?window=24h
GET  /v1/ledger/entries/{user_id}?type=fee
POST /v1/cashback/credit       ← 테더맥스가 쓰기
POST /v1/cashback/revoke
```

**원칙: 읽기는 조회만, 쓰기는 페이백만, 출금 권한은 절대 없음.**

## 4-3. 안전장치 3가지

| 장치 | 내용 |
|---|---|
| **멱등성** | 같은 `trade_id`는 단 1회만 credit. 재시도 시 거래소가 중복 제거 → **이중 지급 원천 차단** |
| **취소** | 24시간 내 `/cashback/revoke`로 원장 마감 전 정정 |
| **권한 분리** | Wallet A(수취)와 Wallet B(지급)를 분리. 출금 권한 없음 |

## 4-4. 갱신 타임라인

```
 D일          거래 발생 · 수수료 부과
   │
   ▼
 24h 집계     DEX가 하루치를 롤업
   │
   ▼
 D+1 지정시각  원장 노출 (00:00 UTC 기준 / Aster는 09:00 공개 이후)
   │
   ▼
 테더맥스     수신 → 전 화면 갱신 → 리밸런싱
```

폴링은 **30초 주기**이며, EdgeX 선택 API Phase 1에서 **webhook으로 대체**하는 로드맵이 있습니다.

## 5-1. 고객이 하는 일은 클릭 한 번

| 항목 | 내용 |
|---|---|
| 최소 출금액 | **10 USDT** — 미만이면 **요청 자체를 화면에서 숨김** |

```
                                      ▼
                            온체인 EVM 전송 + tx 로그
                                      ▼

                                      ▼
                        6개 화면에 변동값 즉시 반영
```

# 6. 운영 리스크와 **아직 비어 있는 숫자들**

## 6-1. 리스크 4가지와 대응

| # | 리스크 | 대응 |
|---|---|---|
| 1 | B지갑 잔액 부족 → 지급 지연 | 전일 예상 + 버퍼 비율 산정, 부족 시 알림 |
| 2 | **네트워크별 가스비 변동** | 지속 폴링 → 이체 금액에 포함, 부족 시 보충 |
| 3 | **B지갑 유휴 잔액 과다** | 최소 필요분만 이체 — 유휴 현금 최소화 |
| 4 | 이벤트성 급증 (예: Aster 만료) | 원장 이력에서 예상치 재계산, 한계 초과 시 알림 |

> ⚠️ **2번과 3번은 서로 반대 방향입니다.** 가스비 변동에 대비하려면 여유를 둬야 하는데, 유휴 자금을 줄이려면 최소만 넣어야 합니다. **그 균형점이 아래 버퍼 비율인데 미정입니다.**

## 6-2. 미정 숫자 4개 — 전부 플레이스홀더

방침 공표 6장 — *"Phase 3에서 확정할 사전 예시값"*

| 항목 | 현재 값 | 의미 |
|---|---|---|
| 일일 A→B 이체 목표 | **`## USDT`** | 하루에 얼마를 옮길 것인가 |
| 버퍼 정책 | 일일 예상의 **`##배`** | 여유를 얼마나 둘 것인가 |
| **가스비 캐시** | **`##일치`** 네트워크 수수료 | 며칠치 가스비를 쟁여둘 것인가 |
| 첫날 상한 | **`##명`** | 오픈 첫날 몇 명까지 받을 것인가 |

## 6-3. 가스비 — 리스크가 두 갈래입니다

| 구분 | 내용 |
|---|---|
| **운영 리스크** | 미리 넣어둔 가스비가 모자라면 **출금이 멈춤** |
| **비용 리스크** | 가스비를 **테더맥스가 전액 부담** — 그냥 나가는 돈 |

### 왜 새로 생긴 부담인가

```
기존 구조    테더맥스가 송금 안 함        → 가스비 항목 자체가 없음
CEX         거래소 내부이체             → 온체인 수수료 없음
신규 DEX    출금 1건마다 온체인 EVM 전송 → 건당 실비 발생 ★
```

### 최소 출금액 10 USDT와의 긴장

```
출금 10 USDT  −  가스비 2~5 USDT  =  테더맥스 실부담률 20~50%
                      ↑ 네트워크 혼잡 시
```

CEX에서는 내부이체라 10 USDT가 합리적이었지만, **온체인 송금에서는 같은 숫자가 다른 의미**입니다. 소액 출금이 몰리면 가스비가 지급액의 상당 비율을 먹습니다.

**현재 문서 어디에도 대응책이 없습니다** — 최소 출금액 상향 / 저가 체인 유도 / 건당 가스비 상한 중 어느 것도 정해지지 않았습니다. `첫날 상한 ##명` 항목이 있는 걸 보면 인지는 하고 있는 것으로 보입니다.

# 7. DEX별 협상 항목

## 7-1. Aster — 4개 항목 · **가장 급함**

| # | Aster 현재 | 테더맥스 요청 |
|---|---|---|
| 1 | 일 1회 (00:00 산정 → 09:00 공개) | **09:00 이후로 갱신 타이밍 합의** |
| 2 | 수수료 자산 그대로 지급 (USDT·ETH·BTC 가변) | **USDT 환산값을 Aster가 계산해 제공** — 테더맥스는 그대로 사용 |
| 3 | **레퍼럴 365일 만료 · 갱신 방식 미정** | **갱신 규칙 확정.** 미합의 시 **12개월 후 전 연동자 지급 중단** |
| 4 | 외부에서 지급을 검증할 방법이 없음 | **검증값 제공** — 내부 CS·교차확인용 |

> **3번이 TOP PRIORITY입니다.** 요청서 원문: *"Row 3 is the loudest item. Until the renewal rule is agreed, payouts will lapse in 12 months."*

## 7-2. ApeX — 5개 항목

| # | ApeX 현재 | 테더맥스 요청 |
|---|---|---|
| 1 | **시간당 배치 기록** | **일 단위(D+1) 집계로 롤업 가능한지 확인** |
| 2 | USDT · Perp 계정 | 환산 불필요, 원장 금액 그대로 |
| 3 | **Rewards Center에서 Claim 필수** (4곳 중 유일) | 신규 연동자는 0%라 적립 자체가 없음 → **신규 가입자 중심으로 논의** |
| 4 | **기존 미수령 잔액이 존재할 수 있음** | **별도 안건으로 분리 결정** |
| 5 | 내부 ID 보유 | 원장 대조값 합의 (UID / internal key) |

> 요청서가 명시적으로 권고합니다 — *"신규 가입자와 기존 미수령 잔액을 분리해서, 각각 독립적으로 결정하자."*

## 7-3. Lighter — 5개 항목

| # | Lighter 현재 | 테더맥스 요청 |
|---|---|---|
| 1 | **주 1회 (월요일, 전주 월~일 집계)** | **일별 원장 + 주간 마감의 집계 윈도우 정의** |
| 2 | USDC 정산 (테더맥스가 1:1 USDT 환산) | **환산 시점과 FX 기준 합의** |
| 3 | **Standard 계정은 페이백 0%** (수수료 0% 티어) | **경고·온보딩 문구를 사용자에게 표시** |
| 4 | 어뷰징 보류 주차 미지급 · $1 미만 미지급 | **보류 건이 원장에 어떻게 나타나는지 동기화 규칙** |
| 5 | **지급 검증 = 온체인 해시** (4곳 중 유일) | 대조 기준으로 활용 — CS·정산 추적 공용 참조 |

## 7-4. EdgeX — 선택 API 5종 제안

EdgeX에는 다른 3곳에 없는 **추가 제안**이 들어가 있습니다.

| Phase | 항목 | 내용 |
|---|---|---|
| 1 | **Webhook** | 30초 폴링을 실시간 푸시로 대체 (30일 내) |
