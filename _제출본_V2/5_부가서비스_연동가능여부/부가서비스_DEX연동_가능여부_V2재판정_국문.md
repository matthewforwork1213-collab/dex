# 0. 왜 전면 재판정인가

V1에서 배제한 **11종은 전부 같은 하나의 이유**로 배제됐습니다.

> **"테더맥스가 DEX 사용자에게 돈을 보낼 수단이 없다"**

V2에서 **Wallet B 자동 지급이 생겼습니다.** 그 이유가 통째로 사라졌으므로 **배제 11종 전부가 재판정 대상**입니다. 방침 공표 15장이 이를 **결정 4번(신규·최중요)**으로 지목했습니다.

## 0-1. 판정 원칙이 바뀝니다

| | V1 원칙 (A-08) | **V2 원칙** |
|---|---|---|
| 기준 | 자격을 만드는 행위는 포함, **돈을 받는 목적지에서는 배제** | **지급 수단이 생겼으므로 목적지 배제 근거가 없음** |
| 새 기준 | — | **데이터가 있으면 적용, 없으면 배제** |

V2에서 배제의 유일한 사유는 **"필요한 데이터를 DEX가 주지 않는다"**입니다. 자금 수단은 더 이상 제약이 아닙니다.

## 0-2. ~~새로운 제약 — 선택 필드~~ → **제약 없음으로 정정** (2026-10-21)

> ### 이 절의 기존 내용은 **오류**였습니다.
>
> 기존에 이렇게 적었습니다:
> ```
> 선택 필드 02  symbol · volume
>      ├─▶ 있으면   글로벌리그 · 맥스보드 작동
>      └─▶ 없으면   두 기능 불가
> ```
> *"이것이 V2의 유일한 기능 제약"* 이라고 결론냈으나, **세 서비스 모두 거래량을 쓰지 않습니다.**

| 서비스 | 실제 산정 기준 | 근거 |
|---|---|---|
| **글로벌리그** | `1 USDT 커미션 페이백 = 1 point` | MAX-8 §3 Score Logic |
| **페이백 랭킹 / 월간 랭킹** | 페이백 금액 순위 | 2026-10-21 확정 (K-1) |
| **맥스보드** | 게이지·연속·랭킹 **전부 페이백 기준** | 맥스보드 PRD 서비스기획서 §1.1 |

> 맥스보드 PRD 원문: *"새로 등록한 UID로 거래하면 받는 **페이백이 그대로 빙고 게이지**가 되고"*
> 랭킹도 *"완성자 한정, **총 페이백 순위**, 매일 갱신"*

**테더맥스는 거래량을 기록하는 시스템 자체가 없습니다.** `symbol`·`volume`은 처음부터 불필요했으며,
거래소 API 요청서의 선택 항목에서 **삭제**했습니다.

→ **V2에는 데이터 의존 제약이 남아 있지 않습니다. 조건부 판정 0건입니다.**

## 2-9. ✅ 페이백 부스트 — **DEX는 고려하지 않습니다** (2026-10-22 확정)

V2 재판정에서 *"부스트 차액을 이벤트 리워드로 지급하면 되니 O"* 로 올렸으나, **DEX는 부스트 대상이 아닌 것으로 확정**됐습니다.

### 왜 이 판정이 맞나

| 컬럼 | CEX | DEX |
|---|---|---|
| `타 플랫폼` | 경쟁 페이백 서비스의 요율 | **출처가 없습니다.** 어느 경쟁사도 DEX 수치를 공개하지 않습니다 |
| `공식 파트너` | 우리 페이백률 | 상업 협의 대기 |
| `🚀 부스트 적용` | 부스트 후 최종 요율 | **DEX에 부스트가 존재하지 않습니다** |

→ DEX 행을 넣으면 **세 컬럼 중 둘이 빈 채로 노출**됩니다.

### 조치

| # | 대상 | 조치 |
|---|---|---|
| 1 | `페이백 부스트` 화면 | **DEX 행을 넣지 않습니다.** 거래소 목록은 CEX만 |
| 2 | 부스트 적용 거래소 선택(어드민) | **DEX를 선택지에서 제외** |
| 3 | 부스트 안내 문구 | DEX를 포함하는 표현이 있으면 제거 |
| 4 | 결정요청서 `D-7` | **해소** — 권고안대로 확정 |

> **V1과 같은 결론이지만 이유가 다릅니다.** V1은 *"지급 수단이 없어서"* 였고, V2는 *"비교할 숫자가 없고 부스트 개념 자체가 DEX에 없어서"* 입니다.

## 2-10. ✅ 페이백 챌린지 — **DEX를 반영하지 않습니다** (2026-10-22 확정)

V2 재판정에서 *"수령 UID 제약이 풀렸으니 완전 적용"* 으로 올렸으나, **챌린지는 DEX를 반영하지 않는 것으로 확정**됐습니다.

### V1·V2·확정의 차이

| | 게이지 | 수령 |
|---|---|---|
| **V1 (부분)** | DEX 페이백도 참 | **DEX 수령 불가** |
| V2 재판정 (O) | 참 | 가능 |
| **확정 (X)** | **DEX 페이백 안 참** | **DEX 안 뜸** |

> **V1의 어중간한 상태가 함께 사라집니다.** *"게이지는 차는데 받을 수는 없다"* 는 사용자가 이유를 알 수 없는 상태였습니다. 이제 챌린지는 **CEX 전용** 하나의 규칙입니다.

### 조치

| # | 대상 | 조치 |
|---|---|---|
| 1 | 챌린지 게이지 화면 | **DEX 안내 문구 없음.** CEX 기준으로만 설명 |
| 2 | 수령 계정 선택 모달 | **DEX 그룹·지갑 행 제거.** CEX UID만 |
| 3 | 페이백 내역 `유형` 필터 | `챌린지 리워드`는 **CEX 전용** — DEX 계정 필터와 함께 고르면 항상 빈 결과 |
| 4 | 챌린지 관련 알림 | DEX 대상 **제외** |
| 5 | 갱신 시각 문구 `매일 13:00 (UTC)` | **이 화면은 수정 불필요해졌습니다.** DEX 갱신 시각(D+1 00:00 UTC · Aster 09:00 이후)을 덮을 필요가 없어졌기 때문입니다. **다른 화면에서는 여전히 고쳐야 합니다** |

### 🔴 하나 남은 결정 — 게이지 합계에 DEX를 셀 것인가

화면은 **「페이백」** 이라고 말하고, **홈의 총 페이백에는 DEX가 들어갑니다.**

```
홈     총 페이백 잔액   1,240.00 USDT   ← CEX + DEX
챌린지  Level 1        980 / 1,000 USDT  ← CEX만?
```

→ 양쪽에서 거래하는 회원은 **두 숫자가 어긋나는 것을 보고도 이유를 알 수 없습니다.**

| 안 | 내용 |
|---|---|
| **A** | 게이지에서 DEX를 빼고 **화면에 「CEX 거래 기준」을 명시** |
| B | 게이지는 DEX까지 세되 **수령만 CEX** — V1의 어중간한 상태로 되돌아갑니다 |

> **권고 — A.** B는 방금 없앤 상태입니다. 다만 **문구를 쓰지 않으면 A도 B만큼 혼란스럽습니다.**

> **부스트와 결론은 같지만 이유가 다릅니다.** 부스트는 *비교할 숫자가 없어서*, 챌린지는 *정책 결정*입니다. 챌린지는 구조상 DEX로도 충분히 됩니다.

# 2-2. ★ UID 소유권 신청 — **DEX 미지원 확정** (2026-10-22)

> **결론: DEX에서는 소유권 인증을 지원하지 않습니다.**
>
> 10-21에 디자인을 근거로 적용(O)으로 올렸다가, 10-22에 **정책 결정으로 되돌렸습니다.**
> 아래 설계는 **CEX 경로로 그대로 유효**하며, DEX만 이 분기를 타지 않습니다.

## 2-2-1. 되돌림으로 사라지는 작업

| 항목 | 상태 |
|---|---|
| 신청 페이지 O3~O10 (영상 업로드·가이드 슬라이드·제출 시트) | **DEX 해당 없음** |
| 심사 상태 O11~O16 (심사중·승인·반려·재신청) | **DEX 해당 없음** |
| 30일 소유권 쿨다운 · `FAILED_RECENT_POSSESSION` | **DEX 해당 없음** |
| 소유권 알림 3종 (승인·반려·피해제자 연동 해제) | **DEX 해당 없음** → 알림 재작성 범위 **3건 감소** |
| 백오피스 가이드 슬라이드 **DEX 4곳 × 2디바이스 × N** | **제작 불필요** |
| 어드민 심사 화면 영상 플레이어 (DEX 행) | **불필요** |
| `FAILED_ALREADY_INTEGRATION` 의 `소유권 인증` CTA | **DEX 분기에서 제거** → 고객센터로 |

> **백오피스 `Exchange Guide → UID Ownership Verification` 섹션 자체는 여전히 신규 구축입니다.**
> MAX-431이 CEX용으로 지시한 것이며, DEX 세트만 빠집니다.

## 2-2-2. 🔴 남는 구멍 — 중복 지갑 처리

지갑 주소는 **온체인 공개 정보**입니다. 본인 소유가 아닌 주소를 연동할 수 있는데,
소유권 경로가 없으면 **정정 수단이 고객센터뿐**입니다.

**결정 필요:** 고객센터가 요청만으로 연동을 해제할지, 어떤 증빙을 받을지.

# 5-2. ★ 맥스보드 — 유일하게 남은 DEX 고유 제약

맥스보드는 작동하지만, **Lighter에서 연속 칸이 열리지 않습니다.**

> **맥스보드 PRD REQ-040**: 연속 칸은 **페이백 배치 반영일 기준 N일 연속** 페이백 시 활성화

| 거래소 | 정산 주기 | 연속 칸 | 금액 칸 |
|---|---|:-:|:-:|
| **Lighter** | **주 1회 (월)** | **❌** | ✅ |
| ApeX | 시간당 | ✅ | ✅ |
| EdgeX | 일 1회 00:00 UTC | ✅ | ✅ |
| Aster | 일 1회 (09:00 공개) | ✅ | ✅ |

주 1회 정산이면 7일 중 1일만 페이백이 찍히므로 **2일 연속조차 성립하지 않습니다.**

### 대응 — **정산 주기 변경이 전제** (2026-10-21 확정)

```
전제   Lighter에 일 단위 원장 제공 요청 (지급은 주 1회 유지 가능)
         └─ 연속 판정은 지급일이 아닌 원장 반영일 기준이므로 일별 원장만 있으면 해결

불가 시 → Lighter 빙고판을 열지 않음
```

> **"금액 칸만 구성"은 기술적으로 가능하지만(REQ-113) 운영 판단으로 채택하지 않습니다.**
> 연속 칸은 거래 습관을 만드는 장치라, 빠지면 맥스보드의 핵심 가치 하나가 사라지기 때문입니다.
> → **맥스보드 1차 대상은 ApeX · EdgeX · Aster 3곳입니다.**

### 추가 — 빙고 Batch 시각

> **REQ-036**: 빙고 Batch는 하루 1회 **전 거래소 공통 고정 시각**, Bitget 페이백 배치 이후 (시각 미정 `#BATCH`)

Aster는 **00:00 UTC 산정 → 09:00 이후 공개**입니다.
빙고 Batch가 09:00보다 빠르면 **Aster 페이백이 매일 하루씩 밀리고 연속 판정도 같이 밀립니다.**

→ 빙고 Batch 시각 조건에 **"Aster 09:00 UTC 이후"** 를 추가해야 합니다.
