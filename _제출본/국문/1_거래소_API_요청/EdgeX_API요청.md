## 1. D1~D8 확인 내용

### D1 — 수익 배분, 단일 요율 · **확인**

공유 요율 모델을 수용합니다. 트레이더 리베이트와 테더맥스 커미션이 모두 `fee × partnerRate`에서 나오고, 트레이더 몫을 우리가 정합니다.

EdgeX가 제시한 예시와 이해가 일치합니다. `partnerRate` 60%, A가 30% 코드로 가입하고 B를 10%로 초대한 경우 → A 38, B 10, 테더맥스 48, 합계 96 = 160 × 60%.

`partnerRate` 값 자체는 상업 항목입니다 (4장).

### D2 — 요율은 테더맥스가 설정, 등급 없음 · **확인**

수용하는 내용입니다.
- EdgeX가 파트너 콘솔에서 `partnerRate` 설정
- 우리가 하위 사용자 요율을 설정하되 `partnerRate`를 넘지 않음
- 각 레퍼럴 코드가 자체 `registrationRate` 보유
- 거래량에 따라 자동 상승하지 않음
- 레퍼럴 검증의 "등급"은 코드의 `registrationRate`

**표시 요율은 `rebateRate`를 그대로 쓰고 실제보다 높게 표시하지 않습니다.** `user.rate_changed`를 표시 요율 갱신 신호로 처리합니다.

### D3 — 귀속 범위, 팀 전체 · **확인 + 요청 1건**

팀 전체 귀속을 수용합니다. `isTethermaxReferral: true`를 팀 전체에 대해 `level`과 함께 반환해 주시면, `level`·`referrerUserId`·`referralCode`를 저장하고 필요에 따라 필터링하겠습니다.

**가입을 완료한 사용자만 반환된다**는 점도 확인했습니다. 지갑을 연결했지만 가입하지 않은 경우는 귀속되지 않습니다. 우리 처리와 일치합니다 — 확인되지 않은 지갑은 연동하지 않고 보류합니다.

### D4 — 리베이트 금액에 하위 오버라이드 포함 · **확인 + 요청 1건**

4가지 금액 구조를 이해했고, 하위를 초대한 회원의 `rebateAmount`가 `feeBasis × rebateRate`보다 클 수 있다는 점도 확인했습니다.

**회원에게는 `selfRebateAmount`만 표시합니다.** `rebateAmount`와 `downlineRewardAmount`는 대조용으로만 씁니다.

**요청: 테더맥스 팀에 대해 회원 간 추천 오버라이드를 비활성화해 주십시오.**

두 가지 이유입니다.
1. **우리가 사용자에게 고지한 규칙과 충돌합니다.** 테더맥스는 DEX 활동에 추천·초대 리워드를 지급하지 않습니다. 팀 회원이 하위 오버라이드를 받으면, 우리 프로그램 안에서 사용자가 추천 수익을 얻는 셈이 되는데 이것은 "그런 일이 없다"고 안내한 내용과 정면으로 어긋납니다
2. **같은 `partnerRate` 재원에서 나가므로 우리 커미션을 줄입니다**

비활성화되면 `rebateAmount`가 `selfRebateAmount`와 같아지고, `totalPaidAmount`가 표시값과 일치해 대조가 크게 단순해집니다.

**불가능하다면 알려주십시오.** `selfRebateAmount`만 표시하고 차액은 내부 대조 항목으로 처리하겠습니다.

### D5 — 출금 가능 잔액 미제공 · **확인**

전적으로 수용합니다. 지급 후에는 마진에 포함되어 구분할 수 없고, 계정의 출금 가능 금액은 계정 소유자의 정보라는 점을 이해합니다.

카드 표시는 이렇게 합니다.
- **`Paid to your EdgeX account`** = `totalPaidAmount`
- **`On the way`** = `accruingAmount` + `pendingAmount`

**EdgeX에 대해서는 어디에도 출금 가능 금액을 표시하지 않습니다.**

### D6 — 레코드 ID · **확인**

EdgeX 리베이트 레코드 `id`를 키로 사용하고, `collateralTransactionId`와 `transferId`를 트레이더 계정 대조용 참조로 씁니다.

0.01 USDC 미만과 지급 실패가 이월되어 **하나의 지급이 여러 레코드를 포괄**할 수 있다는 점도 반영했습니다. 해당 레코드는 지급이 포괄할 때까지 `On the way`에 남습니다.

`FILL_FEE_INCOME`이 EdgeX 수수료 계정의 수입이고 트레이더 계정 항목이 아니라는 점, 리베이트는 `TRANSFER_IN`으로 도착한다는 점도 확인했습니다.

### D7 — 커미션 일 1회 지급 · **확인 + 질문 1건**

USDC로 테더맥스 EdgeX 선물 계정에 매일 자동 지급되는 방식을 수용합니다.

**질문:** 재무팀이 일별 커미션 레코드와 월 명세서 외에 **인보이스나 다른 증빙 문서**가 필요한지 묻습니다. EdgeX가 통상 파트너에게 제공하는 방식을 알려주시면 거기에 맞추겠습니다.

### D8 — 일 1회 00:00 UTC 정산 · **확인**

일 1회 정산을 수용합니다. 표시 시에는 UTC 일 단위로 묶으므로, 요구사항 문서의 1시간 예시에서 바뀌어도 사용자 화면에는 영향이 없습니다.

데이터 지연 판정도 이 주기에 맞췄습니다. 전일 레코드를 01:00 UTC까지 기대하고, 그 이후 임계치를 넘으면 지연으로 처리합니다.

### D9 — 지갑 로그인 기록 · **범위 제외**

10월 13일에 회신한 대로 범위에서 제외합니다. 두 회원이 같은 지갑을 주장하는 분쟁은 **고객센터가 처리**합니다. EdgeX 측 조치는 필요 없습니다.

## 2. 추가 요청 4건

### 2-1. 벌크 레퍼럴 목록 API — **중요**

10월 19일에 제기한 항목입니다.

**일별 커미션 레코드에는 그날 거래한 회원만 들어갑니다.** 그래서 우리에게 귀속됐지만 거래하지 않은 회원을 볼 수 없습니다. 세 가지 이유로 필요합니다.

| 이유 | 내용 |
|---|---|
| **연동** | 트레이더가 지갑 주소를 붙여넣었을 때 우리 팀 소속인지 확인해야 하는데, 아직 거래 전이면 어느 레코드에도 없습니다 |
| **표시** | 연동됐지만 적립이 0인 것은 정상 상태입니다. "우리 팀이 아님"(오류 상태)과 구분해야 하는데, 두 경우 사용자에게 보여줄 메시지가 완전히 다릅니다 |
| **대조** | 팀 명단을 열거할 수 없으면 대조가 불가능합니다 |

`ethAddress` 단건 조회는 개별 케이스를 커버하지만, **거래 여부와 무관하게 테더맥스에 귀속된 전체 계정을 페이지네이션으로 반환하는 목록**이 추가로 필요합니다. 최소 반환 필드는 `ethAddress`, `userId`, `accountId`, 가입 시각, `rebateRate`, `level`, `referrerUserId`, `referralCode`입니다.

### 2-2. API 사양 자체

역시 10월 19일에 요청했습니다. 설계는 받았지만 **실제 엔드포인트·인증·파라미터·응답 형식은 아직 받지 못했습니다.**

다음 단계 안내에 따르면 정렬 항목 확인 후 제공되는 것으로 이해했고, 이 회신이 그 확인입니다. 지금 받을 수 있으면 좋겠습니다.

계획 수립을 위해 인증은 `X-edgeX-Api-Key`, `X-edgeX-Passphrase`, `X-edgeX-Timestamp`, HMAC-SHA256 `X-edgeX-Signature`를 IP 허용 목록에서 호출하는 방식으로 가정하고 있습니다. 다르면 알려주십시오.

### 2-3. 신규 귀속·Pending→Paid 웹훅

설계에는 `user.rate_changed`만 있습니다. 두 가지가 더 필요합니다.

| 이벤트 | 필요 payload | 이유 |
|---|---|---|
| **신규 귀속** | `ethAddress`, `userId`, `accountId`, 가입 시각, 고유 `eventId` | **해당 지갑의 리베이트 수령 계정을 여기서 처음 알게 됩니다.** 회원은 이 값을 직접 입력하지 않습니다 |
| **리베이트 Pending → Paid** | `ethAddress`, `userId`, `accountId`, 레코드 `id`, `payoutId`, 이전·신규 상태, 갱신 시각, 고유 `eventId` | 트레이더가 다음 폴링을 기다리지 않고 상태 변화를 봅니다 |

푸시에 서명을 넣고, 우리가 HTTP 200을 반환할 때까지 24시간 동안 백오프 재시도하며, 중복 제거를 위해 고유 `eventId`를 포함해 주시기를 요청합니다.

출시 시점에 웹훅이 없어도 폴링으로 가능합니다. 다만 **미리 알려주시면 그에 맞춰 설계**하겠습니다.

### 2-4. 정정 처리와 제한 지역

**정정.** 일별 레코드의 정정이나 취소는 어떻게 표현됩니까? 원본 `id`를 참조하는 **새 레코드**를 기대하며, 원본 수정은 아닐 것으로 봅니다. 우리 수집 로직은 레코드를 불변으로 다루고 마감 후 48시간에 확정합니다.

**제한 지역.** `geoRestrictions`와 `otherRestrictions`(캠페인 기간 등)를 사전 공지로 받고 싶습니다. 우선순위는 가장 낮습니다.

## 3. EdgeX가 요청한 다음 단계 — 우리 답변

### 3-1. 메인 계정 등록

이해했습니다. 커미션 수령·출금, 파트너 콘솔 로그인, API 자격증명 보유에 쓸 테더맥스 메인 계정을 EdgeX에 등록하겠습니다.

**계정의 지갑 주소를 별도로 전달**하여 파트너 권한을 활성화해 주시도록 요청하겠습니다.

### 3-2. 공동 테스트

테스트넷 환경을 요청드립니다.

**테스트 계획** — 자체 스테이징 환경이 있으며 아래 순서로 검증합니다.

1. **귀속** — 스테이징에서 지갑 붙여넣기 → 귀속 조회 → `userId`, `accountId`, `rebateRate`, `level` 반환 확인, 비귀속 지갑이 올바르게 거부되는지 확인
2. **일별 레코드** — 01:00 UTC까지 레코드가 들어오고 금액 필드가 기대대로인지, 수집이 레코드 `id` 기준으로 멱등한지 확인
3. **상태 전이** — Pending → Paid 전환과 `payoutId`·`transferId`·`collateralTransactionId` 도착 확인
4. **이월** — 0.01 USDC 미만 금액이 pending에 남고 이후 지급이 포괄하는지 확인
5. **요율 변경** — `user.rate_changed`가 표시 요율을 갱신하는지 확인
6. **대조** — 테스트 기간의 합계가 양측에서 일치하는지 확인

**EdgeX가 요청한 자료**
- API 호출에 사용할 egress IP — **지갑 주소와 함께 전달**
- 테스터 이메일 주소 — 동일
- 테스트넷 계정 등록 — 진행 예정

테더맥스에서 귀사 프로그램을 **어느 지역에** 노출할지에 영향을 주는 질문 2건입니다. 연동을 막는 항목은 아닙니다.

|---|---|---|

각 항목에 짧게만 답해 주셔도 충분합니다.

## 5. 우리 측 데이터 처리 규칙 (참고용)

| 규칙 | 내용 |
|---|---|
| 키 | `ethAddress` + `accountId`가 계정 키, EdgeX 레코드 `id`가 레코드 키 |
| 불변성 | 레코드는 수정하지 않음. 정정은 원본을 참조하는 새 레코드 |
| 확정 | 회원당 UTC일 1건, 해당 일자로 기록. 마감 후 48시간에 확정 |
| 회원 표시 | `selfRebateAmount`를 캐시백으로, `rebateRate`를 요율로 표시 |
| 통화 | 리베이트와 커미션은 USDC. 회원에게는 USDT로 1:1 액면 표시. **통화 없는 레코드는 거부** |
| 지갑 주소 | 소문자 16진수, 대소문자 구분 없이 비교. 파트너가 보낸 주소도 사용자 입력과 동일 규칙으로 검증. **무효 주소는 조용히 버리지 않고 검토 보류 후 EdgeX에 보고** |
| 개인정보 | 요청하지 않음 |
| 조회 기간 | 최대 180일 |

### 대조 검사

| 단위 | 검사 |
|---|---|
| 레코드 | `selfRebateAmount = feeBasis × rebateRate`, `rebateAmount = selfRebateAmount + downlineRewardAmount` |
| 지급 | `payoutId`를 공유하는 레코드의 `rebateAmount` 합 = `transferId`·`collateralTransactionId`로 식별되는 이체 |
| 계정 | `totalPaidAmount` = Paid 레코드 합, `pendingAmount` = 정산·미지급 레코드 합 |
| 커미션 | 일별 `partnerCommissionAmount` 합 = 그날 커미션 레코드 |
| 월 | 통화별 레코드 합 = 월 명세서 |

**미매칭 레코드는 버리지 않고 보류한 뒤 주간으로 보고**합니다. 양측 모두 명세서 후 30일 내에 레코드 `id`를 인용해 이견을 제기할 수 있습니다.

## 6. 수기 CSV 대체 경로 (API 미개통 시)

02:00 UTC까지 접근 통제 공유 폴더로 일 1회 전달. 컬럼은 다음과 같습니다.

```
id, ethAddress, userId, accountId, periodStartTime, periodEndTime,
feeBasis, rebateRate, selfRebateAmount, downlineRewardAmount,
rebateAmount, partnerCommissionAmount, coinSymbol, rebateState,
paidTime, payoutId, transferId, collateralTransactionId
```

지급 필드는 지급 전까지 비어도 됩니다. **`coinSymbol`이 USDC가 아니거나 `id`·`accountId`가 없는 행은 거부**합니다.

## 7. 보안

- **읽기 전용 파트너 키.** 거래·이체·출금 불가
- 테더맥스 보안 키 저장소에 보관, IP 허용 목록에서만 사용
- 지갑 주소·`userId`·`accountId`는 사용자 노출 URL, 분석 이벤트, 외부 노출 로그에 넣지 않음
- **테더맥스는 트레이더에게 개인키·시드 문구·지갑 서명을 절대 요구하지 않습니다.** 공개 지갑 주소만 붙여넣습니다. 공동 브랜딩 자료에 EdgeX도 같은 내용을 기재해 주시기를 요청합니다
