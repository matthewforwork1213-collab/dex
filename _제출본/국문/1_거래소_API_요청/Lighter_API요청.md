## 발송 전 참고

Lighter는 응답이 가장 빠르고 구체적입니다. **10월 19일 senya 답변으로 "단일 지갑 즉시 확인" 문제가 이미 해결됐습니다.** 이전 버전 요청서에 있던 그 질문은 삭제했습니다.

남은 실질 쟁점은 **마스킹 충돌** 하나입니다. senya가 제시한 방법(마스킹 대조)은 식별 문자가 6개뿐이라 다른 지갑과 겹칠 수 있는데, 이 부분은 아직 논의되지 않았습니다.

요율은 Supertramp가 10월 10일에 "20% referral fee kickback + 10% referee fee discount"를 언급했습니다. 확정 여부 확인이 필요합니다.

## 1. 합의 요율 — P0

10월 10일에 첫 주 리베이트를 **주차 이월되는 10% referee 수수료 할인 + 테더맥스 20% referral fee kickback** 구조로 전환 중이라고 하셨습니다. 또한 레퍼럴 지급이 아직 자동화되지 않고 주간 처리이므로 **분배는 우리가 원하는 대로 계산할 수 있다**, 예를 들어 우리 kickback에서 더 높은 비율을 referee에게 돌려줄 수 있다고 하셨습니다.

마무리를 위해 두 가지가 필요합니다.

**(a) 20% kickback과 10% referee 할인이 현재 적용 중입니까, 아직 전환 중입니까?** 첫날부터 정확한 숫자를 트레이더에게 안내하고자 합니다.

**(b) 우리 20% 중 일부를 referee에게 돌려주기로 하면, 그 분배 비율을 어떻게 전달합니까?** 합의에 따라 Lighter가 설정하는 값입니까, 매주 우리가 숫자를 알려드리는 방식입니까, 아니면 우리가 20%를 전부 받고 트레이더 몫을 자체 처리합니까?

**왜 중요한지.** 월요일 지급 사이에 `userReferrals`로 "이번 주 지불 수수료 × 합의 요율"을 계산해 주중 추정치를 보여줍니다. 최종 숫자가 없으면 **지급 사이에 트레이더에게 아무 숫자도 보여줄 수 없습니다** — 캐시백이 주 1회만 나타나고 나머지 기간은 빈칸이 됩니다.

해당 수치는 항상 추정치로 표시하고 지급 합계에는 넣지 않습니다.

## 2. 마스킹 충돌 — P0

마스킹 매칭 흐름에서 **우리가 단독으로 해결할 수 없는 유일한 부분**이며, 의견을 듣고자 합니다.

**상황.** 10월 19일 안내에 따라, 트레이더가 Lighter 지갑을 붙여넣으면 같은 방식으로 마스킹해 `userReferrals`에서 일치하는 행을 찾습니다. 마스크는 체크섬 주소의 앞 4자와 뒤 4자를 남기므로 **식별 가능한 16진수가 6자**입니다.

**위험.** 6자는 고유하지 않습니다. referee 목록이 커지면 결국 서로 다른 두 지갑이 같은 마스크를 갖게 됩니다. 그러면 눈앞의 트레이더가 어느 행인지 판별할 수 없습니다.

**그냥 넘길 수 없는 이유.** 잘못된 행에 매칭하면 다른 트레이더의 바인딩 시각이, 더 나아가 **그 행의 주중 추정치가** 엉뚱한 사람에게 붙습니다. 표시 문제가 아니라 정합성 문제입니다.

**별도 안내가 없을 경우 우리 처리 방안**

| 경우 | 처리 |
|---|---|
| 마스킹 일치 정확히 1건 | 즉시 연동. `used_at`을 바인딩 시각으로 사용 |
| **마스킹 일치 2건 이상** | **연동하지 않음.** 전체 지갑이 담긴 다음 주간 CSV로 확정 |
| 일치 없음 | 테더맥스 레퍼럴이 아닌 것으로 처리 |

**문제를 완전히 없애는 방법** (선호 순)

1. **전체 지갑 주소 1개를 받아 테더맥스 referee인지 반환하는 엔드포인트.** `used_at`과 `tier`만 함께 주면 충분하며, 다른 referee 정보를 노출할 필요가 없습니다
2. 마스크 길이 확대 — 식별 문자를 6자에서 8자로만 늘려도 우리 규모에서는 충돌이 무시할 수준이 됩니다
3. 둘 다 어렵다면 충돌을 주간 CSV에 맡기는 것으로 확인해 주십시오. 위 표대로 구현하겠습니다

1번이 가장 좋지만 마스킹의 프라이버시 취지를 이해하며, 다른 파트너를 위해 그것을 약화시켜 달라는 요청은 아닙니다.

## 3. 마스킹 매칭 구현 확인 — P1

잘못 만들지 않도록 10월 19일 답변에 대한 우리 이해를 확인 부탁드립니다.

| 단계 | 구현 |
|---|---|
| 1 | 읽기 전용 토큰으로 `GET /api/v1/referral/userReferrals?l1_address=<우리 코드 지갑>&limit=300`을 스케줄 폴링하고 캐시 |
| 2 | 결과가 **최신순**이므로 방금 가입한 트레이더는 첫 페이지에 있음 |
| 3 | 트레이더가 지갑을 붙여넣으면 **EIP-55 체크섬 형식으로 변환**한 뒤 **그 문자열의 앞 4자와 뒤 4자**를 남겨 `0x12…abcd` 형태로 만들고 캐시에서 일치 행 검색 |
| 4 | 일치 행의 `used_at`이 바인딩 시각 |
| 5 | 공개 엔드포인트 `GET /api/v1/accountsByL1Address?l1_address=<붙여넣은 지갑>`으로 메인 계정 인덱스와 서브계정 조회. 레퍼럴 바인딩이 전부를 포함하는 것으로 처리 |
| 6 | 주간 CSV가 나중에 전체 지갑으로 확정 |

**특히 확인하고 싶은 두 가지**

**(a) 마스크는 소문자가 아니라 체크섬 주소 기준으로 계산합니다.** 우리는 매칭을 위해 주소를 소문자로 저장하므로, 마스킹 전에 EIP-55 형식으로 되돌려야 합니다. 소문자 상태로 마스킹하면 글자가 맞지 않습니다. 맞는지 확인 부탁드립니다.

**(b) "앞 4자와 뒤 4자"는 `0x` 접두사를 포함한 문자열 기준의 앞 4자** — 즉 `0x` + 16진수 2자, 그리고 뒤 16진수 4자 — 로 이해했습니다. 예시 `0x12…abcd` 및 v2 문서의 "0x + first 2 + last 4 hex" 표현과 일치합니다. 확인 부탁드립니다.

## 4. 주간 CSV 전달 — P1

세 가지입니다.

**(a) 전달 방식.** 접근 통제 공유 폴더를 제안합니다. 다른 방식을 선호하시면 알려주십시오.

**(b) 월요일 몇 시.** **월요일 23:59 UTC까지**를 제안합니다. 그때까지 도착하지 않으면 Lighter 수치를 지연 상태로 표시하고, 아무것도 안 보이거나 0이 되는 대신 마지막 금액과 시각을 함께 보여줍니다.

**(c) 커버리지 — 매주 모든 referee가 포함됩니까, 그 주에 수수료를 낸 referee만 포함됩니까?**

세 번째가 보기보다 중요합니다. 수수료를 낸 referee만 나온다면, 그 주에 거래하지 않은 referee는 파일에서 그냥 빠지는데 **우리가 그 부재를 실패하거나 만료된 레퍼럴로 읽으면 안 됩니다.** 규칙을 알면 거래 없는 주를 올바르게 처리할 수 있습니다.

## 5. $1 미만 주차 — P1

referee의 한 주가 **$1 최소액** 미만이면 그 금액이 **이후 지급으로 이월됩니까, 소멸됩니까?**

어느 쪽이든 그 주를 Paid로 표시하지는 않습니다. 다만 답변에 따라 금액을 적립 중으로 계속 보여줄지 지울지가 달라집니다.

## 사용하는 엔드포인트

| 엔드포인트 | 인증 | 용도 |
|---|---|---|
| `GET /api/v1/referral/userReferrals?l1_address=` | 읽기 전용 토큰 | referee별 1행: 마스킹 주소, 코드, `used_at`, `tier`, `source`, `trade_stats`. 커서 페이징 최대 300. **시간당 폴링** |
| `GET /api/v1/referral/stats?l1_address=` | 읽기 전용 토큰 | 최근 12주 버킷, referee 합산 |
| `GET /api/v1/transfer_history?account_index=&type=ReferralProgramPayout` | 계정 소유자 | 주간 지급 이체: id, 금액, 시각, tx hash |
| `GET /api/v1/referral/get?account_index=` | 읽기 전용 토큰 | 우리 활성 코드 |
| `GET /api/v1/accountsByL1Address?l1_address=` | 공개 | 메인 계정 인덱스와 서브계정 |
| 주간 CSV | — | 테더맥스 referee만: 주차, 전체 지갑, `account_index`, 바인딩 시각, tier, 지불 수수료, 캐시백, 테더맥스 몫, 상태, tx hash |

## 우리 측 데이터 처리 규칙

| 규칙 | 내용 |
|---|---|
| 키 | `l1_address`, 소문자 16진수, 대소문자 구분 없이 비교. 지갑당 Lighter 계정 1개 |
| 주중 추정치 | 이번 주 지불 수수료 × 합의 요율. **항상 추정치로 표시하고 지급 합계에 넣지 않음** |
| 마스킹 주소 | 붙여넣은 지갑 매칭에만 사용. **회원에게 식별자로 표시하지 않음** |
| 통화 | 전부 USDC, 회원에게는 USDT로 1:1 액면 표시 |
| Standard 등급 | 적립 0. `tier`에서 Standard 상태 표시 |
| 적격 | 2026-07-28 이후 바인딩만 |
| 정산 기준 | 월요일 CSV. 그 주 추정치를 대체하며 Paid·Withheld의 유일한 출처 |
| 임포트 검증 | 지갑·주차·상태·금액 없는 행은 거부 |
| 개인정보 | 요청하지 않음 |
| 조회 기간 | 최대 180일 |

**대조**
- 주간 CSV를 **전체 지갑 주소**로 연동 지갑과 매칭
- 아직 연동되지 않은 지갑의 CSV 행은 보관했다가 나중에 연동될 때 매칭합니다. 마스킹으로 연동한 지갑의 확정에도 사용합니다
- 주간 테더맥스 몫 합계 = 해당 주 우리 `ReferralProgramPayout` 이체
- 주간 수수료 = `referral/stats` 주간 버킷
